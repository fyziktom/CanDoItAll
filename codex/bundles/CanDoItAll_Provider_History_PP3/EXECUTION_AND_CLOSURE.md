# Execution stages and closure decision

## Practical sequence

Entry: inspect current source/dependency pair, retained PP2 evidence and private fixture ownership;
arrange signing, map touched consumers and baseline the dev loop. Credit earlier PP2 testing by exact
source hash; do not rerun all 19 cases before a one-family Tooltip regression.

S0: reproduce and close Tooltip lifecycle cancellation at its actual owner with positive/negative
controls and a consuming Blazor host. Record and sign the sibling correction. Continue PP3 rather
than turning a small shared-component fix into another full provider closure cycle.

PP3a: complete the existing History workspace/filter/results family and state seams. Build actual
production projects and run discovered unit/component tests. Review graph and public contracts.

PP3b: complete metadata/content rendering and lifetime, both production entry points, independent
scenarios, publish and large-desktop browser behavior. Preserve scope/auth boundaries and old owners.

PP3c: final native multi-instance History/consumer campaign, selected regression, watch measurements,
statics/docs/export, signed checkpoints and cleanup. Rebuild exact final images and verify the tested
Components source. No code changes after freeze without explicit test/image invalidation accounting.

## Broad checkpoint decision

Do not repeat the prior qualified Stable just to improve a headline. At entry and at final freeze,
record the actual changed production, test-support and build files. Apply current repository named
invalidation rules. A shared BaseLib lifecycle change may merit one final wide component/Stable
checkpoint; no separate whole sweep after each substage. If narrow sibling tests/selected consumers
are sufficient under the rules, document why and exactly which application paths use the change.

Do not use the one-gigabyte tmpfs fixture that caused the previous capacity failure. Separate owned
DB provisioning/cleanup timeouts from normal queries and keep private keys out of logs. Parallel
read-only tests are allowed only with isolated stores/build outputs; never build and hot reload the
same output while collecting proof.

## Defect handling

Repair demonstrated bounded UI lifetime, field reconciliation, asset and harness synchronization
errors in this task with regression tests. Preserve known commits and native diagnostic truth.
An unexpected security/data-integrity failure blocks its mutating/read disclosure path until resolved.
A change requiring global auth, schema or multi-owner durable-protocol redesign needs an explicit
map and follow-up plan, not a speculative large patch. Continue independent safe tests where useful.

Repeated logs must be classified from real caller/circuit/image/time coordinates. Keep unknown
origins explicit. Expected negative tests may assert specific refusal messages, but no blanket
server-error whitelist, disabled browser oracle or 'ignored old errors' over the current run.

## Final report

Use `templates/evidence.json` as an EMPTY structure; never edit the template into a claimed result.
Write actual evidence outside the sealed package. Retain every attempt's commands, discovery,
source/binary/image pair, actual counters, private receipts and sanitized finding summary.
Qualify theory expansion, field-specific follow-ups and source-only scans; do not sum overlapping
selections or silently overwrite failed outcomes.

State separately: `history_ui_complete`, `tooltip_followup_complete`, `native_history_campaign_passed`,
`dependency_delivery` and `application_release_ready`. PP3 does not close provider operational dialogs
or the entire remaining wave. Unavailable external paid evidence is neither a product bug nor a pass.
No paid requests are required or newly authorized; the old live budget remains untouched.

The final safe report names signed SHAs, remaining dirty files, actual served assets, dev-loop mode,
untouched historical bundles, test limitations and exact owned cleanup. A local sibling commit not
yet pushed is reported as a delivery limitation, not silently described as universally available.
