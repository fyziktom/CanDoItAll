FIRST: ADJUDICATE THESE FINDINGS
======================================================================

Before implementation, independently confirm, modify, or reject each finding
against current source and real production composition.

1. Capabilities-01 correctly established a service-free controlled surface
   and a cancellable stale-safe read session.

2. The current assignment handler mutates
   session.Draft.SelectedCapabilityIds before SaveAgentAsync has produced a
   known commit.

3. A validation rejection or optimistic concurrency conflict therefore leaves
   an uncommitted assignment visible in the current UI.

4. CurrentProfileAgentFrameworkWorkspaceService performs canonical agent save
   first and CRM/HR projection/reference-data work afterward.
   AgentDirectoryProjectionSynchronizationException therefore proves a known
   agent commit.

5. Core SaveAgentAsync checks AgentEditorModel.ExpectedUpdatedAtUtc against
   the current AgentDefinition. This is the existing optimistic concurrency
   boundary.

6. FileSandboxWorkspaceStore writes the catalog and subsequently writes the
   workspace index. An exception or cancellation between those stages may
   leave the desired catalog content committed while the caller observes an
   exception.

7. OperationCanceledException after persistence dispatch is not, by itself,
   proof that no assignment was committed.

8. The current capability host catches assignment exceptions generically and
   does not distinguish:
   - validation rejection;
   - concurrency conflict;
   - known canonical commit with secondary warning;
   - genuinely unconfirmed result;
   - pre-dispatch owner cancellation.

9. Assignment and verification busy ownership currently depends primarily on
   session.Generation.

10. A sequence A operation -> select B -> select A can therefore make the old
    A operation invisible to current busy state and permit another operation
    for A before the first one has resolved.

11. The current surface must continue to display authoritative selected
    capability IDs. Pending intent may be shown separately, but must not be
    presented as committed state.

12. Core VerifyCapabilityAsync reads agent/capability/provider, performs the
    diagnostic, and later updates a newly loaded current catalog without
    revalidating that the diagnostic inputs are still current.

13. If the capability is detached while the diagnostic is running, the
    current implementation can still update the global capability proof and
    can update the agent timestamp despite finding no matching attachment in
    the current agent capability list.

14. Capability proof can include filesystem and HTTP observations.
    Reconciliation must not repeat the diagnostic merely to discover whether
    proof persistence committed.

15. Current VerifyCapabilityAsync exposes no typed distinction between:
    diagnostic performed, proof persisted, proof persistence superseded,
    proof persistence committed with warning, and proof persistence
    unconfirmed.

16. Access preview is target-scoped and supports cancellation in its service
    contract, but the current host does not pass a cancellation token.

17. Capability details and setup wizard mutate the global capability catalog,
    not only the currently selected agent. Their natural owner is the
    panel/workspace lifetime, not automatically the selected-agent lifetime.

18. Curator launch is a panel-level fixed-agent effect. Tying its visible busy
    state only to selected-agent generation can permit a second launch after
    an unrelated target change while the first launch remains in progress.

19. StartNewChatAsync is potentially non-idempotent. Cancellation or owner
    replacement after chat creation must not be reported as rollback or
    trigger blind replay.

20. AgentCapabilityList is service-free but remains in
    CanDoItAll.AgentFramework.Components. That project already references
    CanDoItAll.AgentFramework.UI, so a future reverse reference would create a
    cycle.

Record this adjudication in the Capabilities-02 bundle before implementation.

----------------------------------------------------------------------
Immutable assignment attempt
----------------------------------------------------------------------

Capture before the first asynchronous boundary:

- AttemptId;
- AgentId;
- ExpectedUpdatedAtUtc;
- exact immutable before capability-ID set;
- exact immutable desired capability-ID set;
- capability ID that initiated the user intent;
- immutable independent AgentEditorModel request;
- request/submission fingerprint where useful.

Use AgentEditorDraftPolicy.Copy or an equivalent complete public-contract copy
only after confirming it has no unwanted normalization side effects.

Do not pass the live session.Draft into asynchronous persistence.

The user intent is a desired set captured at click time, not a deferred
“toggle whatever state exists later”.

----------------------------------------------------------------------
Authoritative presentation
----------------------------------------------------------------------

Do not mutate session.Draft.SelectedCapabilityIds before a known commit.

Until commit is known, the surface displays the authoritative before set.

A typed pending indicator may identify:

- capability being assigned or removed;
- operation target;
- verification required;
- reconciliation required.

It must not visually claim that the canonical assignment already changed.

----------------------------------------------------------------------
Assignment outcomes
----------------------------------------------------------------------

Use a capability-specific typed result that distinguishes at least:

- Rejected validation;
- Optimistic conflict;
- Committed;
- Committed with secondary warning;
- Definitely not committed after canonical verification;
- Desired current state satisfied after canonical verification;
- Superseded/intervening authoritative state;
- Still unconfirmed;
- Canceled before dispatch.

Do not mechanically copy provider type names or create a universal mutation
framework.

Map AgentDirectoryProjectionSynchronizationException to known commit plus
warning.

Map AgentCatalogConcurrencyException to conflict.

Map AgentEditorValidationException to known rejection.

Unknown exceptions and cancellation after persistence dispatch require
canonical verification unless a lower layer proves the commit state.

----------------------------------------------------------------------
Canonical verification
----------------------------------------------------------------------

Verification of an assignment attempt must only read canonical state. It must
never call SaveAgentAsync.

Classify using AgentId, ExpectedUpdatedAtUtc, before set, and desired set.

At minimum:

1. Current exact desired set with a compatible authoritative revision:
   - desired state is satisfied;
   - reconcile the current editor;
   - do not claim historical causation beyond available evidence;
   - never replay Save.

2. Exact unchanged before set and exact unchanged expected revision:
   - definitely not applied;
   - permit only a deliberate controlled retry using the same immutable
     submission and expected revision;
   - do not auto-retry.

3. Current revision or capability set represents another intervening state:
   - classify as Superseded/Intervening rather than pretending the original
     write succeeded or failed;
   - show the canonical current state;
   - require an explicit user decision to adopt current state or create a new
     intent using the new revision;
   - never replay the old request automatically.

4. Read failure, wrong identity, malformed state, or insufficient evidence:
   - remain unconfirmed;
   - keep blind replay blocked.

A resolved attempt must not remain in recovery bookkeeping. A stale completion
must not clear a newer attempt.

Evaluate whether unresolved assignment recovery must outlive the current
component instance within the same circuit. If component reconstruction
otherwise loses an unresolved submission and permits blind replay, use one
small scoped attempt coordinator. Do not introduce durable storage or copy the
provider recovery hierarchy mechanically.

----------------------------------------------------------------------
Operation ownership
----------------------------------------------------------------------

Assignment ownership must include stable AgentId and AttemptId, not only the
current session generation.

Required behavior:

- only one assignment write per agent may be active;
- switching A -> B -> A cannot start a second A assignment while the first A
  attempt is unresolved;
- an A result cannot update B;
- a stale A finally block cannot clear B or a newer A operation;
- two rapid clicks cannot start two writes before Blazor rerenders;
- a B assignment may run independently only when the design explicitly
  supports and tests per-target concurrency.

Known commit followed by failed reconciliation exposes Retry reconciliation,
not Retry assignment. Reconciliation performs zero additional writes.

----------------------------------------------------------------------
Capability verification
----------------------------------------------------------------------

Capture a semantic input fingerprint sufficient for the proof rule, including
as applicable:

- agent UpdatedAtUtc;
- exact current attachment identity and assignment metadata;
- capability definition fingerprint;
- capability kind/key/configuration/endpoint relevant to proof;
- provider identity and the provider fields or revision used by proof;
- operation/attempt identity.

After the diagnostic completes and before persistence:

- verify that the agent still exists;
- verify that the capability still exists;
- verify that it remains attached to that agent;
- verify that relevant capability, agent, permission, and provider inputs have

If inputs changed:

- do not persist the stale diagnostic;
- do not update the agent timestamp;

attachment exists.

- diagnostic rejected before execution;
- diagnostic performed and proof committed;
- diagnostic performed but persistence superseded;
- proof commit known with secondary warning;
- proof persistence unconfirmed;

stable proof identity such as checked timestamp plus semantic result
fingerprint. It must never rerun the HTTP/filesystem/tool diagnostic.
