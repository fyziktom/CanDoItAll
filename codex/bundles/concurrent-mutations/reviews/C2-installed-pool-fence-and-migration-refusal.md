# C2 installed-pool fence and permanent migration refusal

Approved correction authored in the managed checkout, 2026-10-16; source review and execution remain pending. The narrow installed-pool fence adds four PostgreSQL Facts to the existing five-Fact coordinator class. No build, test, database work or migration generation was run for this candidate. No C2 closure or second-owner activation is claimed here.

## Permanent migration refusal

The ten explicit preflight/postflight/Down refusals in the new migration must use `P0001` (`RaiseException`), not `55000`. The managed migration-body draft and C2 card now say P0001; parent owns the actual generated migration and its four Facts after the frozen run. Existing `20260910225242_AddWorkflowStructureReceipts` already uses explicit P0001 for retained-evidence downgrade refusal.

`AppDbContextOptionsConfigurator` in `Persistence/SwitchableAppDbContextFactory.cs` configures `UseNpgsql` and the migrations assembly, without `EnableRetryOnFailure` or a custom EF execution strategy. The default [Npgsql execution strategy](https://raw.githubusercontent.com/npgsql/efcore.pg/v10.0.1/src/EFCore.PG/Storage/Internal/NpgsqlExecutionStrategy.cs) does not retry; it wraps errors classified transient. [Npgsql 10.0.2](https://raw.githubusercontent.com/npgsql/npgsql/v10.0.2/src/Npgsql/PostgresException.cs) classifies ObjectNotInPrerequisiteState/55000 transient, but does not classify RaiseException/P0001 that way. [PostgreSQL's RAISE contract](https://www.postgresql.org/docs/18/plpgsql-errors-and-messages.html) permits this explicit code. This is permanent operator-action refusal, so the deliberate P0001 choice avoids a misleading wrapper today and a wrong future retry classification. Existing real migration refusal assertions must require exact `PostgresException.SqlState == PostgresErrorCodes.RaiseException`, `IsTransient == false`, unchanged migration history/schema/data and no Down DDL. Do not merely unwrap and bless 55000.

## Concrete second-pool gap

Before this correction, `DatasetActivationCoordinator.EnsureReadyAsync`, `RequireReadyAsync` and `ApplyAsync` iterated only compiled registrations. A future Workbench pool could exist while a Projects-only C2 binary still declared itself ready. Its reactivation loop closed only Projects, leaving Workbench's old Open epoch behind. This must be fenced in the first C2 binary before any later pool is installed. Checking duplicate registrations only in memory does not detect it.

Selected minimum: exact installed pool/version set for the active namespace, plus refusal of unknown retained historical pools or versions. No generic plugin catalogue, persisted registry table, lifecycle-version bump or Projects receipt-version change. C3's stopped-host migration explicitly installs its pool; ordinary startup never discovers a pool and silently adopts it.

### Authored source/API changes

1. `FiniteOperationEpochStore`: two narrow enlisted control-plane checks. `RequireInstalledPoolSetEnlistedAsync(activeBinding, inspectedNamespace, registrations, ct)` holds/verifies the exact active lifecycle binding and compares the inspected namespace's state PoolId/version set to the immutable compiled set. Materialize at most expected-count + 1 rows; an additional/missing/unknown ID or version fails with explicit protocol failure. The same private per-pool readiness query checks an Open current head and the complete unretired prefix in the inspected namespace. Fresh Reactivate applies it to every previous active pool before any closure or initialization; it cannot bypass missing retained history or an already Closed current head. The different inspected namespace is only for this previous-active-namespace audit, never permission to read receipts there or scan arbitrary inactive prefixes. One coherent EXISTS query rejects any retained state or epoch in any namespace belonging to an unknown compiled pool, any known pool with unsupported state version, an epoch lacking its matching state, or any Open epoch outside the inspected namespace. These are bounded-result control-plane queries; they can inspect retained metadata and do not claim constant database work. Absence of a known pool from an older namespace is legitimate (installed later or fully purged) and must not be filled in. Unknown historical evidence fails readiness and is left intact for a matching binary/reviewed migration; never auto-purge or ignore it.
2. `RequireUnissuedNamespaceEnlistedAsync(binding, registrations, previousNamespace, ct)` verifies the guarded active namespace has zero state and epoch rows before first initialization and repeats global compatibility. Bootstrap allows Open rows only in its proposed target, then refuses any target metadata; it cannot silently bootstrap over retained old Open or unknown history after a lost lifecycle marker. Staged Reactivate temporarily permits Open rows only in the inspected previous namespace. After closure/initialization the final installed-set check permits only the target namespace. The existing idempotent per-pool initialization remains unchanged for its explicitly valid callers.
3. `DatasetLifecycleStore.StageActivationAsync` returns a small typed `DatasetActivationStageResult` (`Staged`, `AlreadyApplied`). It determines this under its existing activation advisory key and lifecycle `FOR UPDATE`, at the same exact-binding early-return branch; it performs no extra pre-lock query. Existing callers may ignore the return. This avoids confusing a genuinely new SQL transition with resuming an already committed Prepared plan whose metadata was subsequently lost. It is not a commit acknowledgement.
4. `DatasetActivationCoordinator`: share its duplicate readiness loops through `RequireReadyAsync`. Matching Active EnsureReady, Attach (existing or new), active Resume and superseded-bootstrap Attach acquire lifecycle SHARE, perform exact current installed-set/global compatibility checks, then each existing per-pool structural readiness check, in the same short RC owner transaction. All must finish before MarkActive or business bootstrap. For `ApplyAsync`, retain StageActivation's existing advisory→lifecycle order. `AlreadyApplied` requires the exact new active pool set and each current pool structurally ready; do not rerun previous-namespace closure or initialize missing metadata. `Staged` Bootstrap requires unissued target namespace and initializes all compiled pools. `Staged` Reactivate, while holding the same exclusive lifecycle row, first checks the complete previous namespace pool set/global compatibility and unissued target, then closes every old pool and initializes every target pool. Repeat exact target set/readiness before commit. Any failure rolls the SQL marker/metadata changes back; the exact Prepared file remains for explicit recovery.

Do not acquire lifecycle SHARE before StageActivation and then upgrade it: that would invert its advisory→lifecycle order and create competing upgrade waits. The checked previous namespace may be Closed only on a previously applied plan; that path now validates the committed target and does not require historical rows that may legitimately have been purged. Fresh Reactivate still validates/fully closes the old active installation. No file lock enters a foreground SQL transaction.

### Race and compatibility boundary

Normal readiness holds lifecycle SHARE until every check completes; supported installation/activation takes conflicting lifecycle exclusion first. A second-pool migration must acquire lifecycle utility EXCLUSIVE before metadata DDL/installation and run with hosts stopped, preserving the existing transfer lock order. Reactivate's exclusive guard remains held from StageActivation through previous-set audit, closure, initialization and commit. Concurrent bounded metadata purge can only remove eligible inactive rows; an unknown historical-row observation may conservatively refuse, but cannot erase or grant authority. Missing/unexpected active metadata and unsupported concurrent schema writes remain fail-closed.

The return from StageActivation is necessary for crash recovery: `AlreadyApplied` + missing target pool must refuse, not mint a fresh epoch. `Staged` + unknown target metadata must refuse, not adopt a namespace collision. Matching Active readiness must not create a Prepared file on set mismatch. A new Attach may have already written its exact Prepared plan; failure leaves that evidence rather than marking it Active.
