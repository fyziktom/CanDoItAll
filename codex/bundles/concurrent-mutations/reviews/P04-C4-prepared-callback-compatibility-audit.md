# C4 prepared-write callback compatibility audit

Read-only review against the conditional narrow protocol E73E4BEB… and current managed first-party workspace/catalog/run callers. No production or test source changed; no build, scan, database or runtime proof. The small coarse probe remains the prerequisite to selecting a production strategy. No additional test matrix is proposed.

## Finding and limits

No first-party callback inspected performs provider dispatch, SQL mutation, independent file publication, event publication or transient-context registration inside the supplied synchronous mutation lambda. Its observable work is validation, immutable-record/list construction, clock/identity selection and assignment to invocation-local variables. Nested provider profile normalization and project-access configuration transforms are local computations. The current catalog mutation policy does perform awaited SQL **reads**, and capability verification captures a live in-memory provider snapshot; neither can be treated as immutable file-only validation across a new lock wait.

No inspected prepared-result local escapes as a successful return after a throwing store await. Preserve that ordinary exception propagation. A broad rewrite to remove every local or introduce a generic command/result framework is unnecessary. This conclusion covers the current concrete first-party callers, not arbitrary future implementations of public Func-based interfaces. A callback with an independently visible mutation cannot gain rollback semantics merely by being synchronous; it would need a separately reviewed owner boundary before the narrow protocol supports it.

## Definite prepublication conflict is not global no-effect evidence

1. `AgentToolAdmissionJournal.Effects.cs:271–288` currently distinguishes its own `EffectCheckpointConflictException` from generic checkpoint failures. The new store-owned prepared conflict needs an explicit branch to the existing CheckpointConflict disposition. Do not classify a proved unstarted **new** checkpoint as generic unknown publication; retain all previously confirmed commitment knowledge and current disclosure checks. Recovery already completed before the refusal is separate evidence.

2. `MafToolRunContext.cs:417–453` invokes the actual tool, captures its result/owner commitment, then calls `CompleteInvocationAsync`. Its current catch attempts `PreserveUncertainInvocationAsync` and rethrows the original if that also fails. A new prepared conflict at either journal write cannot establish that the tool did not commit. Preserve the original operation/result/owner receipt knowledge and no-retry behavior. The analogous D1 `RecordSavedEffectOutcomeAsync` is a late outcome writer; never reinterpret its conflict as permission for fresh effect dispatch. This is a required classification checkpoint before the narrow owner can be activated, not a claim of a present extra D1 effect invocation.

3. Catalog `.ProvidersAndCapabilities.cs:45–141` runs health diagnostics or remote model maintenance before updating its provider profile. `ProviderRuntimeAdministrationService.cs:122–159` has the same split with its existing typed provider mutation wrappers. Repeating the complete request after a file conflict can repeat remote work. Retain the observed result/remote-operation status; reconcile only the local projection, without rerunning diagnostics or model maintenance automatically. The callback itself is pure. This boundary already permits post-effect persistence failures; a new conflict must not be advertised as a global pre-effect rejection.

4. `WorkflowBackedAgentExecutionCheckpointBridge.cs:64–106` creates the actual MAF checkpoint and shadow file before saving its reference into execution state. A later prepared conflict can leave that real checkpoint without the run reference. Preserve its identity and classify/reconcile publication; do not create a second checkpoint or claim that no filesystem effect happened. `MarkCheckpointResumedAsync` only publishes its record change. The bridge is an ordinary Agent approval dependency despite its Workflow-backed storage name; this review does not add Workflow execution to C4.

5. `DatabaseProviderProfileRegistry.cs:274–323,419–452` commits canonical SQL before file projection and already wraps projection failure with `ProviderCatalogProjectionException`. `SharedProviderCatalogProjectionCommitObserver.cs:24–68` similarly preserves saved-provider knowledge. Retain those wrappers when the inner failure is the new conflict. `ReconcileAsync:355–370` can publish runtime observer state before its file update; a file conflict must not imply all reconciliation effects rolled back. No new broad committed-exception family is needed.

## Current validation that must survive the new wait

`CapabilityVerificationPublication.cs:151–158` compares the diagnostic's original inputs and obtains `providers.CaptureProvider(...)` **inside** the callback. The production `ProviderRuntimeProfileSnapshotService.cs:193–199` reads its current ready in-memory projection, independently of the file catalog. Exact file-witness comparison after the new key wait cannot alone prove that external provider projection stayed current. Preserve a final owner-controlled equality check of the same original provider fingerprint at the existing publication boundary; refuse if it changed, without rerunning diagnostics or the mutation callback. A catalog-only key is not a lock on canonical provider SQL/runtime projection. The guarantee remains an explicit current observation unless that independent owner supplies a held fence.

The existing `AgentProjectAccessCatalogPolicy.ApplyAsync` reads current Project lifetime/reservation facts and may add bindings/UpdatedAt during normalization. Preparation must include its actual final target/key set; a final check may confirm that exact prepared result or refuse. It cannot silently add another Agent/key or run the arbitrary caller callback again. Preserve the existing current-Project semantics and no catalog→Project recursive publication path.

## Smallest compatibility scope if parent selects narrow mode

Keep the first-party callbacks and their awaited return order. Add only the one reviewed owner-specific prepared conflict at the storage boundary, then map it at the concrete receipt-checkpoint and user-visible conflict boundaries above. Preserve existing typed canonical-commit carriers and distinguish post-provider/tool/checkpoint publication failure from ordinary unstarted save. Add an explicit final provider-input equality check where the callback currently reads non-file state. Do not add callback retries, a global cache, an outbox framework or a new generic coordinator.

Validation should extend the already required callback-once/failed-CAS and existing owner/approval/provider projection arrangements: no prepared receipt/claim returns on refusal, no external effect is repeated, existing commitment survives a late conflict, and final provider/catalog policy change refuses before new file publication. These are required assertions in the existing planned scope, not newly authored or source-counted test rows.
