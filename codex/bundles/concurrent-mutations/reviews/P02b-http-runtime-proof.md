### Outcome truth and retry fences

- `ProjectDefinitionWriter.ExecuteProtectedAsync` and `RecoverOutcomeAsync` preserve exact known acceptance, return current typed context/access refusals, and return Unconfirmed when reconciliation infrastructure is unavailable. A fresh receipt read may recover an earlier acceptance after an admission/precommit failure. An exception alone is not evidence that an earlier duplicate did not commit. The owner does not automatically retry a mutation transaction.
- The tool adapter records accepted effect evidence before returning the historical acknowledgement. A mutation-lease release failure after owner acceptance logs the cleanup failure and keeps that accepted result. Creation session-access bookkeeping errors likewise do not change acceptance into a rejected effect.
- `RequireOpen` admits a potential effect only for the original operation's explicit Open observation. Draining, ClosedAbsent, expiry, unavailable detail, dataset/caller change and access denial cannot silently allocate another operation. Unconfirmed outcomes carry unknown effect state and prohibit corrected-input retry; a deliberate corrected proposal is only appropriate after a known rejection, while preserving any uncertainty from an earlier dispatch.
- The generic reconciliation provider maps owner absence to NotObserved without granting redispatch. That generic observation lacks the owner-specific open/closed distinction and must not become a future retry signal. R1/R2 must retain the original operation and use the exact owner evidence rather than interpreting a missing receipt as rollback.
