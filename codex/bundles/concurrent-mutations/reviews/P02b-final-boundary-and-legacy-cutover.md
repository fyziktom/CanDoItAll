# P02b boundary review and remaining producer cutover

Status: independent source review. The owner runs serialized builds, test discovery, execution and static enforcement. This record does not claim those checks passed for the source described here.

## Result-truth repair

`ProjectDefinitionWriter.ExecuteProtectedAsync` previously returned a typed epoch-admission rejection without checking whether a concurrent original invocation had accepted the same operation. A duplicate can observe a missing receipt, pause, let the original commit, and then encounter the now-closed epoch before reaching the operation lock. The rejected attempt is not evidence that the original operation was never accepted.

The writer now uses one bounded `RecoverOutcomeAsync<T>` helper after owner resources have unwound. It returns the exact authorized receipt when available; preserves a current typed namespace/caller/access/result-support refusal; returns `Unconfirmed` when the recovery observation fails; and returns no outcome only after a completed `Open`/`NotObserved` observation. The generic exception path uses the same distinction. An unexpected failure before an attempt can be prepared has no absence evidence and also preserves the original address as unconfirmed. A known local commit or authorized accepted replay still wins over subsequent completion failures.

`ProjectDefinitionOperationTests.AdmissionRecovery.cs` adds six source cases:

- `Duplicate_that_missed_acceptance_before_epoch_closure_recovers_exact_receipt_under_current_read_permission`: allowed read, revoked read and unavailable lookup. The fixture holds the duplicate's original SQL observation, commits the original, explicitly closes only the owned epoch state without modifying its issued replay promise, and releases the duplicate. It checks fresh recovery, exact receipt bytes or the correct refusal/uncertainty, and one durable effect/receipt. This selects the interleaving deterministically; it is not a real-time maintenance performance test.
- `Initial_receipt_lookup_failure_cannot_reject_an_already_accepted_operation_without_current_recovery_evidence`: an accepted original followed by an initial lookup outage, with successful recovery, current read revocation or a second lookup outage. The operation identity and stored accepted result stay unchanged.

## Boundaries reviewed without another blocking finding

- `ProjectDefinitionOperationProtocol`, `ProjectDefinitionReceiptReader` and `ProjectDefinitionOperationStore`: semantic digest comparison remains separate from current receipt disclosure. Historical detail comes from the exact bounded result, not a current definition read. Current target lifetime/availability and current read permission are checked before disclosure. The receipt's replay deadline must equal the original epoch promise; it is not widened by current configuration.
- `ProjectOperationEpochService`: an admitted transaction holds its epoch guard; closure and retained watermark distinguish draining/open absence from final retained absence. Purge bounds rows/bytes and respects both issued and closure-derived retention deadlines. This source review does not establish capacity under production load.
- `ProjectDefinitionHttpAccess`, `ProjectDefinitionApi`, `ProjectDefinitionHttpBody` and `ProjectDefinitionHttpResponses`: verified issuer/subject determines authenticated caller binding; disabled authorization explicitly selects OpenApi. Missing credentials in enabled mode do not select OpenApi. Write dispatch requires current read and write; lookup rechecks current read. The body is bounded under supported version-one maxima before model construction, while stricter current deployment limits apply to potential new effects after receipt lookup.
- `ProjectPendingOperationSession`, `ProjectEditorOperationSession` and `ProjectsPage.Pending`: browser dispatch is claimed before the owner call; a known acceptance is retained before browser persistence/reconciliation; restored accepted data requires current owner lookup before applying it; reconciliation is one-shot; retired sessions cannot initiate another owner call. Starter work remains a separate effect, and its completion cannot be inferred from the definition receipt.

These are source conclusions scoped to the reviewed paths, not proof that all callers use them. Typed refusal is not a global proof of absence: callers must continue to distinguish current disclosure/admission refusal from `ClosedAbsent` and from an unambiguous first-attempt rejection.

## Ordered closure cards

1. **Ordinary transport closure.** Migrate external consumers to the protected endpoint contracts; explicitly close the old Projects POST mutation. Assert that old bodies cannot create or update through a hidden server-generated operation. Keep replay/current-read authorization regressions.
2. **Structure transport and runtime closure.** Add the operation envelope to structure HTTP without weakening its authority/lease rules. At actual runtime launch owners, retain original prepared source and admitted journal identity for the three definition tools; explicitly refuse unsupported nonjournal contexts. Assert same-ID replacement, expired-source replay, current read revocation and no refreshed source/epoch during restore.
3. **Workbench native creation closure.** Use the same pending/session contracts already employed by the Projects page, with the reserved creation intent frozen once. Assert accepted-before-local-error, response loss/restart, later typing, and no automatic repetition of starter effects.
4. **Coordinator closure.** Make CRM conversion and subproject transfer retain their stage's original definition operation/reservation in their existing orchestration owner. Add meaningful response-loss and restart cases at the stage boundary; retain assignment/move proof separately. Do not build a generic coordinator framework or force cross-module effects into the Projects transaction.
5. **Remove bypasses.** After production callers have moved, remove/restrict operation-free writer/facade mutation APIs, update isolated fixture creation explicitly, and add a scoped caller guard so new production code cannot silently use legacy paths. Repeat the inventory across the full source tree and update endpoint/tool docs.

P02a original revision/lifetime protection is present in the inventoried ordinary update paths. The remaining issue is durable result recovery and original dataset/operation fencing, including restore of the same project IDs/lifetimes/revisions under a fresh dataset activation. P02 closure cannot claim all definition producers are protected until the cards above have evidence.

## Follow-up actual MAF fixture correction

The parent's `p02bc-boundary-fixed.trx` records 16 executed cases: 15 passed, one failed, no skips. The remaining failure was `Actual_MAF_definition_update_restores_completed_accepted_result_without_reexecuting_after_read_revocation` at its final restart. Initial setup used `SaveMetadataActorAsync(structureWrite: true, taskWrite: false)`, but read restoration assigned `SaveActorAsync(canRead: true)`, which explicitly clears write flags. The resumed runtime therefore composed a different toolset. `MafAgentExecutionAdapter` computes the actual contract fingerprint, and `MafRuntimeStateCompatibilityPolicy.EvaluateSchemaV2` correctly refused this mismatch before provider dispatch. This was not evidence that current read policy failed or that the saved effect was replayed.

The test now explicitly asserts that read-restored/write-revoked policy still receives `tool-admission.runtime-denied`, makes zero provider calls, and changes neither the saved proposal nor the later owner definition. It then restores the original exact metadata policy through `SaveMetadataActorAsync` and retains the original assertions: one provider continuation sees the exact historical accepted result, no later current content is substituted, and neither proposal nor owner is mutated. Current read revocation remains independently tested before these steps. Direct governed receipt recovery under write revocation remains covered by its separate existing test; that permission does not imply compatibility of an entire provider-session checkpoint.

Only this existing test and this proof note changed. Test count remains one Fact; no production fingerprint or authorization rule was modified. The follow-up edit has not been built or executed by this reviewer.
