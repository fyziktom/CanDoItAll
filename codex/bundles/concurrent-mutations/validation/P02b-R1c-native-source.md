## Behavior and boundaries

The native chat host retains an immutable, sanitized continuation observation before its subsequent workspace read. A checkpoint failure can carry observed commitment without a confirmed Waiting transition. Current access denial or unavailability contributes no new receipt knowledge and does not erase the previously known lower bound. The UI says “at least” because retained observations across attempts are not an authoritative current total or a complete receipt ledger. It does not cache raw receipt payloads.

A confirmed checkpoint followed by run-lease cleanup failure is separate: `AgentEffectReconciliationCleanupException` preserves its accepted continuation and sets a sticky release-unconfirmed flag. The UI displays that uncertainty separately and blocks another slice. SnapshotRead cannot clear the flag because persisted-state observation does not prove resource release. No owner-issued release-confirmation command exists in this slice; operational inspection/restart recovery remains an activation gate. The first Fact also covers cleanup failure followed by explicit readback, which must leave recovery disabled. A combined incomplete checkpoint and lease-close failure retains the typed incomplete continuation and the same sticky release flag; both native exception paths preserve it. The existing Fact additionally proves that this combined failure neither publishes Waiting nor allows a second recovery call. Its internal exception factory is accessible through the existing Core Components friend assembly; no new public fault seam was introduced.

`AgentChatSession` retains the authorized current-read continuation alongside its accepted run. `SnapshotRead` is rendered explicitly as a read, with no receipt lookup or continuation claim. In particular, `Persistence.Confirmed` on a current read is not evidence that this read published a Waiting checkpoint. The host only labels an actual Waiting run as awaiting continuation. Original draft text, attachment references and composer identity survive receipt recovery; post-dispatch typing and replaced profile/target lifetimes remain fenced.

Successive receipt slices require an explicit “Check next receipt slice” click. They keep the original run, session and trusted stream/profile identity. Busy completion is retired only after its cleanup, before rendering the next enabled action. `AwaitingContinuation` is appended to the existing floating-chat state enum and mapped from the typed activity phase; it is neither active provider execution nor approval. The host preserves the existing no-new-message guard while effects remain unresolved.

Reopened views can display the authorized snapshot, but cannot start recovery without the original captured stream. The current orchestrator has no trusted read-to-recovery admission capture seam. The UI explains this limitation; it does not manufacture a stream or use current readback as effect authority. This remains a producer-activation/restart gate, not completed restart recovery.

Receipt-only results have no assistant message or metric. Native voice requires actual assistant output. Scenario notifications use a small pure presentation mapping: continuation remains a warning, and a completed run without available response evidence is informational. `ScenarioHarnessSnapshot` no longer labels every Waiting run as approval. Scenario notification assertions exercise the exact mapping consumed by the host, not a running scenario/provider.

## Activity-finalization amendment

Its closed read-denied/read-unavailable reason can update presentation without disclosing inner errors. A separate sticky activity-finalization flag blocks new messages and further receipt slices. The file-lease flag is preserved independently and is never inferred from activity publication/disposal failure. Ordinary publication exceptions without an effect outcome keep their existing path. Neither flag can be cleared by SnapshotRead; this amendment adds no cleanup command, restart admission or dispatch authority.
