# H2 — HTTP definition current-write cutover

Status: implementation design reviewed against the managed checkout on 2026-10-16. H2 production and 18 deterministic test Facts are now authored; the sibling-owned 12 actual HTTP/PostgreSQL arrangements remain in progress. See the [source checkpoint](../validation/P02b-H2-current-write-source.md) for exact files, counts and pending proof. No H2 discovery, execution or benchmark is claimed. The parent reported the H1 prerequisite lane passing before releasing implementation. This card refines [the observation decision](P02b-http-current-write-observation.md), including the request-local reuse and final commit placement accepted by the parent review.

## Exact effect boundary

HTTP retains Read Committed and no source lease. Governed invocations retain their actual source lease, Serializable isolation and existing lock order. Neither account generation nor a successful file observation excludes a subsequent independent revocation through SQL commit.

Protected owner sequence:

1. Validate/capture the original HTTP caller before opening a Projects transaction. Perform the existing independent receipt lookup first; it uses current read disclosure.
2. On a receipt miss, acquire the existing source (if applicable), transaction, lifecycle/epoch/operation and sorted project guards through `ProjectSourceMutationScope.BeginDefinitionAsync`. A locked receipt observation still exits and releases resources before fresh authorized disclosure.
3. After that replay branch and all initial owner/source/lifetime waits, require CurrentWrite before changing any entity.
4. Apply root/children, flush the required search projection and exact receipt in the same transaction.
5. Inside the definition-specific commit path, finish the **existing final source and lifetime checks first**. Then require CurrentWrite, check cancellation, set `attempt.CommitAttempted = true`, and immediately call the actual transaction commit. Acquire no new source lease after project guards.
6. Preserve `scope.IsCommitted` before source disposal and `attempt.Committed`/accepted payload before later cleanup. No observation after commit may demote acceptance. Existing failure recovery releases owner resources before a fresh receipt read; no nested connection is introduced.

The existing `ProjectMutationAuthority.cs:CommitAsync` awaits source validation and `ProjectWriteAdmissionService.RequireManyForMutationAsync`; the latter issues an enlisted `FOR KEY SHARE` lifetime read. Therefore adding the second check only in `ProjectDefinitionWriter` before calling `CommitAsync` is insufficient. Add `CommitDefinitionAsync(ProjectDefinitionOperationAttempt attempt, CancellationToken)` and share a private commit core with unchanged legacy `CommitAsync`. The core receives the typed optional attempt, not a generic mutation callback. It owns the second observation and commit-attempt flag; remove the writer's earlier flag assignment. The first observation remains in the writer after `ReplayObserved` handling.

Retain a trusted typed CurrentWrite refusal on the attempt before throwing its mapped protocol rejection. `ProjectDefinitionWriter.DisposeResourcesAsync` currently aggregates a primary failure with cleanup failures; that aggregate reaches the generic recovery catch, whose failed independent receipt read can return Unconfirmed. A known precommit CurrentWrite refusal must survive this path: after the existing known-accepted/replayed precedence, an attempt with that retained refusal and `CommitAttempted == false` returns the same sanitized Rejected result even if rollback/context disposal also failed. Report cleanup separately without replacing the refusal or exposing file details. Do not weaken `RecoverOutcomeAsync` for other failures or infer rollback for an earlier dispatch at this address. The client's earlier Unconfirmed state remains sticky; this rejection describes only the current attempt. An exception before the observer produces a trusted decision is not such evidence.

## Remove the redundant pre-admission account scan

Current source does a complete ordinary-account read in `ApiManagedTokenValidation.ValidateAsync` through `ApiSessionService.ResolveIdentityAsync`, then another in `WebCurrentPrincipalResolver.ResolveAsync`. H1 bounds both but does not remove this cost. Use the following narrow reuse boundary for protected definition **write capture**, not a general authorization cache.

Ordinary sessions call `IApiUserStore.ReadSnapshotAsync` once and project the selected validated identity, normalized username and generation. Existing `ResolveIdentityAsync` and this method share the same identity-validation core: active record, user-auth mode, account existence/enabled/revision, reserved administrator name, supported password-hash shape and exact grants. | Web new `Api/ApiAuthenticationObservation.cs` | Internal immutable request feature, minted only after successful real JWT validation. Copy verified issuer/subject/expiry/managed binding and relevant scope facts, freeze token metadata/scopes and the session snapshot. Do not retain a mutable `ClaimsPrincipal` as the evidence, raw JWT/password/account collection, or externally writable list. No serialization or DI singleton cache. |
| Web `Api/ApiManagedTokenValidation.cs` | Keep cryptographic validation, duplicate-claim rejection and `ApiTokenPayloadValidation.Matches` semantics. The feature's identity and scopes are observations from the real middleware, not proofs a claim can manufacture. Construction stays internal; endpoint tests use the real handler. A direct nonmiddleware caller keeps the existing explicitly fresh resolver/validation path, or is refused by the new capture API. There is no implicit fallback to a cached decision or to full reads inside an owner transaction.

Publish from `TokenValidatedContext.Principal` and the already validated token facts: `HttpContext.User` need not yet contain the authenticated result inside this event. The unmanaged branch must return immediately after `context.Fail` for forbidden session claims; only its successful branch publishes the observation. Capture and later compare the relevant claim values using the same inbound-claim mapping and pure scope interpretation. Refuse ambiguous/missing/mismatched identity or managed-version facts rather than using a new permissive `FindFirst` projection; preserve the legitimate repeated scope claims and parallel `scope`/`scopes` representations emitted by current tokens. Keep the resolver's existing bounded subject/issuer validation. Freeze both selected identity scopes and token scopes into detached read-only collections; neither an `ApiSessionIdentity` positional record nor an `IReadOnlyList` alone prevents collection aliasing. No `ClaimsPrincipal`, `JsonElement` tied to the disposed payload document, or complete account snapshot survives in the feature.

Keep the existing `ResolveIdentityAsync` entrypoint's fresh `ReadAsync` behavior and share its pure identity-validation core with the new prepared `ReadSnapshotAsync` entrypoint. Do not forward every identity read to the new snapshot method: non-Web callers have no H2 readiness contract. The Web middleware selects the prepared snapshot path explicitly. Existing `IApiUserStore`/`IApiTokenRegistry` H1 interfaces already expose all required operations; H2 adds no further store-interface members.

For an ordinary new session write with a receipt miss, this removes one of the two complete account reads: **one full read before owner admission, zero full account reads under project guards**. Replay or later receipt disclosure still performs a fresh read and may legitimately add another scan. Machine requests have no account read. This is a source-level allocation reduction, not measured capacity proof; one 64 MiB document at 32 requests can still be unacceptable.

Existing policy registration uses `HasApiOrSpecificScope` for the verified claims, while `WebCurrentPrincipalResolver.RequireScopeAsync` additionally requires each exact scope in a managed credential. Preserve both rules for ReadProjects and WriteProjects; an `api` claim cannot bypass a managed record's exact grants. Reuse the existing pure scope interpretation rather than creating another parser or invoking an arbitrary new authorization policy under the owner lock. Administrator-session grants remain Session/ManageAccess and do not become Projects grants. Configuration is currently `IOptions`, not a promised hot-reload API; deterministic tests may replace options explicitly.

## CurrentWrite contracts and observations

In `Modules.Projects/ProjectDefinitionInvocation.cs`, add:

- `IProjectDefinitionCurrentWriteAccess.ObserveAsync(CancellationToken) -> ValueTask<ProjectDefinitionWriteAccessDecision>`.
- `ProjectDefinitionWriteAccessDecision`: `Denied = 0`, `Allowed`, `CallerChanged`, `AuthorityChanged`, `Unavailable`. Unknown enum values fail closed.
- Final optional constructor argument/property `CurrentWrite`; AuthenticatedSubject/OpenApi invocations require it. LocalWorkspace remains explicitly trusted; GovernedExecution still requires the existing real authorization/effect binding. The observer is trusted runtime state, never transport or digest content.

Use a small Projects-owned guard to map decisions to existing protocol rejection handling. Add `DefinitionWriteDenied`, `DefinitionAuthorityChanged`, `DefinitionAuthorityUnavailable` constants in `ProjectErrorCodes.cs`; use existing `DefinitionCallerChanged`. Do not add a Web/Workspace/ControlPlane reference to Projects.

Web `ProjectDefinitionHttpAccess` should replace its `writing` flag with explicit `ResolveWriteAsync(ct) -> ProjectDefinitionInvocation` and `ResolveReadAsync(ct) -> ProjectDefinitionReceiptInvocation`. Existing GET context/coherent read/lookup use the read invocation (the receipt reader already supports it), so requiring CurrentWrite on an actual write invocation does not accidentally require write authority to read. All three protected POST/PUT handlers use the write method. `ReceiptAccess` continues resolving current read permission on each disclosure.

Implement new internal `ProjectDefinitionCurrentWriteAccess` in Web, carrying the immutable capture and prepared stores/configuration/clock. Each observation:

1. Reject mode transition, issuer/subject/principal substitution, exact JWT expiry or relevant session configuration drift. OpenApi is allowed only while still open; it cannot inherit authenticated authority or vice versa.
2. For managed credentials, call only `ObserveCurrentAsync(originalTokenId)`. Absent/revoked/expired or lost grants is Denied; subject/kind/user binding change is CallerChanged. Require the original payload-bound metadata and session revision/scopes to remain compatible with the frozen verified facts. Reuse/extract the existing payload matching projection; do not parse/revalidate a raw JWT inside the lock or silently pair a changed token revision with an old user snapshot.
3. For an ordinary session, call only `ObserveAuthorityAsync(originalGeneration)`. Current permits the captured account validation under the cooperating publisher contract; Changed is a conservative conflict even if a different account changed. Unavailable remains distinct. Recheck relevant pure current config and exact time after awaited reads and before Allowed.

Use a linked, disposed **one-second cooperative budget per observation**. Budget cancellation becomes sanitized Unavailable only after the awaited operation has completed/canceled; caller cancellation propagates. Never use a detached `WhenAny` timeout or authorize from a late result. No provisioning, migration, mutation gate, password hashing or full-snapshot fallback under project guards. Synchronous filesystem open/path calls have no claimed hard wall-time limit; PostgreSQL transaction timeout separately bounds database lock lifetime.

Check caller cancellation first and the observation budget after each awaited read and again before Allowed, including when a collaborator ignored cancellation and returned a nominal Current/Found result. If caller and budget cancellation coincide, caller cancellation wins. Classify an `OperationCanceledException` as budget expiry only when that budget is actually canceled; an unrelated cancellation is not fabricated timeout evidence. Use one captured observation clock consistently for exact expiry/config rechecks; tests must explicitly arrange the relevant injected clocks rather than relying on JWT middleware's separate 30-second clock skew. The two observations have separate budgets, not one shared timeout spanning owner work.

## Startup, errors and exact knowledge

Add one Web-owned `ApiAuthorityReadiness.PrepareAsync` helper using existing stores/options. Before Web `MarkReady`/listen, when API authorization is enabled, call `PrepareCurrentReadAsync`; when ordinary session authentication is enabled, also call `EnsureAuthorityFormatAsync`. Reuse this exact helper in `ApiTestHost` before StartAsync. Keep startup outside SQL transactions. Failure stops readiness, does not overwrite malformed state. No new hosted framework or lazy read repair. H1's stopped-old-writer/schema-v2 requirement remains operationally necessary.

| Stage / decision | HTTP contract |
| --- | --- |
| Invalid JWT, absent/revoked/expired managed credential at actual middleware | Existing 401 behavior. Existing pre-auth registry/session I/O also becomes 401; H2 does **not** claim this outage distinction is solved. No broad auth challenge redesign. |
| Typed post-auth capture unavailable before command parsing | 503 `status: rejected`, `operation: null`, sanitized authority-unavailable error. No definition effect was attempted by this request. |
| Post-wait or final CurrentWrite denied | 403 typed Rejected, original operation, rollback of this attempt. |
| Caller changed / authority generation changed | 409 typed Rejected with distinct caller/authority code. Do not describe a whole-file generation change as proof this user's grant was revoked. |
| Current token/header unavailable or observation budget expired before commit | 503 typed Rejected, original operation; no effect committed by this attempt. Do not expose path, exception, account, token, hash, claim or file contents. |
| Actual commit acknowledgement uncertain and receipt cannot resolve it | Existing 503 `status: unconfirmed`. No new identity, automatic retry or false rollback claim. |
| Commit known accepted, cleanup or later presentation fails | Existing Accepted/retained receipt semantics; never reclassify using a later write observation. |

A Rejected result describes this attempt only. It cannot clear a client's earlier Unconfirmed attempt under the same operation address. Exact authorized receipt or retained ClosedAbsent evidence remains necessary. Fresh re-admission after AuthorityChanged may reuse the **entire original** operation, command and business expectation; do not refresh only identity/epoch/revision.

`ProjectDefinitionApi.RejectionStatus`/`GuardAsync` own the new mapping. `DescribeWrite` and `ProjectDefinitionOperationOpenApiSchemas` must advertise both 503 shapes with an explicit discriminated union (`status` constants); two competing `.Produces` calls are insufficient. Existing generic access-denied 403 shape remains accounted for. Refresh actual emitted-schema assertions before any SPA generation. No receipt schema, semantic digest, epoch contract or SQL migration changes.

## Bounded implementation ownership

1. **Workspace/Web authentication owner:** shared session validation/runtime snapshot, immutable request feature, actual middleware capture, protected capture resolver and observer, startup/test-host preparation. Preserve all existing session/policy behavior; no global resolver cache.
2. **Projects owner:** invocation contract/guard/error constants, first writer observation and narrow final commit core. Update all AuthenticatedSubject/OpenApi constructor consumers explicitly; do not add an unconditional production Allow observer. Existing local/governed callers do not acquire this HTTP mechanism.
3. **HTTP/schema owner:** explicit read/write access methods, endpoint mappings, sanitized 503 union and emitted-schema assertions. Reuse current source-generated/serializer conventions.
4. **Validation owner:** new focused files below, existing source-backed filters, then serialized build/discovery/execution, full portability gate and only afterward isolated capacity proof. No UI or SPA writer activation is included.

The constructor inventory in current main has one production HTTP creation owner, `ProjectDefinitionHttpAccess`; native `ProjectNativeDefinitionOperations` stays LocalWorkspace and Workbench's governed factories keep their real source/effect arguments. Read endpoints switch to the already available receipt-only invocation type instead of constructing an authenticated write invocation without an observer. Existing component-only `ControlledUserStore`/`RecordingTokenRegistry` doubles intentionally reject H1 prepared reads and do not run Web readiness; do not give them permissive implementations for this slice. `ApiAdministrationOutcomeHttpTests.ReadBackFailureStore` already delegates preparation/snapshot/observation to the real store, so startup preparation need not consume its intentionally failing ordinary read-back. New counting/pending-read doubles must implement the actual H1 interfaces and be explicit about every operation used.

## Capacity proof and remaining gates

Run machine and ordinary-session paths across **1 / 1,000 / 10,000 accounts × 1 / 8 / 32 writers × hot / disjoint targets = 36 workload cells**, preferably one source-counted LongRunning benchmark Fact producing 36 samples per repetition, not a claim of 36 discovered tests. Use the same representative account shape, actual valid hash/grants and recorded serialized byte count in baseline and candidate. Retain the old two-scan baseline honestly; compare the new single pre-admission scan, not only the two cheap final observations. Machine population is a control and should produce zero account reads.

Capture complete HTTP p50/p95/p99 and offered/completed throughput; accepted/rejected/unconfirmed/canceled counts and exact codes; allocated bytes/GC and peak process memory; total full-snapshot/token/header reads and bytes; observation duration; project guard hold/wait and SQL transaction duration. Hot-target conflicts are outcomes, not successful throughput. Disjoint operations retain their own original expectations; do not hide contention by refreshing them. Include unrelated-authority edit conflict rate. Separate warmed repeat measurements from process/reopened-handle startup; reopening is not proof of cold OS cache. Never flush shared caches or use ordinary port 5032.

The H1 10,000-user source fixture with 64-character usernames, 128-character display names, 512-character placeholder hashes and two short scopes is a **count/wide-fields fixture**, not a valid representative login workload and not the canonical maximum serialized document. Raw Infrastructure fields/scopes have no per-field finite maximum; the actual aggregate bound is 64 MiB. Separately construct canonical escaped/large-field inputs at the byte ceiling and one byte beyond using the real serializer, including 10,000 records where practical. Verify admission/fail-closed bounds and measure the maximum valid input at one writer first. Only admit 8/32 such simultaneous inputs after memory headroom is measured; document inability to safely run rather than causing OOM. A 64 MiB byte cap does not bound total DOM/materialized/snapshot heap.

Hard correctness gates: no full account scan or hidden write under project guards; bounded constant token/header bytes; one full snapshot for a new ordinary-session request; canceled observations never allow commit; all deterministic outcome/cleanup proofs pass. Performance acceptance needs the complete HTTP baseline and explicit capacity targets before release; neither source inspection nor earlier native benchmarks supplies them. If one remaining full snapshot fails the 10,000-user target, stop the release and review a bounded immutable index/read model outside P separately instead of claiming the bottleneck solved.

Remaining blockers are H1 runtime/portability/Windows publication proof, H2 source/constructor inventory and actual 30-row discovery, actual emitted 503 union validation, and measured capacity/memory/observation budget. No new authority lease, account-schema redesign, global auth-outage remapping, SQL migration or client mutation activation is needed for this card.
