# P02b governed definition tool cutover

Status: implementation card, 2026-10-16. The ten governed binding/read-policy tests
are source cases, not execution proof. Parent owns serialized validation and commits.
This card closes runtime integration left by the pure binding helpers; it does not
claim that those helpers alone protect a tool call.

## Persisted interpretation

Use the existing Agent tool journal, not another invocation or receipt store.
The three supported tools are project create, subproject create and project scalar
update. Their new prepared payload uses semantic version 2, Mutation/OwnerReceipt,
original canonical arguments, and a `projects-definition-source` version 1 envelope.
The source is generated by Workbench from a verified saved session and admission.
It contains primitive immutable evidence, no live lease, service, token secret, or
LLM-supplied actor identity. The existing 64 KiB source envelope ceiling is enforced
before journal admission; overly large source policies fail explicitly.

Persist the original namespace, epoch, caller binding, request schema/normalization
version, verified session identity and original Agent or Process source. Capture
these during async provider construction and freeze them before preparing a proposal.
The proposal digest binds original arguments and the exact source envelope. The
Projects operation ID is the journal's saved BusinessIntentId; diagnostic call IDs
and new random retry IDs cannot allocate owner identity. The final effect binding
also binds the saved batch, intent and approved proposal digest, independently of
the caller key. It deliberately does not hash itself through SourcePreparation.

Restore the original v2/v1 interpretation during the retained horizon, using the
version-one hard decoding limits. Current deployment limits apply only to a new
effect. A new tool context, epoch, claim, policy or newer decoder must not overwrite
the saved operation context. Legacy proposals without this source and operation
address remain on their existing explicit reconciliation path; they cannot be
silently upgraded into replay-safe effects.

## Minimal shared runtime seam

`AgentRuntimeToolMetadata` gains an optional typed restore callback accepting the
original arguments and original source envelope. `MafToolRunContext.Prepare` calls
it only for restoration. A declared restore callback with missing/corrupt source
fails closed. Providers without this callback keep their existing behavior.

`PrepareInvocation` resolves the exact original proposal by active batch/call/tool,
or by the exact prior approval binding. It uses original preparation for Prepared,
Executing, ReconciliationRequired and Completed states. It never searches another
batch by identical name/arguments. Existing completed context-tool behavior remains
separate. `CheckRecoveryAsync` uses the same restoration callback. Completed results
still require the current owner disclosure callback; restoring preparation does not
authorize a write or disclose a result.

## Owner order and creation

1. Verify the live journal claim or canonical read-only reconciliation claim.
2. Decode and bind the exact saved source, request and stable caller. Build the
   original operation address from saved source plus saved business intent.
3. Query the Projects receipt under current target read permission. An accepted
   result returns its exact historical acknowledgement, never a current definition
   read. Expired, changed, invalid or closed context cannot allocate a reservation
   or dispatch a new effect. Draining without receipt remains unresolved.
4. Only a genuinely Open/NotObserved operation may enter new effect preparation.
   Revalidate original source/current policy and original target lifetime. Keep the
   request's original definition revision; no fresh read supplies its expectation.
5. For creation, derive the reserved project ID from an explicit domain-separated
   fixed primitive encoding of namespace, trusted caller kind/key and intent.
   Use the business intent as the existing reservation operation ID. Existing
   `ReserveCreationAsync` persists and recovers the exact Reserved/Consumed lifetime.
   Do not call the coordinator's old random-ID path on retry. The same exact
   reservation participates in normalized creation intent and source effect binding.
6. Submit through the protected Projects writer. Record known acceptance in the
   runtime effect scope before optional access/session/result bookkeeping. Preserve
   Accepted versus Rejected versus Unconfirmed; no new operation is allocated on
   response loss. The owner remains the final epoch/authority/transaction fence.

For subproject creation, original parent admission must come from retained source
or explicit original request evidence. An unrestricted Agent grant is not evidence
that a newly read same-ID parent was the parent of the original proposal.

## Focused proof required

- Restore keeps namespace/epoch/original expectation and material source despite a
  new provider snapshot; missing/corrupt/unsupported source fails before dispatch.
- Same tool/name/arguments in another batch cannot inherit the first operation.
- Prepared approval continuation and Executing uncertain continuation use the exact
  saved source; Completed replay invokes disclosure only and does not invoke owner.
- Changed approved intent/material source changes semantic effect; caller remains
  stable for the same admitted execution. Different execution changes caller.
- Lost response followed by replay returns the same accepted scalar/full result
  after a later edit, including expired dispatch and write-revoked/read-allowed.
- Current read revocation or lifetime replacement prevents historical disclosure.
- Recreated parent rejects original subproject proposal before reservation/effect.
- Creation response loss reuses exact reservation, project/lifetime, operation and
  result; no duplicate project or fresh reservation is created after Closed/Expired.
- Accepted creation followed by session-grant/disclosure cleanup failure remains
  known committed and reconciles from its owner receipt.
- Actual runtime declarations have preparation, restore, approval, disclosure and
  cancellation-reconciliation coverage; unchanged tools retain prior metadata.
- Bounded source/arguments and hard-limit old receipt restoration are tested.

No source-policy JSON is accepted as caller authority. Only the trusted journal and
its verified claims may supply restored evidence. Actual new effects still acquire
the existing current source lease and owner transaction guards.

## P06 reservation and grant cleanup boundary

The governed creation adapter retains the existing owner reservation and catalog
grant before the protected definition transaction. These are separate durable
preparations. An exact retry reuses the business-intent reservation and the fixed,
domain-separated project identifier; it does not allocate another target. Lookup
precedes reservation/grant work, so an already closed or expired operation cannot
start preparation. Closure can nevertheless race between that lookup and the
separate preparation commits. The definition transaction's epoch fence still
prevents publication after closure, but preparation may remain.

Never compensate automatically after a timeout, disconnected response, unknown
commit, or one rejected duplicate attempt: another original dispatch may still
commit or have committed. The current adapter deliberately retains preparation in
these cases and does not call the old creation coordinator's exception cleanup.
Accepted owner result remains authoritative even when later session bookkeeping
or the optional reservation reread fails; such failures are logged and the exact
acknowledgement is returned.

P06 must implement cleanup as a separate owner-authorized action, with original
namespace/caller/epoch/intent and exact reservation tuple. It must first obtain a
retained ClosedAbsent observation, then atomically ensure the same reservation is
still Reserved and no live creation receipt/target exists before cancellation.
Catalog grant removal must address only that exact reserved lifetime; a consumed
reservation or accepted owner result is never compensated. A crash after
cancellation and before grant removal must remain resumable through the existing
reservation/catalog owner seams. An expired or unavailable receipt alone is not
evidence authorizing cleanup; retention policy must preserve enough closure and
reservation evidence to decide it safely.

Required P06 tests are closure between prelookup and reservation, cancellation
after ClosedAbsent, accepted/unknown duplicate racing cleanup, consumed reservation
refusal, recreated project lifetime preservation, and crash between reservation
cancellation and catalog grant removal. Until this closes, report retained orphan
preparation explicitly; do not claim fully automatic creation cleanup or weaken
accepted receipt retention.

The final cutover audit must also cover provider contexts outside a recoverable
interactive/background journal. They currently use the earlier authority-guarded
mutation path and have no protected operation identity. Move each real producer to
an existing durable admitted execution or explicitly reject these three definition
mutations in that context. Never mint an identity from agent labels, invocation
text or a random retry identifier, and do not describe the current journal-specific
adapter as protection for those remaining producers.
