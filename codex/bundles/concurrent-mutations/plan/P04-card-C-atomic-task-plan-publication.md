## C1 contracts and exact new-task shape

Authored internal signatures, with concrete types rather than a generic command callback:

```csharp
ProjectTaskPlanProposal Normalize(ProjectTaskPlanDraft draft);
ProjectTaskPlanStagedBatch StageNewPlainTasks(WorkbenchDbContext context,
    ProjectWriteAdmission target, ProjectTaskPlanProposal proposal,
    ProjectTaskPlanCurrentMaterial current, DateTimeOffset acceptedAtUtc);
ProjectNodeBindingStorage.PreparedPlainTaskBinding PrepareNewPlainTaskBinding(
    ProjectObjectRecord detachedTask);
void StageNewPlainTaskBinding(DbContext context, ProjectObjectRecord addedTask,
    ProjectNodeBindingStorage.PreparedPlainTaskBinding preparedPlan);
Task<ProjectTaskPlanCurrentMaterial> ReadEnlistedAsync(WorkbenchDbContext context,
    DatasetActivationBinding binding, ProjectWriteAdmission target,
    CancellationToken cancellationToken);
```

Both binding helpers remain internal to the existing binding owner, with `StageNewPlainTasks` their only new production caller. Pure preparation validates a detached row and creates its existing `ProjectNodeBindingPersistencePlan`. A narrow `PreparedPlainTaskBinding` holds that plan, the exact row reference and an immutable identity/value snapshot; staging requires the same unchanged Added row once. The old generic plan has no row identity and therefore cannot supply this correspondence by itself. Nonempty new IDs, one exact project, canonical Task subtype, fixed project-root parent and the closed plain-task shape are mandatory. A tracked existing row, foreign binding, media/storage reference, explicit or legacy metadata reference, unknown metadata extension or duplicate staged identity is rejected. There is no `skipLocks`, `validate=false`, generic bulk upsert or arbitrary `ProjectObjectCreateRequest` overload.

Construct every detached task and prepare every binding plan before tracking any entry. Check target/current-material identity, complete proposal/row/combined bounds and duplicate IDs/node keys first. Take one snapshot of relevant tracked task/binding identities and states, then use HashSets for collision checks; do not repeatedly enumerate `ChangeTracker.Entries` or `DbSet.Local` per task. Only after all validation succeeds may the synchronous owner stage the complete task and binding arrays. No await, external mutable row or callback is admitted between preparation and staging. The Added-state/plan correspondence guard remains in the binding owner; normal input refusals must leave the context's prior tracked state unchanged. Unexpected staging/Save failures still require the caller to discard/roll back the owner transaction, not reuse a partial tracker.

The draft has only a version and an ordered list of `{ Title, Description, Notes, Priority }`. Ordinal is the stable request-to-result mapping; no client node identity, arbitrary subtype/metadata/parent/status, schedule, dependency, assignment, resource, estimate, asset, Process or Workflow field exists. A strict external adapter later rejects unknown fields rather than ignoring requested functionality. Normalize once: trim Title/Description/Notes consistently with the existing owner text behavior, reject blank titles and titles over 200 characters, validate Priority in 0..6 rather than clamping, reject malformed UTF-16. Initial proposed bounds are 1..100 tasks, 64 KiB UTF-8 per Description/Notes, 256 KiB aggregate raw proposal strings, 1 MiB canonical proposal and 2 MiB exact receipt. These are hard candidate caps, not measured deployment limits; bounds are checked before list/string copies, again during bounded encoding, and before effect admission. No truncation. Versioned hard decoding limits survive later tighter deployment limits for old receipts.

Those raw field ceilings do not promise that every boundary-size string fits the stored shape. B1 limits the entire stored `MetadataJson` field to 65,536 UTF-8 bytes (`ProjectTaskPlanBasisLimits.MaximumFieldBytes`), including envelope/default fields and JSON escaping. After constructing canonical metadata, run the actual row through `ProjectTaskPlanMaterialProjection.ValidateSourceBytes` and `Project`; reject a serialized field above that ceiling before tracking. A 64 KiB Description can therefore be refused even when its raw field fits. Do not silently raise B1's limit, truncate, or accept a row that immediately makes supported capture impossible. Raw-input checks still precede normalization/copying; the bounded canonical encoding check is a second check, not a replacement allocation claim.

For each normalized item create `ProjectObjectRecord` with a new owner-generated Guid and `custom:{guid:N}` node key, WorkItem/Task, Subtitle `Task`, Status `Draft`, progress from the canonical status helper, the requested validated priority, fixed project root, null Start/End/Duration, empty markers and fresh typed WorkItem metadata. The latter has requested Description, null Due, empty estimate/assignment and NotStarted execution. Give each row a fresh `ProjectNodeReferenceCollection` with empty entries; its existing static `Empty` instance is mutable and must not be shared by the new batch. Set Created/Updated once from the transaction's nondefault UTC database timestamp. Layout uses the already read candidate count plus ordinal and is included in the exact acknowledgement; it is not a planner input or a reason to query graph layout. No links, row-order entries, assignments, resources, external bindings or Storage objects are inserted.

Owner-generated IDs are not part of semantic request equality. A rolled-back attempt can allocate unused IDs; an accepted attempt always replays its stored IDs. The acknowledgement contains every accepted item in original ordinal order, its record ID/node key/root key and exact normalized persisted scalar/typed metadata/default layout values. It is historical accepted content, not a later `GetStructureAsync` result. Use a bounded plain-task acknowledgement, not the unrestricted `ProjectStructureNode` DTO with runtime/external fields.

### Why the global binding lock can be omitted here

`ProjectNodeBindingStorage.PersistAsync:305` currently acquires `workbench:managed-storage-bindings` (B), reads an existing binding and reads references for every node. A loop adds two per-task SELECTs and serializes disjoint projects.

The preparation phase calls the same private `CreatePersistencePlan`, verifies that the resulting binding is exactly the local project route/WorkItem kind with null external ID and empty media/storage fields, and verifies zero references. The Added-only stage then uses the existing insert branch of `UpsertBindingRecord` and `Apply`. It stages one binding per new task with zero SELECTs, zero lock queries and no B. Checking `NodeReferences.IsEmpty` alone is insufficient because `ResolveReferenceCollection` can discover legacy references in metadata; checking only the filtered plan references also does not admit malformed explicit reference entries. Require both the closed input shape and the validated plan.

`ProjectObjectMetadataSerializer.SerializePreservingUnknownProperties` deliberately retains unknown top-level and nested members. Its ordinary validation is not a strict plain-task gate. The new preparation must require metadata to be the exact canonical serialization of the closed typed task envelope, including its fixed default values, before calling the ordinary plan helper. This internal path receives owner-created canonical metadata, so refusing reordered, duplicate, legacy or unknown syntax is intentional and requires no new general JSON parser. The operation cannot change or claim a managed Storage object, so no shared Storage ownership exclusion is needed. Existing object uniqueness/PK constraints still apply, P excludes same-project writers/deletion, and lifecycle/table fencing excludes import/restore. All existing generic binding writes retain B.
