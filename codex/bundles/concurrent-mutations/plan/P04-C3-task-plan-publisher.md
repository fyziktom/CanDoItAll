## Atomic checks and lock order

Before the first dispatch, the eventual producer durably saves the original typed envelope under its existing intent/decision identity. C3 alone does not supply that producer persistence. It never mints a new operation on retry or refreshes an original business expectation.

1. Bound/validate supported original input before copying/normalizing/encoding; capture current active profile/binding and trusted caller. Perform bounded independent receipt lookup first. Exact accepted result with current read permission replays before current write/generation checks and before stricter present-day new-write limits. Identity conflict is not a new command. Initial malformed input or definite admission refusal is a no-effect result for this attempt only.
2. For a possible new effect acquire the held source/decision lease outside any SQL transaction. Build the exact target plus explicitly declared source-project admission set; reject duplicate contradictory lifetimes and unsupported producers. Initial append has one target and at most its one original source Project; do not accept an unbounded caller-supplied lock list.
3. Begin a dedicated Workbench PostgreSQL **ReadCommitted** transaction. Enter that exact context in the coordinator; install the issued/current minimum finite transaction, statement and lock deadlines via `FiniteOperationEpochStore.EnterAsync`. It performs the expired-request precheck before lifecycle SHARE, then lifecycle/epoch SHARE and authoritative check. Acquire one transaction advisory operation key containing the fixed Workbench pool/family, namespace, epoch, caller kind/key and operation ID. Do not share the Projects definition operation domain.
4. Recheck the exact receipt under operation exclusion. If found by a bounded existence projection, retain that positive existence knowledge, leave SQL ownership completely, and release the already-held source/catalog lease before independent current disclosure/reconciliation. Dispose the transaction/enrollment/context first, then the held source lease, then invoke the receipt reader/access boundary. Never borrow a second pool connection while holding the first or acquire a second catalog read while retaining the first: a queued catalog writer can make the latter deadlock. Retain the observed existence and attempt knowledge across both cleanup steps; do not load the full payload under the operation lock only to test its presence. A release failure preserves already-disclosed Accepted with a typed cleanup warning or unresolved Unconfirmed; undisclosed receipt details remain withheld, and cleanup never becomes a fresh no-effect rejection. For a new effect establish any already-approved enlisted source guard, then acquire the complete sorted P set once with `SerializableMutationScope.AcquireRelationalScopeLocksAsync`. The helper name does not change RC. No B, nested scope, task loop of locks or application-wide semaphore. Recheck finite admission after all waits.
5. Invoke C1 `ReadEnlistedAsync`. Require exact original namespace, profile, Project lifetime/revision/scalars and whole typed task-set equality; no hash-only currentness. Compare database observation time to the immutable original capture and decision times. Initial owner mandate is RequireCurrent with Fail or PauseForReview and zero automatic replans; neither PinnedObservation nor unsupported Replan is accepted. Positive work/basis-age ceilings are explicit validated options, never an invented default or client-only promise. Provider read mode can remain RunSnapshot/StepSnapshot but cannot weaken owner publication.
6. Stage all C1 tasks/bindings and the exact encoded owner acknowledgement in the same context. Repeat held source/decision/current Project admission, both decision-policy age/work budgets using server time, and issued deadline immediately before the only SaveChanges/commit sequence. Use existing `ProjectWriteAdmissionService.RequireManyForMutationAsync` for the bounded complete admission set; it creates an enlisted owner context on the same connection, not an independent pool connection or another P acquisition. The owner row gates stabilize basis facts; no unlocked full graph, resource validation or pricing occurs. A final check cannot make independent file authority revocation atomic with SQL commit; each concrete adapter must state its actual held-lease/observation guarantee.
7. Record commit-attempted before CommitAsync and known Accepted immediately after its acknowledged return, outside cleanup scopes. Any later source/context/connection cleanup failure preserves exact Accepted with a typed cleanup warning. An unacknowledged commit remains Unconfirmed until exact outside-transaction reconciliation. SQL 40001/40P01/known rollback is a refused attempt, never an automatic semantic replan; a duplicate may already have committed, so reconcile the address before claiming historical absence.

The outer attempt must preserve **both** effect knowledge and cleanup failures through every unwind. After commit-attempted, read denial/unavailability, changed namespace or an uninspectable result cannot downgrade Unconfirmed to Rejected. A later same-envelope denied attempt does not resolve an earlier uncertainty. Only exact Accepted or authoritative fully retained ClosedAbsent can resolve prior ambiguity; NotObserved in Open/Draining is insufficient. Retired/unsupported detail remains historically unknown.
