## Confirmed gap and guarantee

`src/App/CanDoItAll.Web/Api/ProjectDefinitionHttpAccess.cs` checks current Projects read/write in `ResolveAsync`, then creates `ProjectDefinitionInvocation` without `Authorization`. Its receipt adapter rechecks current read only. `ProjectDefinitionWriter.ExecuteCoreAsync` can wait for lifecycle/epoch/operation/project guards and commit without another HTTP write check. `ProjectSourceMutationScope` skips source checks when source authorization is absent. Existing HTTP tests prove revocation between requests, not during an admitted request's owner wait.

The effect-time statement in `docs/architecture/concurrent-mutations/07-projects-contract-cutover.md` must distinguish:

- Governed source invocations retain the existing source lease and validation protocol, including its isolation and lock order.
- HTTP observes the original trusted caller's current write authority after owner waits and immediately before attempting commit. Independent credential persistence can change after the last observation. This is not atomic revocation exclusion through SQL commit.

Do not implement HTTP as a fake `IProjectMutationSourceAuthority`: it would imply an unheld exclusion and unnecessarily move source-null definitions from Read Committed to Serializable. There is no Projects-to-Web/Workspace dependency, token-ID caller partition, implicit new operation ID, or receipt-disclosure-as-write-authority shortcut.

## Alternatives and decision

| Alternative | Correctness/performance result | Decision |
| --- | --- | --- |
| Two whole-store reads under P | Current observation, but O(document) reads/allocations twice while holding project locks. A 64 MiB ceiling is not a throughput solution. | Rejected. |
| Streaming targeted user lookup under P | Retains one account, but preserving current whole-store validity and duplicate-ID/name checks still requires scanning all users. Stopping at the first match changes malformed-unrelated-account behavior. | Useful outside P; insufficient as the final under-P design. |
| Same-document authority generation | Full bounded validation and targeted capture before P; small current generation read plus bounded token record under P. No cache, sidecar publication gap or held file lock. Unrelated authority changes conservatively reject this attempt. | Recommended primary design below. |
| Participating authority read lease | Could prevent cooperating revocation from acknowledging until SQL releases the lease, but requires shared per-token/per-account gates, every writer's participation and a new cross-resource lifetime. Global account lease would serialize unrelated callers. | Do not introduce unless the stronger revocation guarantee is explicitly required. |
| Pre-observation + nonwaiting owner acquisition + proof-age limit | Removes local file reads under P, but only proves authorization was observed recently. It cannot observe a revocation after capture even if it precedes commit. | Valid only as an explicitly weaker contract; does not close the present final-observation claim. |

## Primary design: one authority generation in the existing account document

Keep the existing account file and owner. Introduce a canonical version-two envelope whose first fields are `schemaVersion`, nonempty server-minted `authorityGeneration`, then `users`. The generation and complete document are published by the same `DurableFileWriter` atomic replacement. There is no sidecar, new database, per-user registry, watcher or cached authorization.

### Authority projection and write rules

The generation changes when the complete account set's authority projection changes: account ID/existence, UserName, NormalizedUserName, Enabled, AuthenticationRevision, PasswordHash or AllowedScopes. Compare raw scope strings in ordinal sorted order while retaining multiplicity; do not normalize an invalid spelling/duplicate away or add an Infrastructure dependency on Workspace's scope catalog. This conservatively rotates for altered raw grants even when later domain validation might find equivalent authority. Include the password hash because direct store Save can change its validity without incrementing AuthenticationRevision. Do not log or expose a hash/fingerprint of this projection; the public generation is a fresh random GUID, not derived secret data.

Exclude DisplayName, Version, CreatedAtUtc and UpdatedAtUtc from the projection. Store validity and existing version/CAS rules still apply. Pure presentation/version/time changes through the low-level store preserve the generation. An administration Update still rotates it because the current service intentionally increments AuthenticationRevision even for cosmetic UI edits. Login rehash rotates it conservatively; normal/failed login and token issuance do not. There is no new per-request generation write.

Centralize this comparison in `FileApiUserStore.SaveAsync`/`DeleteAsync`, inside the existing whole-file mutation gate and before publication. New account/deletion always rotate. A valid rewrite with unchanged authority preserves the previous generation. Authority A→B→A gets a new generation on each change; do not reuse old values. Two hosts use the existing mutation gate plus current stored version, so they cannot both publish from an unchecked stale document.

The writer first freezes incoming AllowedScopes at its API boundary. Projection comparison, validation and publication must use that same detached list; an externally mutable IReadOnlyList must not change after comparison while retaining the old generation.

### Reuse the validated account snapshot before any Projects transaction

`IApiUserStore.ReadSnapshotAsync` returns a detached immutable collection of users and the generation from the same opened document. Nested scope collections are detached too; `IReadOnlyList` alone is not an alias boundary. Reuse the existing complete-document semantic validation, including malformed unrelated accounts and duplicate IDs/names. A bounded framework JSON DOM checks the supported envelope and account count before record materialization. A missing requested account remains absent rather than a default enabled identity. This whole snapshot is read only before Projects/SQL admission; final observations never fall back to it.

H1's approved ceilings are a 64 KiB token document, 64 MiB account document, 10,000 accounts and a 4 KiB canonical header window. There is no new 16 KiB per-account limit. The stream byte cap precedes DOM/record allocation; count validation precedes materializing the user list. These input bounds do not bound total heap size or prove acceptable latency at 32 concurrent writers. A large valid field may still allocate heavily outside P. Canonical maximum serialization and complete-request allocation measurements remain required. Oversized or noncanonical legacy data needs explicit remediation; no truncation/fallback. No deployment's private files were inspected.

H2 makes `ApiSessionService` project current identity and generation from one shared validation core. Successful real JWT middleware publishes an immutable request-local observation containing that selected result; the protected-write resolver consumes it without the current second full account scan. The generation is trusted runtime state, never public session JSON or caller claims. Missing middleware evidence is explicit refusal in this HTTP capture path; direct nonmiddleware callers retain an explicitly fresh validation path. Ordinary resolver and receipt disclosure remain fresh. The existing two-scan cost remains the measurement baseline; the candidate is one full pre-admission read for a new ordinary-session write, not a zero-read/cache claim. See the exact ownership and lifetime in the H2 card.

### Small final observations under P

After all owner waits, and again just before `CommitAttempted`, the HTTP observer:

1. Verifies current mode, verified issuer/subject and expiry against the original trusted caller. OpenApi must still be open; authenticated mode cannot fall back to OpenApi. The HTTP principal path never starts interactive refresh.
2. Re-reads the bounded original token record when managed. It must remain active, identify the same subject/kind/user binding and permit both Projects read and write together with the verified claims. A changed session token revision/scope binding cannot be silently paired with the old user snapshot.
3. For an ordinary user session, reads only the canonical account header through a fresh handle and compares its generation to the fully validated pre-admission snapshot. If equal, the account authority projection has not changed under the cooperating writer protocol. Pure in-memory checks also re-evaluate expiry and relevant current configured administrator/mode rules. No password hashing, full account scan or new database connection occurs here.

Changed generation returns a distinct known-precommit `AuthorityChanged` decision, not "this user was revoked." Even another account's authority change can cause that conservative conflict. Roll back this attempt and return a typed conflict, with no internal effect retry. Re-admission may use the exact original operation/payload/business expectation and capture fresh current authority; it must not mint an operation ID or refresh the expected Project revision. A previous Unconfirmed attempt remains unresolved until exact retained evidence says otherwise.

### Prefix validation, corruption and compatibility

Both initial full validation and the prefix reader require the exact supported header order and unique required fields with nonempty generation; unexpected legacy shape, missing/duplicate/reordered header fields, prefix larger than the ceiling or malformed JSON before `users` fail explicitly. There is no fallback to full account reads, migration, directory creation or token/account mutation-lock acquisition under P.

A prefix reader cannot detect a malicious/incorrect edit later in the body that preserves the generation, or a duplicate generation appended after `users`. Soundness therefore explicitly depends on canonical whole-document validation at initial capture and every cooperating publisher. A full capture rejects such malformed tail data; the final prefix alone cannot. Private-file permissions and existing safe paths remain required but are not claimed to detect arbitrary trusted-local tampering. Unsupported online direct edits/restores must stop writers, perform full validation/recovery and publish a fresh generation before resuming. File time/length is not substituted as a security proof, and no silent self-healing occurs.

Add one explicit `EnsureAuthorityFormatAsync` readiness operation on the existing store, called by Web startup before admitting HTTP, outside database transactions. It takes the existing account mutation gate. Absent state becomes an empty canonical v2 document; an exact supported v1 document is fully validated and atomically rewritten once with a new generation; valid v2 preserves its generation; malformed/unknown formats fail readiness without overwrite. A crash before replacement leaves v1; a crash/lost acknowledgement after replacement leaves complete v2. Retry validates that state rather than reminting a successful generation. Old binaries reject schema v2 instead of publishing v1 over it. No hidden migration occurs on an authorization read. Profile/business import remains unrelated.

## Why not a read lease or a proof-age shortcut now

A real lease would acquire token then account shared authority gates before any Projects transaction, retain them through commit, and require token Register/Revoke/Delete plus account Save/Delete/migration to take corresponding exclusive gates. The account gate must be per account, with the existing global writer gate ordered before it; a global read lease would block all account administration behind any admitted owner. Register currently lacks the required authority gate. Revocation fairness is not guaranteed; timeouts and retained commit knowledge would need explicit contracts. This is materially larger than a same-document generation observation.

Cross-platform lease safety also cannot be inferred from FileShare alone: the .NET 10.0.4 Unix implementation uses advisory locks, permits disabling them, and ignores some unsupported-lock errors. A guaranteed fail-closed lease would need supported-filesystem verification and actual cross-process proof, not a new wrapper around best-effort behavior. See the [version-pinned .NET source](https://github.com/dotnet/runtime/blob/v10.0.4/src/libraries/System.Private.CoreLib/src/Microsoft/Win32/SafeHandles/SafeFileHandle.Unix.cs#L314-L328). That is not required by the recommended observation contract.

The proof-age alternative is explicitly weaker: observe outside SQL, acquire *all* lifecycle/epoch/operation/project locks without waiting, reject any contention, use a monotonic short age limit, and refuse commit when the proof is too old. It can support "authorization observed no more than X ago," not "current write observed after waits/finally." A revocation completed after the observation can be missed within X. Transaction/data locks can still wait after advisory acquisition, so an actual final age check remains necessary. The present waiting source scope is not a drop-in nonwaiting API, and replacing it would introduce hot-project refusals and new admission semantics. Do not adopt this by quietly weakening the current contract.
