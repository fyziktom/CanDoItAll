## Exact narrow collection configuration

The following is a runsettings design, not an executed configuration. Replace the output path with the absolute pre-recorded directory in the parent's checkout and XML-escape it. Preserve the parent's existing harness environment and exact filter independently.

```xml
<RunSettings>
  <RunConfiguration>
    <MaxCpuCount>1</MaxCpuCount>
    <TestSessionTimeout>600000</TestSessionTimeout>
    <TreatNoTestsAsError>true</TreatNoTestsAsError>
    <EnvironmentVariables>
      <DOTNET_EnableEventPipe>1</DOTNET_EnableEventPipe>
      <DOTNET_EventPipeOutputPath>ABSOLUTE_OWNED_DIRECTORY/receipt-gc-{pid}.nettrace</DOTNET_EventPipeOutputPath>
      <DOTNET_EventPipeCircularMB>80</DOTNET_EventPipeCircularMB>
      <DOTNET_EventPipeConfig>Microsoft-Windows-DotNETRuntime:40020019:5</DOTNET_EventPipeConfig>
    </EnvironmentVariables>
  </RunConfiguration>
</RunSettings>
```

`80` is hexadecimal 128 MiB. The provider mask is the explicit union GC `1`, Loader `8`, JIT `10`, JIT-to-native mapping `20000`, and Stack `40000000`, at verbose level five. GC allocation ticks provide sampled type/size/allocation-stack attribution; this is not every allocation. No exception, database, logging, DiagnosticSource, HTTP/network, private-runtime or application provider is enabled. No heap-collection keyword is enabled. Do not silently use EventPipe defaults, which enable broader providers. [Environment syntax and hexadecimal buffer](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/eventpipe#trace-using-environment-variables), [runtime keyword definitions](https://github.com/dotnet/diagnostics/blob/main/documentation/dotnet-trace-instructions.md).

Keep normal runtime rundown/stackwalking; do not disable it to reduce file size. The reviewed runtime v10.0.4 implementation requests startup stacks, writes process information and executes method rundown on stop. These internal details must be rechecked against the runtime patch recorded by the actual host, not inferred from target framework. The trace can contain method/type/module names, local paths and process command line. Pass no secret on the command line and retain the raw trace locally in the owned artifact directory. It does not require application JSON, argument values, token files, SQL parameters or memory dumps. [Pinned startup/stop implementation](https://github.com/dotnet/runtime/blob/v10.0.4/src/native/eventpipe/ep.c).

## Bounds, process ownership and cleanup

Reuse the parent's existing reviewed fresh-host runner and ownership record. Before launch record the exact output root, runsettings hash, one-row selector, expected source/binary hashes, permitted process tree and output limits. Keep traces outside fixture roots. Only recorded process identities may be stopped; no process-name kill, global temporary cleanup or ordinary application access.

- Wall-clock budget: 600 seconds including setup/workload, plus at most 120 seconds for host/collector shutdown, rundown and output drain. Poll at 250 ms with awaited tasks rather than a busy loop. If the current unprofiled row cannot fit, revise this declared budget before launch; do not extend it automatically after a stall.
- Operational output budget: 512 MiB trace acceptance limit, stop requested at 448 MiB, at least 2 GiB free trace-volume headroom before launch, and bounded 16 MiB stdout plus 16 MiB stderr files. Drain both pipes continuously even after the retained-text limit, recording discarded byte counts; await both pumps and exit independently with bounded cleanup. Never retain an unbounded `ReadToEnd` string. Raw exception/command-line dumps are not summary diagnostics.
- `EventPipeCircularMB` is an internal buffer limit, **not a disk quota**. Runtime v10.0.4 streams startup output by default. A polled stop can overshoot its threshold; this plan does not claim an exact maximum on disk or peak process memory. Record actual size/overshoot, refuse oversized traces for analysis, and preserve their identity/termination status for operator-reviewed cleanup. An exact disk quota would need a separately provisioned mechanism; neither startup tracing nor stock dotnet-trace provides it here. [Pinned runtime streaming default](https://github.com/dotnet/runtime/blob/v10.0.4/src/coreclr/inc/clrconfigvalues.h), [session buffer/stream implementation](https://github.com/dotnet/runtime/blob/v10.0.4/src/native/eventpipe/ep-session.c).
- Prefer normal one-row exit. At a deadline, record failure, stop only the owned runner/host tree, and mark any interrupted trace incomplete even if a parser opens it. Do not retry automatically or interpret lost rundown as absence of allocations. For attachment, request collector stop before terminating it, then use the bounded grace above; do not let a collector survive its host unnoticed.
- Reconcile terminal harness evidence, exact fixture-root cleanup, PID exit, pumps, trace closure and hashes separately. A passing TRX with a surviving host or incomplete trace is not successful diagnostic collection. Delete only reviewed generated diagnostic/tool artifacts after their last use, retaining the compact report and exact failure evidence required by the bundle.

Profiling adds buffer, event and file-write costs. Keep diagnostic memory/timing separate from the 8 GiB/2 GiB/3 GiB unprofiled envelope; do not subtract guessed profiler overhead or treat the traced row as a matched performance sample.

## Parser and interpretation gate

The existing dotnet-stack 9.0.661903 installation's deps file identifies `Microsoft.Diagnostics.Tracing.TraceEvent` 3.1.23. Its installed DLL SHA256 is `7AD04F5ABBD704E8BD9C7B29F9AEAB951F20CDC5D5C8E701F256BE52A6E8543E`. The pinned 3.1.23 parser supports NetTrace major versions 3–6; the reviewed .NET 10.0.4 startup path selects format V4. This establishes source-level format compatibility only. Do not mutate or load arbitrary code into the testhost to parse. A separately owned offline parser must use the exact existing dependency set, record its own version/hash and fail on unresolved dependencies or unsupported format. [TraceEvent 3.1.23 parser](https://github.com/microsoft/perfview/blob/v3.1.23/src/TraceEvent/EventPipe/EventPipeEventSource.cs).

Before accepting attribution require: exactly the intended process; normal end/rundown; nonzero GC allocation samples with resolved application allocation stacks; no reported lost events; sensible monotonic timestamps; observed runtime version; and successful full-stream parsing. Record unresolved-frame/sample percentages and any unknown event versions explicitly. A zero-event parser result is failure, not a zero-allocation finding. Do not rely on a CPU-only `topN` or Speedscope conversion to supply allocation/GC analysis. Do not upload traces to a public viewer. Parser compilation/execution, if needed, remains a separate parent-authorized diagnostic action.

Report weighted allocation samples by managed type and allocation stack, GC counts by generation/reason/type, pause intervals, heap/LOH state at completed collections and event-loss totals. Allocation ticks occur after roughly an allocation threshold and identify the triggering allocation; their weighted totals are estimates, not exact per-type totals. Compare direction and dominant stacks with the harness's precise **process-wide** cumulative delta rather than requiring numerical equality. Do not add background-GC durations to stop-the-world pauses. [GC event meanings and allocation sampling fields](https://learn.microsoft.com/en-us/dotnet/fundamentals/diagnostics/runtime-garbage-collection-events).

Current harness phase offsets are relative to each probe and lack a shared absolute EventPipe timestamp marker. This first trace therefore attributes the whole host, including setup, warmup, all cohorts and cleanup. It may distinguish code paths by stack, but cannot precisely assign every sample to the seven measured windows or assert the exact peak between 20 ms memory observations. No DiagnosticSource payload wildcard is allowed to manufacture correlation. If exact phase correlation proves necessary, propose one separately reviewed test-only monotonic marker; do not add a production telemetry abstraction now. Live-object retention paths and unmanaged allocation roots are also outside this trace's proof.

## Filesystem evidence under the current privilege boundary

Existing read diagnostics/activity payloads remain logical owner observations. `GetProcessIoCounters` may be read with a limited query handle to the owned process, but aggregates process I/O: it does not identify files, replacement/flush operations, cache effects or physical device writes. The trace writer itself adds I/O. Retain any such counters only as process totals, never as a disk attribution result. [Windows process I/O API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getprocessiocounters), [counter fields](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-io_counters).

Standard EventPipe cannot capture Windows kernel filesystem/disk events or native stacks. Actual per-file operation evidence requires a separately authorized Windows ETW/WPR or Process Monitor collection with the appropriate tracing/driver privileges, verified target PID and owned-root restrictions. General ETW permissions and kernel session restrictions differ; no such rights are assumed for this non-admin account, and this plan neither installs a driver nor requests elevation. A later kernel file-I/O trace would establish OS operations, while physical disk attribution additionally needs disk events/correlation and still includes filesystem-cache/writeback behavior. [EventPipe scope](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/eventpipe#eventpipe-vs-etwperf_events), [ETW session access](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/nf-evntrace-starttracew), [SystemTraceProvider restrictions](https://learn.microsoft.com/en-us/windows/win32/etw/configuring-and-starting-a-systemtraceprovider-session), [Process Monitor capabilities](https://learn.microsoft.com/en-us/sysinternals/downloads/procmon).

Thus the supported non-admin action here is managed allocation/GC attribution plus existing logical owner evidence. Physical filesystem-operation/flush/device-I/O proof remains explicitly uncollected. No reduction in logical serialization bytes alone closes that gate.
