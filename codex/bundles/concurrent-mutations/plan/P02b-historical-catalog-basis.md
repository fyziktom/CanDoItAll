# Historical receipt review: invocation catalog basis

Status: parent-authorized source amendment, frozen design before code. The preceding cold graph is rejected for integration because its authority callbacks repeatedly decode the full catalog. No test, allocation, byte-volume or latency qualification is claimed. The new basis is an invocation-only proof used before a response is disclosed; it grants no mutation, provider, journal or approval capability.

## Source-derived defect

For four accepted interactive receipts, the current Core initial/final checks each read the catalog twice (4 reads). Each receipt has six claim checks (claim wrapper before/after, provider before/after, receipt access before/after), each reading it twice, plus two target-policy catalog reads: `4 + 4 * (6 * 2 + 2) = 60` full catalog decodes. With a Process initiated by an Agent, the canonical executor check, original Process source query and source-Agent checks repeat: the corresponding actual branch is `8 + 4 * (6 * 4 + 8) = 136`. These are source call counts, not measured device I/O. A 64 MiB per-file refusal does not make that aggregate acceptable.

## Exact owner-local shape

Add a server-only `AgentHistoricalCatalogBasis` in Core, constructed for one review invocation with the explicit historical catalog port, exact current fence and a cheap current-host predicate. It captures at most two deeply immutable selected `AgentDefinition` records; the full decoded catalog is discarded. Preserve the current Agent projection and permission helpers initially rather than copying a second permission model. Strings are immutable; permissions' allowed-secret list, capabilities and tags must be copied to immutable arrays. No projection or full fingerprint is serialized publicly.

Retain the catalog's already-computed full file digest alongside its assigned `CatalogDataRevision` and scope in `AgentHistoricalAgentRead`; do not hash or serialize the catalog again. The basis pins all three. The original executor A is selected only after Core has validated the actual saved run/session/request correspondence. A second identity B may be selected only by the historical Process source observer after the real original-evidence query returns the exact matching stored Process authority and its Agent ceiling. A proposal/request cannot nominate B. A equals B requires no second decode. Missing/mismatched scope, revision or digest refuses the entire page. A third identity always refuses.

Explicit methods distinguish capture from freshness: initial executor capture, original Process-source capture, sealed selected-record access, current-fence/liveness requirement, final fresh catalog comparison, retirement. Capture of an unexpected identity after sealing refuses; it never reads another catalog. The basis is sealed before the first receipt lookup. Subsequent source/target read-policy checks use only the explicitly captured selected projection. They must not call a cache-shaped `ReadHistoricalAgentAsync` adapter that pretends to make a fresh observation. Retired or concurrent misuse refuses. The claim retains its existing single-use active/retired lifetime and cancellation drainage independently.

One typed composition-root factory, `Func<AgentHistoricalCatalogBasis, AgentHistoricalReceiptReadParticipants>`, creates immutable explicit background/receipt participant collections for that invocation. Its DI construction captures fixed current read dependencies. Its invocation only constructs the shared Workbench historical Process authority plus the Process background and Projects receipt reader using the supplied basis. No child DI scope, per-call service location, ambient context, cross-request cache or generic registry is introduced. The neutral `Processes.Application.IProcessHistoricalSourceAuthorityObserver` contract remains unchanged; only Workbench and Modules.Processes owners already referencing Core receive the basis. The original canonical Project Structure source provider has no catalog constructor dependency and continues using the existing pure policy plus actual source-lifetime query.

## Required call order

1. Require prior initialized profile/current runtime correspondence. Construct one empty basis and its explicit participants. Read and validate the original saved run, journal, chat identity and cursor. No basis grants authority by construction alone.
2. Capture executor A once. Evaluate canonical current read against A and the unchanged saved governance/source. For background Process, query the actual original Process evidence, verify source/execution identity, capture B once if distinct, and evaluate its current source grants. Run the actual source-project lifetime/retirement checks and current operator/API-option/time checks as applicable. All awaits retain current-host fencing.
3. Seal the selected identities and exact catalog witness. Begin the bounded receipt loop (at most four owner lookups, five-second cooperative budget). `claim.RequireAsync` now checks only active/single-use claim, request-specific admission, token and current host fence. This is an explicit protocol change: fresh full-catalog validation surrounds the undisclosed batch rather than every internal await.
4. Each actual Projects owner lookup still validates original namespace/caller/epoch/receipt, runs current target policy using the captured record and original ceiling, and performs its post-access coherent SQL target-lifetime/nonretirement/dataset-lifecycle check. Preserve activation before/after observation and actual Process original-source/SQL checks. Do not delete post-await owner checks to achieve the catalog count.
5. Reread the exact original run/chat witness. Recheck initial/final current source SQL and current operator policy against the same captured records, retaining original Process owner evidence/fingerprint comparison. Any failure discards all pending page knowledge and successor cursor.
6. After **all** receipt, source SQL, activation, run/chat and other awaited checks, make one fresh catalog observation of A. Require scope, catalog revision and full digest equal the initial A/B witness. Check current host fence and requested cancellation immediately afterward. There is no later awaited source-policy check, owner callback, result serialization callback or other async work before pure result construction. File observation itself retains before/after layout/pending checks.
7. Return only sanitized page knowledge/current context/cursor, or a refusal with neither observations nor cursor. Retire the basis on success, exception and drained cancellation. Retirement is synchronous and cannot disclose additional state.

This remains sequential optimistic observation. It does not create a cross-file/SQL lock, prove linearizable revocation, or detect external ABA preserving every durable witness. It is no weaker at the final disclosure boundary: catalog mutation during an awaited owner/source/run operation invalidates the whole page, including observations collected earlier.

## Count and remaining work bounds

|---|---:|---:|---:|
| Interactive Agent | 1 | 1 | 2 |
| Process operator source | 1 executor | 1 | 2 |
| Process Agent source A equals B | 1 shared executor/source | 1 | 2 |
| Process Agent source A differs from B | 2 matching witness selections | 1 executor witness | 3 |

The bounds apply to a four-receipt page and count full catalog deserializations, not physical I/O. The existing logical-byte Activity must report every actual catalog/index/run/chat read; no zero observations are invented. At provisional file ceilings, catalog content can still be 128/192 MiB per page, runs up to 2 × 64 MiB and chat scan up to 2 × 256 MiB, plus indexes, activation, allocations and SQL. ConfigurationJson grant parsing still repeats in existing pure owner helpers; attribute it separately before any owner-local parsed-projection change. Neither reduced counts nor a five-second cooperative token is capacity qualification.

Separate required availability correction: the current scoped cold store permanently pins its first RuntimeSnapshot, which prevents a long-lived native circuit from reviewing after a generation change. The dedicated review service will retain the already initialized immutable canonical Profile and stateless runtime/options/environment dependencies, then capture RequireInitialized(runtimeState) and construct a new standalone store/observer/basis/participants at each explicit method entry. CanonicalRuntimeDatabase is the existing singleton with immutable Profile; no ResolveProfile, initialization, new DI scope or service locator is needed. The original deferred entry guard remains before resolving that singleton/service. The per-call store verifies exact profile/fingerprint correspondence and snapshot equality. A later call on the same canonical profile can use the new generation; an in-flight call keeps its old fence and refuses when changed. A genuinely different profile/fingerprint cannot silently rebind this host and still refuses. Add this next-call versus in-flight distinction to the existing deferred-owner Fact arrangements; do not substitute an undocumented page reload.
