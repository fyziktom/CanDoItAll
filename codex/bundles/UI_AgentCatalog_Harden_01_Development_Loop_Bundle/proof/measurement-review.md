# Direct measurement review

The comparable primary cohort contains 27 completed edit/undo cycles: three repetitions of the frozen Razor, C# and CSS edits on fullapp, Parity and Fast. All three runs use protocol direct-local-v7-confirmed-final-visible, the same machine, SDK 10.0.303, Node 24.19.0, Playwright 1.61.1 / Chromium 149.0.7827.55, live sibling revisions and 1600x1000 frame. See direct-results.json, direct-results-table.md and the original per-run ledgers/events. Every source undo matches its frozen SHA, every run confirms the actual mode and owned runtime/watch generation, and all final production CSS hashes match.

The primary clock covers fsync completion to the final local DOM/computed-style predicate and two animation frames after SDK completion. First-visible time is retained separately in each record and aggregated in JSON. This is a conservative confirmed-visible developer-loop measurement: a transient render can precede the SDK's subsequent browser reload. SDK apply/update durations are separate. No Manager, SourceWatch, remote browser tool or screenshot transport is included.

Primary medians (ms): fullapp Razor 3393.3, C# 1646.5, CSS 7076.5; Parity 962.1, 238.4, 1202.2; Fast 787.9, 171.4, 1029.4. The sandbox is faster for these measured edits. Fast has lower observed medians than Parity, but ranges overlap and n=3 is too small for a general claim. First repetitions are generally slower; they remain in the distributions. No cold-start comparison was performed. Startup/build/hydration time is excluded as a prerequisite, with populated caches. Host order is fixed, so cache/order effects cannot be ruled out.

All 18 primary Razor/C# cycles used SDK-driven browser reload; all nine CSS cycles used static hot update. No primary restart/failure occurred. The CSS edit is real catalog CSS isolation with the correct companion Tailwind watcher, not a Tailwind-only compile benchmark. The Fast output is 12536 bytes versus 115598 production theme bytes; these are only the chosen root outputs, not the total shared BaseLib/scoped asset payload.

The original complete fullapp run using v6 measured first-visible state before SDK completion. Its nine cycles are retained as an incomparable endpoint calibration, not silently relabeled. Under the final v7 protocol, an earlier fullapp run produced five complete cycles and then crashed during the sixth cycle's C# undo. Its source was restored, but the runtime exited with the Blazor renderer exception 'The renderer does not have a component with ID 0.' This is retained as an explicit failed cycle and unresolved development-tool limitation. The next run repeated the unchanged whole-lane protocol and completed. The primary comparison uses complete sequential lanes; earlier successful prefixes and every failure remain available in run-index.json and original evidence.

Other retained warm calibration: one 60-second first-Razor timeout/visible-undo timeout at the isolated database startup confirmation; one missing-SDK-event sample where the event arrived after the first-visible observation; three startup/hydration observation failures; and one deliberately stopped pre-readiness launch after an unapplied harness edit. Readiness now handles the public confirmation continuously during filter and clear and proves a stable interactive catalog. Confirmation counts are preserved; no confirmation was needed inside the final primary trials. No operator database was used.

Acceptance calibration also retains launch argument/profile mismatches, unavailable local browser revision, prerender interaction races, tooltip-trigger targeting and asynchronous favorite-render observation. The final browser versions and controls are frozen and verified. Run-index.json is the exact attempt inventory. Failed calibration never becomes a favorable timing sample.

Historical SB03 remains unchanged and describes a different managed observation loop. These numbers do not rewrite it, measure Manager performance, or prove all application edits will behave the same way.
