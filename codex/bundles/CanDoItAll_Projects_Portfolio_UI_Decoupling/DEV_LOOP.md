# Isolated desktop development loop

The deliverable is a smaller real renderer development closure, not just more projects. Record app/sibling SHA, configuration, framework, source/package mode, restored asset inputs and actual graph/watch set.

Before the move, capture one representative supported-desktop portfolio/editor scenario on an owned Web process. After the move, measure the corresponding extracted Web scenario and independent sandbox. Use the same warm/cold-cache description and a small, stated sample count (for example three Razor, three C# and three owned-CSS edits). Do not spend time on many viewport permutations or statistically unsupported universal speedup claims.

A probe must execute the changed behavior and show it after hydration, not merely detect a build log line. For CSS verify an effective scoped rule. There is no mandatory JS edit probe if this feature owns no JS; test its real shared assets instead. Restore every probe byte exactly and verify the resulting diff.

Use the existing sandbox layout and source-mode conventions. Referencing Web CSS as content is different from referencing Web as a project; nevertheless the content/watch graph still must be recorded. Independently publish the sandbox and prove that its actual components, fonts and theme work without running the production host or database.

Check all protected existing leaf/sandbox graphs for added implementation dependencies, packages, native assets, cycles or unresolved edges. Explain legitimate shared-contract changes. Do not promise a five-project closure in advance; use the actual necessary BaseLib/Common/AppComponents graph, not a duplicated simplified component to hit a target count.

Keep 1920×1080 and default zoom. Functional focus, full wizard/footer access and correct dialog stacking are required. New mobile/medium-screen layout work is not.
