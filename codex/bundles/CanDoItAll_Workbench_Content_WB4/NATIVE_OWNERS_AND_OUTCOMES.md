# Native owners, context and outcome boundaries

This slice must remove presentation coupling without duplicating storage/authorization.
Before edits draw the actual call/commit table for each path from its renderer to native writer.
Use the current source, not class names as proof of semantics. Primary map: S10-S21.

| Path | Native checkpoints that must stay distinct |
|---|---|
| New text/upload | Payload preparation; stored node/media; extra graph links; placement; view readback. |
| Collection open | Semantic scope admission; source set/revision; browser instance; known-file activation. |
| Direct edit | Exact known-file session; SaveTarget acceptance; persisted content revision; editor acknowledgement. |
| Download/local open | Fresh authorized item action/lease; actual browser/host effect; final feedback. |
| Generated image | Placeholder write; queue admission; provider effect; media write; observation. |
| Transcript analysis | Explicit content disclosure; provider result; native metadata/reference save; observation. |
| Summary/image export | Original snapshot/capture; actual stored asset; graph follow-up and readback. |

Use precise results the owner already provides. A known rejection before mutation can allow
corrected input; a known commit retains identity even if secondary work fails; a genuine
unknown result preserves the draft/evidence and prevents blind replay. Do not infer rollback
from a cancellation token, caught exception, dialog close, HTTP status alone or missing toast.

## Captured authority

The original project admission must reach the real mutation boundary, not only a renderer
check. Node/parent record identity matters when a public NodeKey is reused. The actor and
profile lifetime matter for reads as well as writes. A late operation may finish an already
accepted original write, but its acknowledgement cannot reset a new view or acquire the
new view's permission. Reference equality of a renderer request is not a grant.

Scope identity, native file handle, content revision and UI opening are different concepts.
One must not be derived from another by filename or label. Releasing a browser does not
necessarily release an independently held known-file interaction; releasing a view does not
revoke an already issued provider request. Keep ownership explicit and test each release.

## Narrow repairs rather than generic infrastructure

If a native result lacks a necessary accepted identity or phase, add the smallest concrete
result/exception/overload in its real owner and inspect callers. Preserve old non-UI semantics,
public wire formats and documentation. A change that requires migration, cross-owner atomic
commit or a general durable job protocol needs a detailed follow-up map and remains blocking
for the affected unsafe path. Do not skip a native guard to finish the UI.

Do not reset healthy Planning/Insights/Structure sessions, re-extract completed Agent/Provider
UI, broaden FileTools scopes, disable optimistic content concurrency or add AllowAll grants.
No subscription to all modules is needed simply to render one content overlay. Respect
lazy data requirements: metadata before explicit content, bounded sources before activation,
provider choices before explicit invocation; no full-history read at ordinary opening.

## Accounting and evidence

Keep exact input/output fingerprints and effect identities separately from private payloads.
A safe diagnostic identifies the operation, source pair, phase, exception type and protected
original identity without logging secret values or whole contents. Shared raw exceptions can
contain URLs/paths; redact at the existing diagnostic boundary instead of stripping all errors.
A data receipt must not contain reusable credentials. All destructive test actions are limited
to task-owned resources and require exact matching identities.
