A2. Capture exact intended target postconditions
-----------------------------------------------------------------------

Inspect:

The current SharedProviderTargetAttempt records Kind and Before, but does not

unlocking recovery merely because state or concurrency tokens changed.

Required invariant:

A target attempt must capture its exact intended semantic outcome before the
write begins. Do not infer the complete intent only from Kind and Before.

Represent, directly or through an equivalent bounded design:

- Publish:
  intended IsPublished = true;

- Unpublish:
  intended IsPublished = false;

  exact ImportId and ProviderProfileId;

Use canonical normalization shared with the authoritative write path where

Target verification must check:

- exact provider identity;
- exact import/publication identity where applicable;
- exact requested postcondition;
- relevant before/current concurrency tokens;
- stale target, changed target, and generation fencing;
- whether the current authoritative state is still the unchanged before
  state, the desired current state, or an intervening/superseding state.

Do not claim historical causation when only the current desired authoritative
state is provable. It is acceptable to model “desired authoritative state is
satisfied” separately from “this historical attempt is proven to have caused
it.”

Required semantic outcomes:

1. Desired authoritative state satisfied
   - bind the current authoritative state and current tokens;
   - clear the unresolved write lock;
   - retain later unrelated UI state;
   - publish a semantic change only when one is required;
   - never replay the backend mutation.

2. Exact unchanged before-state proves the mutation was not applied
   - clearly report that the write was not applied;
   - permit a deliberate retry or a new deliberate user action;
   - do not perform an automatic replay.

3. Different/intervening/superseding state or insufficient evidence
   - remain visibly unresolved;
   - keep writes blocked;
   - do not clear the attempt merely because the read succeeded;
   - do not replay the mutation.

4. Failed, canceled, stale, or wrong-target read
   - retain the unresolved attempt;
   - emit no stale callback;
   - do not update another target.

Prefer a pure evaluator with direct tests over embedding all classification
logic in the Razor component. Do not introduce a universal mutation framework.

A3. Separate mutation resolution from semantic change delivery
-----------------------------------------------------------------------

Inspect:

- SharedProviderRecovery.cs
- SharedProviderManagementPanel.razor.cs
- SharedProviderSourcesDialog.razor.cs
- AgentProviderProfilesPanel.razor.cs
- the ProvidersChanged callback path
- all source and target recovery tests

The current flow can:

1. remove the unresolved attempt;
2. mark publication as claimed/delivered;
3. await ProvidersChanged.InvokeAsync(...).

If that callback fails or the component is torn down during the handoff, the
backend commit may be known while the parent reconciliation event is lost.
The original write must not be replayed to compensate.

Required lifecycle:

- mutation unresolved;
- mutation resolved with an optional semantic change;
- semantic change pending delivery;
- delivery in progress, serialized by attempt;
- delivery acknowledged;
- terminal attempt cleanup.

Required invariants:

- A known committed or canonically verified change must not be forgotten
  before its parent reconciliation callback is successfully acknowledged or
  explicitly retained as pending delivery.

- Marking a change as delivered before invoking the callback is forbidden.

- A callback failure must leave a visible, retryable delivery/reconciliation
  state.

- Retrying delivery must never repeat the provider/shared-provider backend
  mutation.

- Component/overlay reconstruction in the same circuit must be able to
  continue pending delivery.

- Delivery for target/source A cannot be consumed by target/source B.

- A stale component or stale generation cannot acknowledge or clear a newer
  attempt.

- Concurrent retry clicks must not invoke the same pending delivery in
  parallel.

- Once delivery is successfully acknowledged, normal repeated rendering,
  loading, or verification must not invoke it again.

Do not pretend that arbitrary EventCallback execution has durable exactly-once
semantics. Use the attempt identity as the bounded idempotency key. If the
current callback contract cannot make partial callback execution safe, choose
and document a minimal explicit approach, for example an attempt-scoped
delivery envelope and idempotent receiver-side handling.

Do not broaden this into a general application event bus.

Visible behavior must distinguish:

- write outcome unresolved;
- write resolved but parent reconciliation delivery pending;
- write definitely not applied and eligible for deliberate retry;
- write resolved and fully reconciled.
