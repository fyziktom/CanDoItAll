# Effect, credential and profile safeguards

The selected form edits storage addresses and references, not secret plaintext. Only the
production owner may resolve a credential through the existing StorageCredential purpose
and consumer identity (ST02). Do not pass raw values to the renderer/scenario store, expose
runtime configuration/connection strings wholesale, or record bearer URLs, grant handles,
passwords or private vault keys in receipts. Endpoint/path/username fields can be sensitive
operator data: retain only what the active editor requires; use sanitized controlled fixtures
for logs/screenshots. A safe type alone does not make arbitrary driver exception text safe.

Use coded/typed outcomes with bounded sanitized diagnostic text. Log structured operation,
stage and safe identity. An exception in logging/notification cannot overwrite a known commit.
A generated candidate ID is not a persisted acknowledgement. Do not expose a complete private
submission through generic serialization/receipt inspection just to implement reconciliation.

Preserve bootstrap/system-managed protection, credential references, host-bound filesystem
rules and provider normalization. Disablement is UI guidance, never the only owner guard.
Do not promote a UI capability preview into file access authority. Effective routing/file
read/write/preview authorization remains in current Storage/FileTools/project owners.

Distinguish three identities:

1. Storage catalog/database profile and generation (business data plus host binding).
2. Instance-local API accounts/tokens (not moved by a database switch).
3. Current view/caller/read or operation origin (not durable authority).

A selection change cannot lend an old operation new identity. A current access denial retires
the original management authority; stale denial cannot retire a successor. Completed effects
retain their safe original evidence rather than being described as rolled back by disposal.
Do not copy the API authority model into Storage indiscriminately: use the actual owner's
profile/actor semantics and existing host subscriptions.

Never start network tests, uploads, provider discovery, migrations or credential resolution
from a render, simple filter, wizard step or receipt observation. Existing owner bootstrap-on-
read is explicitly documented in STORAGE_REVIEW_NOTES.md; do not broaden it or conceal it.
The test host owns every database, file root, credential and process. Do not use operator
storage or the ordinary application at port 5032. No real FTP/IPFS account or executable
launch is required. A connection test over private filesystem roots is still an owner effect
and needs exact cleanup and independent assertions.

Recovery/placement continuation is deferred. Keep original intent, target, grants and explicit
operator decisions untouched. An unavailable host slot in the sandbox must be labelled; it
must not simulate authoritative recovery or declare an unresolved placement completed.
