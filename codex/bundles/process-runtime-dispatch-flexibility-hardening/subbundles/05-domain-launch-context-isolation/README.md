## Deliverables

- Smaller domain contributors or strategy classes for .NET scaffold context, software-delivery completion requirements, runtime command writeback, UI screenshot writeback, and generic project-structure context.
- Explicit supported-definition matching with typed constants or descriptors.
- Negative tests proving unrelated business analysis, supplier analysis, reporting, quality management, and data analysis definitions do not receive `.NET`, Blazor, screenshot, product mutation, or runtime command launch variables.
- Compatibility tests proving existing software-delivery, dotnet-solution-setup, dotnet-feature-function-implementation, dotnet-runtime-command-writeback, and dotnet-ui-screenshot-writeback variables still materialize as before.
- Clear separation between parent process launch variables and subprocess-scoped derived variables.

## Implementation Steps

1. Inventory current variables emitted by `DotNetProcessLaunchVariableContributor` and classify them by domain concern.
2. Extract focused contributors or internal strategy classes while preserving registration through `IProjectStructureProcessLaunchVariableContributor`.
3. Replace hardcoded repeated process keys with typed constants/descriptors.
4. Add explicit negative tests for non-software enterprise definitions.
5. Preserve current positive tests for software-delivery and .NET subprocess definitions.
6. Verify project-structure subprocess launch still supplies parent/child identity variables and scoped launch variables correctly.
7. Update proof artifacts and execution report.

## Scope Exceptions

- Template text cleanup is allowed only when needed to align with extracted launch contributors and must preserve process behavior.
- Full migration from launch variables to new typed launch contracts is a follow-up unless SB04 created compatibility wrappers and all templates remain supported.

## Do Not Do

- Do not make the generic process launch service understand .NET solution structure or software-delivery process keys.
- Do not emit DotNet or product mutation variables for unrelated process definitions.
- Do not remove existing variables used by current templates without compatibility tests and migration notes.

## Acceptance Checklist

- Domain contributors are small enough to reason about and test independently.
- Supported process definitions are matched through typed constants/descriptors.
- Non-software enterprise process launch variables remain clean.
- Existing .NET/software-delivery variables and completion requirement maps remain compatible.
- Subprocess launch variables preserve parent run, parent step, definition key, and project node scope.
