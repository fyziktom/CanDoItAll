# Normalized Requirements

| ID | Requirement | Observable Acceptance |
| --- | --- | --- |
| R001 | Preserve all functionality introduced by commit `6775de820 phase1` while refactoring. | Existing affected unit and integration tests pass or are replaced by equivalent behavior-preserving tests with clear justification. |
| R002 | Split `ProcessRuntimeIntegrationServices.cs` into coherent services, helpers, drivers, or strategies. | The file no longer owns unrelated launch, prompt, adapter, evidence, telemetry, and recovery classes; extracted services have direct tests and DI registrations. |
| R003 | Keep generic process runtime and application concepts domain-neutral. | Generic process tests for business analysis, supplier analysis, reporting, quality management, and data analysis do not receive software-delivery/.NET/ProjectStructure guidance. |
| R004 | Isolate AgentFramework execution behavior behind process driver services. | Agent invocation, structured output validation, result conversion, manager signals, and runtime execution metadata are owned by driver-level services with interfaces or internal typed contracts suitable for tests. |
| R005 | Extract prompt and brief composition into replaceable driver-owned strategies. | AgentFramework/MAF prompt fragments are composed through typed driver contributors/strategies, can be mocked in launch tests, and can vary by model/provider without editing a monolithic builder or generic Processes application code. |
| R006 | Isolate subprocess launch and child-run outcome handling. | Subprocess launch/reuse/defer/complete behavior is handled by a focused service, with tests for active child waits, stopped child evidence, blocked child propagation, and launch coordinator failures. |
| R007 | Extract completion evidence policies from adapter execution into driver-owned services. | Product mutation proof, managed artifact materialization, required paths, required tool receipts, file content checks, and grounded reference validation are handled by focused driver policy services. |
| R008 | Keep .NET/software-delivery/project-structure launch enrichment domain-specific. | `DotNetProcessLaunchVariableContributor` or replacement contributors are only active for supported definitions and do not mutate launch variables for unrelated enterprise process definitions. |
| R009 | Clean dispatcher branch and recovery responsibilities. | `ProcessRuntimeDispatchApplicationService` delegates branch routing and recovery concerns through injectable services, invokes selected drivers for step execution policy, removes stale duplicated private branch methods, and preserves claim lifecycle behavior. |
| R010 | Keep diagnostics explicit and actionable. | Extracted services return typed decisions or throw explicit exceptions; logs/diagnostics identify run id, step id, step key, policy name, tool name, and masked sensitive values where relevant. |
| R011 | Decompose tests along the new service boundaries. | Large adapter tests are split or augmented with focused tests for prompt strategies, subprocess service, evidence policy, receipt policy, grounding policy, dispatcher branch cleanup, and launch contributors. |
| R012 | Prove enterprise-domain flexibility, not only app-building. | Tests include at least one non-software process launch/brief/dispatch path that remains free of .NET, Blazor, repository, screenshot, and product mutation assumptions. |
| R013 | Driver ports own completion evidence, prompt composition, and step execution dispatch behavior. | Process driver abstractions expose typed ports or strategy facets for prompt composition, completion-evidence validation, and driver-specific step dispatch/recovery policy; generic dispatcher invokes these ports instead of containing AgentFramework/MAF policy. |
| R014 | Maintain one-way dependency direction from MAF/AgentFramework to Processes contracts. | `src/Processes/*` projects reference no MAF, AgentFramework, or module wrapper assemblies; any MAF/AgentFramework process driver implementation references `CanDoItAll.Processes.Drivers.Abstractions` from below and is wired by composition. |
| R015 | Keep generic runtime dispatch orchestration separate from driver-owned step execution dispatch. | Scheduling, claims, runtime state transitions, and immutable plan validation remain generic; provider/tool invocation, prompt fragments, completion evidence, subprocess adapter policy, and driver recovery semantics are implemented by selected drivers. |
