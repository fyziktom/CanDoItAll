# Build Blazor application

Create or update the requested Blazor solution and app using the project-structure declared mode, package choices, routes, features, and output folder. Use workspace file and command tools only inside the approved product root; if that product root is absent, create it there. Never scaffold, restore, build, or write product files under backup, agent-evidence, observation, process-definition, launch-plan, or other evidence-only folders.

If the contract names an exact generated app output root, that root is the only product root. Scaffold the runnable host directly in that root by passing its parent as `parentDirectory` and its leaf folder as `name`; do not scaffold a sibling app with the scenario name, copy a scaffold into a sibling, or validate a sibling as the delivered app. Put generated tests under `<ProductRoot>/tests/<Host>.Tests`, never beside `<ProductRoot>`. Do not create probe, template-test, scratch, copied scaffold, scenario-named project directories, `BaseOutputPath`, `BaseIntermediateOutputPath`, or `MSBuildProjectExtensionsPath` changes inside the process-run output tree; use normal `bin`/`obj` output and final build/run/test commands that target the approved product root.

For greenfield delivery, scaffolding is only the first action, not a deliverable. Implement every explicit project-structure acceptance criterion in this step, including the named UI behavior, routes, input handling, local persistence, PWA/static-hosting assets, and validation proof required by the delivery contract. Do not mark complete while game/business/UI behavior, tests, publishing/static output, or PWA requirements are deferred to "next actions". If a requested criterion cannot be implemented with the available tools, block with the exact failed tool receipt and affected criterion.

Do not ship placeholder behavior for named interactions. If the contract names keyboard controls, route behavior, persistence behavior, or domain/game mechanics, the implementation must make those controls change observable application state and must exercise them in self-review. A scaffold, no-op handlers, random demo loop, or document that lists missing work is not a completed implementation.

For Blazor WebAssembly or PWA work, prefer `workspace_dotnet_new` with the matching Blazor template under the approved product root, then modify the generated project in place. If the contract says WASM PWA, Progressive Web App, installable, offline, manifest, service worker, or static-hosting PWA, scaffold with the Blazor WebAssembly PWA option (`blazorwasm` with the PWA switch supported by the tool/template) and verify `wwwroot/manifest.webmanifest` or `wwwroot/manifest.json`, service worker files, and index.html registration exist before implementation is considered complete. A plain Blazor WASM scaffold without PWA assets is the wrong scaffold for WASM PWA work and must be repaired in the same step.

Before the final build/run handoff, inspect the delivered app entry document (`wwwroot/index.html` for WASM/PWA or the equivalent layout/root document for SSR) and make every local `href`/`src` reference resolve to a real file under the product root or build output. Do not reference Bootstrap, scaffold CSS, icons, manifests, service-worker scripts, or generated CSS paths unless those files exist at the exact referenced route. If the scaffold wrote `wwwroot/app.css`, reference `app.css` or move it under `wwwroot/css/app.css`; do not leave a stale `css/app.css` link. Browser console 404s for local static assets are implementation defects, not acceptable warnings.

For Blazor WebAssembly or PWA apps, inspect `Program.cs` after adding services and again after the final routed component edit. Every service used by a component `@inject`, every constructor-injected interface or concrete service, and every transitive interface dependency must be registered with the WebAssembly host, for example `AddScoped<IStorageClient, BrowserStorageClient>()` when a service depends on `IStorageClient` and `AddScoped<PantryPlannerStateStore>()` when a page injects that concrete service. If the app uses a global JavaScript bridge from a local script, load that script before `_framework/blazor.webassembly.js` in `wwwroot/index.html`, or use an explicit JS module import from the service. Do not mark complete while the rendered page can stay on the loading placeholder because of missing DI registrations or a JavaScript bridge loaded after Blazor startup.

Replace starter content and routes with the contract routes. If the contract names `/`, `/game`, `/scores`, or equivalent primary/scores routes, implement those routes and make the primary route render the actual app surface, not a link list to a secondary scaffold page. Use `workspace_dotnet_run` as HTTP startup proof for web apps; do not request a foreground web run that is expected to keep running until timeout. Run dotnet restore before build-sensitive changes when dependencies changed. Run dotnet build after implementation and run dotnet test when tests exist or are created. For generated test projects, keep tests deterministic and bounded: do not write `while` loops that depend only on mutable game/UI state without a maximum iteration guard and an assertion that each state transition succeeded. Treat compiler, build, test, and analyzer warnings as validation defects in generated apps; do not hand off with warnings in test output when the cited file is editable. For MSTest count assertions, prefer analyzer-approved APIs such as `Assert.HasCount(expected, collection)` over `Assert.AreEqual(expected, collection.Count)` when the generated MSTest package exposes them. Use a `workspace_dotnet_test` timeout of 300 seconds or less unless a real diagnostic proves the generated app tests need more time. When the current-run tool requirements include runtime startup proof, start the app once with `workspace_dotnet_run` and record the startup receipt; leave browser screenshots and console proof to the validation step. Do not mark complete if explicit acceptance criteria are omitted, if output is written outside the approved product root, or if project-structure constraints are narrowed without a decision record.
