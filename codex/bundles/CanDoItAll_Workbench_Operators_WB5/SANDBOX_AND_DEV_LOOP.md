# Independent sandbox and development loop

Provide the same complete participant, meeting, protected reference, quick-action, approval
and web-preview renderers as production. Use two independent specimens for each stateful
family. Fixture callbacks may be deterministic but must not claim a real directory, vault,
process launch or embedding permission. Model unavailable native capabilities explicitly.

Scenarios include loading, successful empty, realistic/large data, missing saved reference,
restricted contact/secret metadata, dirty draft, delayed A→B→A read, rejected write, accepted
write with failed observation, unknown outcome, guarded close, and an independent successor.
Runtime scenarios expose separately started, failed-to-start, early-exit, uncertain, waiting,
serving, stopping and exited states. Do not label a mock URL as native serving proof.

Reuse real BaseLib/RecordBrowsing/CanvasOverlay/EmbeddedBrowser children, not text surrogates.
Feature CSS travels with renderers; neutral assets remain in Components. Inspect generated
manifests, dependency closure, actual network responses and scoped CSS in both source and
independently published hosts. No native DB/bootstrap is required to render this sandbox.

## Desktop-only

All new visual checks use 1920×1080 at device scale 1. No small/medium viewport matrix, mobile
navigation redesign or tablet tuning. Still check actual large-screen visibility, action
footers, scroll ownership, long errors, keyboard/focus, nested-dialog stacking, two windows and
close/remount. Hidden or off-screen text in the DOM is not sufficient visual proof.

## Measurement, not a promised speedup

Record actual SDK, source pair, host configuration, evaluated project graph, watched file set,
startup and edit-to-visible-change. Perform three reversible edits/restorations per owned
Razor, C# and scoped-CSS kind, plus JS only if this slice owns changed JS. Record server PID,
browser navigation/time origin, expected rendered marker and served/computed bytes. Same PID
alone does not prove in-place application; navigation and restart must be separately marked.

Do not claim removal/restoration succeeded because insertion did. Verify byte-exact source
restoration and visible/computed restoration. WB4's successful small-host CSS observations and
WB3's earlier native tooling qualification have different conditions. A repeatable SDK issue
may be qualified with evidence; do not upgrade SDK or disable security/asset assertions to hide
it. A --no-hot-reload restart is useful fallback evidence, not hot-reload proof. [S02]

Keep the existing WB1–WB4/Agents/Workspace/Projects sandbox graphs unchanged unless a small
intentional shared-neutral delta is explicitly justified and tested. A root-wide build cache
change is not the purpose of this slice.
