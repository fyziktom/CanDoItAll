# Native application journeys

These are proof requirements, not authorization to use the normal application, real customer
records, real credentials, paid inference or destructive host-wide cleanup. Run on owned test
resources, using the actual production routes and owners. External model responses may be
scripted; persistence, tools, approvals, scope checks and process ownership may not be faked.

## A. Directory and assignments from the Structure UI

Create a project through the existing Projects UI, then participant and meeting nodes through
Structure. Add untouched neighboring nodes and another project. Exercise local-only,
existing-party link, explicit unlink, currently supported quick-create kinds, meeting defaults
and selection. Read actual directory/assignment/Workbench records after each accepted phase.

The S0 delayed-create case must create only one original native object and leave the successor
form and its unrelated records unchanged. Fault injection after a real directory commit must
retain identity; repairing lookup cannot call CreateParty again. No automatic participant
link is inferred from successful quick-create.

Competing meeting/participant editors must expose a conflict or exact explicit merge. Verify
native role scope, primary/affiliation identities and missing references; do not silently save
only IDs visible in today's option list. Changing metadata must preserve independent assignment
changes and changing assignment must preserve unrelated node fields and rich unknown metadata.

## B. Protected references and Agent restriction

Use a private synthetic credential and the real secret editor/owner. Prove existing-reference
selection, metadata-only lookup, missing/denied reference, and create-and-use. Inject post-vault
and post-reference failures and reconcile exact IDs. Do not recreate a secret by matching name.
Keep raw values out of snapshots, HTML dumps and test reports; assert safe metadata and hashes.

An ordinary test Agent without the new secret permission must still be refused by the native
tool/owner. Where the product supports it, an explicitly granted Agent can use only the intended
reference. Do not globally change AllowAll, approvals, role ownership or hidden configuration.
Use owned entities and preserve original fields before and after this test.

## C. Real runtime lifecycle

Through the native quick-action/approval UI start a reviewed harmless loopback server/probe in
an owned root, using the actual typed plan and process host. Read the exact session identity,
observe serving bytes, close preview without Stop and verify it remains alive, reopen and Stop
that original process. Confirm exit and descendant cleanup, leaving a separate process/canary
untouched. Do not use a user service as a test process.

Test stale approval after target reclassification/profile replacement, double dispatch,
missing dependency, path refusal, cancelled confirmation, early exit and cancellation after
process acquisition. A request held at Stop must not kill a successor session under the same
node. Retired readiness cannot open a newer preview. Unsupported terminal/elevation stays
unavailable, not relabelled as successful native execution.

## D. Joint operator → Agent → file → report path

Use a UI-created project with the new participant/meeting configuration. Open its actual
contextual Agent chat, require it to read a hidden file canary without putting the canary in
the prompt, then propose one exact allowed file write and attachment plus one separately denied
write. Check actual approval arguments, project/node/file identities, original transcripts,
canonical receipts, file bytes and download hashes. Never treat a model's success sentence or
Completed run alone as proof of filesystem effects. No new capability or broad permission may
be silently added merely to make the scenario pass.

Use deterministic external responses with exact provider call budgets. Observe and continue
accepted identities after a harness timeout; do not replay an approval or recreate the file to
obtain a prettier result. Native content edits must preserve WB4 revision conflict and storage
permission-loss checks.

## E. Workflow, Scheduler, Usage and History continuity

Use saved native Workflow definitions and versions on the same owned project, execute a small
supported Workflow and verify its accepted output/reference through real owners. Retain the
known-incomplete-response refusal. Exercise the already repaired finite enabled Scheduler plan
through restart and keep the future neighbor singular. Do not turn off the finished plan to
avoid the startup regression.

Verify corresponding canonical Usage and separately authorized History. An incomplete derived
index is a legitimate partial state, not a test failure to conceal. Only an explicit documented
owned-scope maintenance operation may derive that index; fingerprint canonical payloads before
and after and do not fabricate usage rows. Historical flows without a content owner stay that
way; do not invent transcript History ownership.

## F. Final owned source + two clients

Reuse the repository's safe multi-instance harness and deterministic upstreams. Keep actual
native-driver model labels and opaque route IDs distinct, default/nondefault selections, saved
client choices, source policy and no personal-provider fallback. Rotate only owned fixture
credentials using exact secret identities after metadata readiness. Maintain both client and
source separation; do not select the first ambiguous name.

Run the affected final consumers on an image built from the final production source pair.
Record app/Components/FileTools sources, fixture/upstream revisions, image digest, test DLL
hashes, expected discovery and actual attempts. The initial baseline is not evidence for the
final rebuilt application. A protocol suite from an unchanged earlier input may be inherited
only with explicit impact justification; it must not be described as newly run.

## Safety and interpretation

Isolated PostgreSQL 18, private artifact roots, unique ports/networks/compose names and owned
processes are mandatory. Do not touch the normal port 5032 application, historical fixtures or
user worktrees. Linux process lanes use --init. Acquire no secrets from real customer systems.
No paid call is authorized; the historical 40/40 budget cannot be reset or renamed.
A correctly provisionable owned fixture is not "blocked" merely because the old manual fixture
is unavailable. Missing OS/elevation permission is reported accurately rather than bypassed.
