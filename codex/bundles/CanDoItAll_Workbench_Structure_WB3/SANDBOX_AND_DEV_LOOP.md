# Representative sandbox and developer-loop proof

The independent Structure sandbox renders the same actual canvas, toolbar,
standard-block toolbox, generic composer and structural dialogs as production.
Use realistic bounded graph fixtures, not a screenshot or a replacement HTML list.
Two independent mounted instances must preserve separate selection, clipboard,
composer, overlay geometry and disposal. Provide controlled delayed reads/writes,
known rejection, committed-with-refresh-warning and unknown outcomes.

Include loading, unavailable, failed and stale context; an empty project; nested and
wide graphs; read-only/system-managed nodes; long labels; multiple independent
editors; raw invalid inputs; unsupported actions; and original-target replacement.
Preserve the actual generic setup-renderer behavior used by the selected fixture.
Do not make all nodes editable or all provider/reference choices available merely
for demonstration.

Use the sibling Components MCP for relevant non-WebGL controls when available.
WebGL/canvas contracts are inspected directly. If a supplied MCP is unavailable,
record the actual failed access and use source/CLI tools; do not install new
services, reconfigure the developer machine or claim an MCP ran when it did not.

## Assets and graph

Evaluate all project/package edges and inspect publicly exposed types; reject
unresolved references and cycles. Protect existing Planning/Insights/Agents/etc.
root graphs. Keep scoped CSS, feature JS, static-asset paths, Fonts/Icons and Tailwind
inputs with their real owners. Use shared CanvasLib asset components in the correct
order. Do not copy font binaries into this handoff or duplicate shared JS source.

Validate source Fast/Parity and separately published Fast/Parity with no native
module services or database. Match served JS/CSS and relevant assembly hashes to
source-pair/publish manifests. A changed scope identifier is not automatically a
missing asset; prove corresponding DOM/CSS coherence.

## Supported UI size

Primary viewport is 1920x1080, DPR1. A second large-desktop viewport is optional
only for a concrete functional issue. No new mobile/tablet/small/medium tuning.
Still verify focus, keyboard path, scroll, menu bounds, full forms/footers, hit
regions, stacking and disappearance of only the intended dialog. Do not remove
existing shared responsive tests or hide real large-screen failures.

## Measure rather than infer

Capture comparable entry and final conditions: SDK, OS, refs, build mode, relevant
props, restore graph, watched paths, startup, three reversible samples for Razor,
C#, scoped CSS and changed feature JS. Confirm the actual visual or behavioral
result; restore source bytes. Record whether the server PID changed, whether the
browser navigated automatically, required manual navigation, or updated in place.

WB2 reported a native SDK CSS hot-reload failure and used restart mode for successful
native CSS samples. Keep that qualification. Reuse a proven small-host configuration;
do not spend the run repeatedly rediscovering the same SDK limitation. A bounded
reproduction is appropriate if the new graph changes it, not a mandatory SDK upgrade.
Report isolated loop usefulness separately from full-Web speedup and release readiness.
