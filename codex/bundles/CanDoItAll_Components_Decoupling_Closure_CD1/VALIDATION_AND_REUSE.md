# Validation with source-addressed reuse

## What this task must not do

Do not start by replaying the entire six-hour PC4 Stable campaign. Do not duplicate every
historical acceptance row/test name into new files, rebuild the entire solution per keystroke,
create a custom configuration per phase, or count overlapping runs as additional coverage.
Do not skip an affected test simply because its previous result was green.

Read the complete current `docs/testing.md`, current CI selections and applicable SharedInfo
before finalizing commands. The paths and class names here are discovery seeds, not frozen
filters or assumed case counts. Do not copy old bundle-specific build configurations from
historical records. Product `CanDoItAll.slnx` intentionally excludes test/support projects.

## Impact selection

Use current CodeAnalytics to find callers, affected test topics and reference chains, recording
index scope, freshness and diagnostics. Include manual/semantic coverage for Razor descendants,
route discovery, dynamic dialogs, DI, JSON/public parameter compatibility, CSS/JS and package
assets. If the configured MCP is unavailable or narrow, document the limitation and follow the
approved repository recovery/fallback procedure; do not fabricate a whole-repo index.

Mandatory discovery seeds include the real `HomePageTests` in
`tests/Components/CanDoItAll.Tests.Components` (namespace
`CanDoItAll.Tests.Components.Shell`), dashboard native/cache tests, MainLayout/startup/profile
and runtime capability tests, shell collaboration/context/conversation tests, existing boundary
and sandbox tests, plus actual affected callers found by analysis. `MainLayoutCollaborationTests`
and `CollaborationBrowserTests` are explicit current shell-regression seeds in `docs/testing.md`.
Resolve other names from the actual checkout rather than guessing a filter that returns zero.

Preserve PC4 launch/predecessor/role-resource integration and browser cases as a regression
floor for any touched Process/Workbench dependency. If those native sources and dependency
closures remain unchanged, reuse their valid owner proof while still driving their affected
application navigation/overlay route through the new shell.

For every executed lane record production/test projects, SDK/source/sibling/configuration/
asset-mode tuple, exact filter, expected and actual discovered cases, refreshed assembly hash,
result rows and retained log/TRX. Build changed production projects first. `--no-build` is valid
only on current outputs. Theories, nonserializable expansion and repeated display labels need
identity reconciliation, not blind de-duplication by text.

## Evidence reuse ledger

Each obligation receives one of `NEW_EXECUTION`, `REUSED_UNCHANGED`, `NOT_APPLICABLE` (reason),
or `BLOCKED`/`NOT_RUN`. A reused record links its actual prior source and proof, lists consumed
code/contract/fixture/asset hashes, explains why the CD1 delta cannot invalidate it, and identifies
its original layer/platform. Missing raw evidence is `UNAVAILABLE`, not a newly verified pass.

Reevaluate compiled/runtime dependency effects; a whole-Web reference can affect integration
or host tests even when their source file did not change. Reuse is not permitted solely from
a same test name or unchanged leaf file. Conversely, a report-only change does not force a new
native runtime campaign. Never present the mixed ledger as a fresh complete Stable invocation.

Retain original failed/interrupted attempts and count only completed eligible rows. PC4 reports
17,401 final passing rows and 18 browser cases; those are prior facts, not CD1's starting score.

## Final integration gate

After implementation stabilizes, run current required static/boundary/documentation gates,
all selected native/light tests and fresh cross-surface browser checks. A change to root shell,
shared assets or route composition requires a broad **UI/native consumer** sweep, not just the
new sandbox. Reconcile all family rows with current proof and rerun affected existing journeys.

Assess the final Stable requirement explicitly under current repository policy and actual
transitive impact. If policy or uncertainty requires a complete Stable run, run **one final
canonical sharded campaign**, preserving completed shards and rerunning only invalidated or
interrupted shards. Do not weaken filters, exclusions, assertions or timeouts to call it green.
If a narrower/composite final closure is justified, give the exact coverage and reuse ledger and
label it as such; never call it a fresh full-suite pass. A mandatory fresh gate cannot be waived
by an old result. Test-framework/build/global fixture changes broaden the impact automatically.

Playwright remains separate from Stable. Deterministic loopback provider and media fixtures
prove their declared native/browser behavior, not live speech or external paid model quality.
Run real-provider tests only with explicit current permission and bounded budget; lack of such
permission is not a reason to mark all component architecture unfinished.

## Assets and development loop

For each moved surface build/publish its light host and the real Web consumer, inspect evaluated
references/runtime assemblies and serve actual assets. Verify current source mode and supported
package/Fast/Parity modes as applicable, sequentially in reusable Debug/Release outputs. Do not
invent asset-mode flags for a project that has none. CSS isolation/Tailwind/published content,
JS module URLs, charts, file renderers, dialogs and lazy descendants need actual browser proof.
Existing unchanged modes may reuse their properly identified proof; the new application seam
must have fresh source and published evidence.

Measure one representative lightweight and native scenario before/after under the same tuple:
startup, watched projects/files, Razor/C#/scoped-CSS/JS edit-to-visible behavior when applicable,
process/browser identity and documented restart cases. State samples and conditions. No invented
speedup, arbitrary timing threshold or backend load from a presentation-only change. A new
read/poll loop or broadened sandbox runtime graph is a regression to resolve, not explain away.

## Required invariants

Retain drafts/EditContext/raw invalid inputs, rendered-target identities, independent read lanes,
one write per actual owner lifetime, accepted/unknown/rejected outcome distinctions and safe
retirement after profile/project/opening changes. Cover two views and delayed completion where
this task changes those lifetimes. Do not rerun every old race solely to fill an acceptance table.
Portability-static final enforcement is required for protected changes, with reviewed deltas
and no final baseline-write mode. Keep schema/pending-model checks if native model inputs change;
no new migration is expected for this presentation closure.
