# Large desktop and development loop

All new visual validation uses 1920×1080, scale 1. Do not spend this run on small/medium/mobile/tablet breakpoints. A second genuinely large viewport is optional only for a concrete reproduced functional bug. Keep existing neutral library tests intact; do not expand a responsive tuning campaign because an old fixture contains other sizes.

Check actual chart/canvas/media initialization, text wrapping, long unknown names, sparse/large lists, scroll containers, reachable actions/footers, keyboard focus, nested overlays and two independent instances. DOM presence alone is not actionability. Use bounded ownership/readiness assertions instead of sleeps or fragile transient implementation maps.

Measure before/after on the same machine/SDK/configuration. Record evaluated project graphs, watched path sets, cold startup and repeated edit-to-visible times for Razor, C#, scoped CSS and owned JS where applicable. Use three visible samples for relevant file kinds. State whether a new component activation, browser reload, process restart or no-hot-reload mode was required. Restore probes byte-for-byte and stop only the owned watcher.

WF1 already narrowed its watch paths to 768 from Web's 4,681, but those results do not establish AC1 performance. Expanding existing AgentFramework.UI may affect its sandbox; report any regression and actual reason. No guaranteed acceleration from file moves alone. Do not weaken asset isolation or add a live application backend to make a sandbox responsive.

Fast/Parity and independent publish must render the same extracted components. Deterministic fixtures may implement the narrow external operation boundary, not replace a hard child widget with a static picture or fake DOM.
