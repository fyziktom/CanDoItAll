# Development-loop proof

This wave isolates UI to make later iteration practical. Establish the actual current technical
editor baseline before moving it. Measure the corresponding original host, final host and independent
A1 sandbox with the same visible selected core scenarios. Do not redo P1/P2 measurements as a new
benchmark project; their retained reference graphs/watch sets are regression inputs.

Record SDK/runtime, platform, source/package mode, main and sibling refs/trees, build configuration,
evaluated reference/package closures, exact watch set and build/hydration conditions. Distinguish
initial build, interactive startup and edit-to-visible time. Record one first and two warm observations
per relevant Razor/C#/scoped-CSS probe; fewer justified samples are observations, not a performance
claim. Do not invent feature-owned JavaScript when there is none. If a probe needs a refresh to
recreate state after Hot Reload, say so and use the same definition across compared hosts.

Use task-owned short paths and ports; no concurrent expensive validation or rebuilds during timing.
Restore probe bytes and verify SHA-256, then rebuild/check affected final artifacts. Do not disable
normal file watching, change global SDK flags or remove template behavior in the actual product to
improve the chart. A sandbox with no backend graph is useful even if a first Razor probe is slower.

Independent publish proof is separate from watch proof: run the published sandbox outside source,
without product connection config, and inspect served theme/scoped CSS/fonts and actual widgets.
Core/Workspace/Projects/catalog UI must not acquire new Editor dependencies. Report legitimate graph
increase in product composition separately from preserved lightweight leaf closures. No fixed project
count, interface quota or universal Web speedup is an acceptance criterion.
