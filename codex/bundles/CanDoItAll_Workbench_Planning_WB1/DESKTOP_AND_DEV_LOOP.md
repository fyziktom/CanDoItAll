# Supported desktop and real development loop

Primary browser viewport: 1920×1080, scale 1. A second large viewport is optional only for a
specific functional issue. No small/medium/mobile/tablet responsive tuning. Preserve current
shared library tests; this restriction does not authorize deleting existing coverage.

Before moving code record actual SDK/configuration, sibling refs, evaluated dependency edges,
watch file set and warm-output startup. After extraction repeat equivalent scenarios, with
at least three observations each for owned Razor, C# and scoped CSS where present. Measure
an owned JS file only if the new family actually owns one; use a separate lifecycle proof
for unchanged shared JS rather than making up a probe. Restore probe bytes and verify hashes.

For every warm sample record edit, actual visible/behavioral observation, browser reload and
process PID. Distinguish true hot reload, new component activation, browser reload, and full
server rebuild/restart. A smaller graph is not by itself a speedup. Keep original failed
attempts and orchestration delays. Do not repeatedly warm the baseline while timing a cold
candidate. Use current dotnetwatch MCP when available, otherwise the actual CLI and browser.

Production and sandbox use the same Calendar/Gantt/Task renderers and genuine shared assets.
Inspect source and independent published Parity/Fast. Include full Gantt gestures, interval
fields, invalid raw text, long labels, wrapped warning, real menus, modal footer/focus, scroll,
Mermaid strict preview, PNG and text download bytes, two independent panels and disposal.
Element existence is not actionability. Confirm a pointer gesture actually reached the shared
control and persisted the intended native effect in the production lane.

Keep shared fonts and assets under their original package; do not distribute font files in
this handoff. No app backend, production registrations or database merely to render a sandbox.
