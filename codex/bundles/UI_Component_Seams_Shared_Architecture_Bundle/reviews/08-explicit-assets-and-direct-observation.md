# Explicit sandbox assets and direct observation

Proven follow-up from CDA-UI-SEAMS-CATALOG-HARDEN-01, after its direct mode builds, browser acceptance and retained 27-cycle comparison. This does not rewrite reviews 05/06 or historical managed observation proof.

A development specimen may have a production-parity asset mode and a bounded fast mode, with explicit purposes and independently validated output. Make the actual compiled mode observable and reject contradictory configuration or missing assets. A fast mode must own its generated output and must not silently fall back to, or overwrite, production assets.

Audit the rendered source closure before choosing utility scan roots. A live sibling that already supplies compiled CSS need not be rescanned wholesale. Retain real fonts, icons, overlays, component isolation and representative interaction states; a smaller output is not by itself performance proof.

Measure the developer loop at the layer being claimed. Local direct source-flush-to-browser timing and an orchestrated observation loop answer different questions. Freeze process ownership, active mode, source patches, undo hashes, browser predicates and repetition rules. Separate SDK apply time, first visible change and confirmed final rendering when SDK browser reload can occur after an intermediate render. Retain startup prerequisites, failures, outliers and incomparable endpoints explicitly.

Use the same machine, SDK, browser, source mode and asset pipeline for comparisons. Classify hot updates, browser reloads, restarts and failures. A tiny sample with overlapping ranges supports only a narrow observation; do not infer broad improvement from project count or stylesheet size. Preserve negative evidence such as a hot-reload runtime crash even after a subsequent complete run.

These are evidence and ownership rules, not a mandate for these particular mode names, scripts or a universal sandbox framework.
