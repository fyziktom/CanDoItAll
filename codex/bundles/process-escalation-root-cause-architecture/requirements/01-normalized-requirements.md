# Normalized Requirements

## R01 Runtime Diagnostics

Blocked process runs must expose typed, durable diagnostics that explain why the step blocked, which source generated the diagnosis, and which action can recover it.

Success criteria:

- `NeedsManager` and `Blocked` outcomes preserve diagnostic code, category, safe summary, retry safety, idempotency, failed capability/tool/MCP when applicable, and source step/run ids.
- Runtime projection/API readback can show the actionable blocked reason without requiring direct database inspection.
- Unit tests prove that a blocked result with diagnostics is persisted and projected.

## R02 Artifact And Result Lineage

Process artifacts and strategy results must be traceable enough for manager fallback, read models, and evidence-source snapshots to find the primary evidence behind a blocked or completed step.

Success criteria:

- Result receipts or adjacent persisted records expose enough detail to locate the finalizer result and produced artifacts.
- Artifact ledger readback includes stable refs or resolvable artifact locations, not only ids and hashes.
- Missing artifact cases produce explicit diagnostics instead of generic manager escalation.

## R03 Capability Readiness Contract

Each process step must have a typed readiness contract for runtime tools, MCP tools, skills, skill suppressions, instruction fragments, allowed operations, required receipts, and browser/tool access.

Success criteria:

- Launch/readiness can detect missing or denied tools/MCPs/skills before dispatch.
- Readiness failures identify whether the problem is agent configuration, process scope, tool policy, MCP availability, or template contract.
- Management-only steps can suppress development skills/tools without changing the agent's global settings.

## R04 HR Matching And Preflight Surfacing

Role matching and launch preview must surface capability mismatches before the process run starts or before the affected step is dispatched.

Success criteria:

- The matching dialog/preflight can report which step requires which capability and whether the selected agent can receive it under current process scope.
- The result distinguishes hard blockers from warnings and optional context.
- Tests cover a matching pass where the agent has a development skill globally but the step suppresses it.

## R05 Driver-Owned Recovery

Manager fallback must be driven by typed failure categories and driver-owned recovery strategies, not by generic prompt heuristics.

Success criteria:

- Generic runtime defines domain-neutral failure categories.
- Domain drivers may provide recovery playbooks for their own steps.
- The dispatcher records which recovery strategy was chosen and why.
- No silent fallback marks a step completed without required proof.

## R06 Domain Isolation

Generic process runtime, dispatcher, projection, MAF common workspace tools, and generic process contracts must remain free of software-delivery-specific instructions.

Success criteria:

- Static tests or architecture tests reject .NET, Blazor, Calculator, Tetris, screenshot, or Playwright-specific logic in generic layers except where the generic layer names generic capability kinds.
- .NET delivery specifics live in domain templates, driver strategy projects, or module adapter composition.
- `WorkspaceImageAnalysisPromptNormalizer` remains domain-neutral.

## R07 .NET Delivery Driver Isolation

.NET solution setup, build/test/run proof, and UI/browser proof orchestration must be isolated behind .NET/software-delivery driver contracts and strategies.

Success criteria:

- .NET scaffold validation is testable without constructing the full process dispatcher.
- Required receipt definitions and repair plans are generated by typed driver policy, not copied across long prompt strings.
- The process still supports any app topic, not only Calculator, Tetris, or Blazor examples.

## R08 Template Hardening

Process templates must be reviewed and reduced where they encode brittle prose-only orchestration or fixture-specific assumptions.

Success criteria:

- Templates preserve domain-specific context only where the process owns that domain.
- Software-delivery templates do not force UI/browser proof for non-UI steps.
- Management-only steps do not receive development skill/tool context when suppressed.

## R09 Regression Suite

The final implementation must include characterization, unit, integration, and replay tests proving the root causes are fixed.

Success criteria:

- Tests cover the observed latest escalation shape.
- Tests cover missing MCP/tool, denied policy, missing artifact, instruction non-compliance, provider failure/timeout, and child-run blocker categories.
- Tests include a simple .NET development run, a non-UI software task, and a management-only step with dev skill suppression.
