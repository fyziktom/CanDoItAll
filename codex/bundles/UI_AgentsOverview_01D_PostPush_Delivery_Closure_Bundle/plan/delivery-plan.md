# Delivery plan

The owner authorizes A00-A06 sequentially before Governance G00-G03. Diagnostics preparation remains locked until Governance closure. No commits or history changes are authorized.

## Retention decision

Use allowed strategy 1: retain exact existing Overview and Governance proof. The entry inventory contains 101,041,872 Overview bytes and 428,144 Governance bytes across all bundle files. The historical commands, failing attempts, full measurement samples, compressed TRX, source inventories and inspected browser images remain available without reconstructing evidence. The largest uncompressed raw artifact is 30,714,773 bytes. This bounded approximately 96 MiB bundle is intentionally retained intact; file count is not an acceptance invariant. No new uncompressed execution logs will be retained. A failing-first clean-filter witness also requires every proposed manifest entry to survive Git clean filters byte-for-byte before it can pass.

Narrow ignore exceptions apply only to the two named proof roots. Exact historical and fresh retained evidence bytes use scoped -text attributes; this prevents silent Git newline conversion from invalidating historical hashes. New work uses retained/Axx, never generic ignored proof. Historical evidence is not relabeled as fresh execution. The entry inventory remains immutable; a separate final secret-scan receipt supplies its pending scan disposition.

## Validation

Fresh exact discovery precedes execution. The existing historical broad stable gate already covered the accepted navigation API. An actual correction to common DialogService semantics or a changed shared graph triggers a fresh broad stable checkpoint; extra lease tests alone do not. Overview measurements are invalidated only by changed measured renderer/assets/protocol, not by documentation, manifest tooling or the chat display-name correction.

The inherited 118 historical tracked-log documentation findings remain visible and prevent merge readiness. Phase A closure is explicitly proposed-byte delivery, never a claim that sibling changes are pushed. Components must be committed/pushed before primary, then the owner verifies actual tree manifests and clean layout.
