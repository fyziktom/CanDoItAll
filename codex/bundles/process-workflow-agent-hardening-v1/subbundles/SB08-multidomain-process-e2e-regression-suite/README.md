- Scenario upload/run harness.
- Five process run records or explicitly diagnosed blockers.

- Per-scenario usage/cost summary.

- Runtime host cleanup receipts.

## Dependency Impact

SB09 final closure depends on E2E proof. Any failure here reopens the earliest faulty critical subbundle.

## Validation Depth

Deep E2E validation. Must include real process runs, browser proof, usage ledger proof, host cleanup, and genericity audit.

## Implementation Steps

1. Create isolated project structures for each scenario.
2. Upload scenario input packet into project structure through canonical API/tool path.
3. Start the generic software-delivery/application process for each scenario.
4. Capture process run ids, execution run ids, artifacts, browser proof, usage summaries, and cleanup receipts.
5. Validate each produced app with domain-specific browser checks.
6. Run genericity audit for each scenario.
7. Compare evidence quality across scenarios.
8. If a scenario fails, classify as product defect, process defect, agent/skill defect, environment defect, or scenario defect and reopen the earliest affected subbundle.

## Scope Exceptions

If resource/time constraints prevent all five full E2Es in one pass, run Tetris plus at least two non-game domains and mark the remaining scenarios as blocking before final release. Do not mark SB08 complete with fewer than five unless the user explicitly accepts a reduced gate.

## Do Not Do

- Do not special-case Tetris.
- Do not inject hidden instructions outside scenario packets.
- Do not claim browser proof from page load only.
- Do not ignore usage/cost unknowns.
- Do not leave runtime hosts alive.
