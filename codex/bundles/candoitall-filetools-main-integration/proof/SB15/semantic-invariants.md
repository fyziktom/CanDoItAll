# SB15 Semantic Invariants

Date: 2026-07-13.

| Invariant | Required behavior | Positive evidence | Adversarial evidence |
| --- | --- | --- | --- |
| `SB15_INV_TRUTHFUL_CATALOG` | Project, filesystem, IPFS, and FTP groups are derived from current registered configuration and rendered even when empty. | Catalog unit test and real Browse catalog show current projects/filesystem plus explicit IPFS/FTP zero states. | Disabled and write-only storages are omitted; unsupported sources are not relabeled as supported. |
| `SB15_INV_CURRENT_BINDING` | Every storage binding re-resolves the current source and exact configuration fingerprint before driver access. | Current source returns one bounded root and reuses the resolved binding cache safely. | Missing/changed fingerprint returns Conflict before the driver registry is called. |
| `SB15_INV_CURRENT_PROMOTION_AUTHORITY` | Promotion reactivates the selected current occurrence and authorizes the current actor and exact View operation before persistence. | Ordered promotion test proves activate, context, authorize, save, publish, revoke. | Forged/stale/cross-actor/wrong-storage tests perform no persistence and no revision publication. |
| `SB15_INV_STABLE_PERSISTENCE` | Durable resource config contains only provider-neutral stable source/storage/locator metadata. | Strict connector round-trips filesystem, IPFS CID/MFS, and FTP configurations; EF writer persists and reloads the curated schema. | Unknown `Handle` field and invalid provider/locator combinations are rejected; general Resources save rejects the governed connector. |
| `SB15_INV_POST_COMMIT_REVISION` | A source revision is published only after a newly created resource save succeeds. | Success-order and PostgreSQL integration tests observe exactly one post-save revision. | Persistence failure and cancellation publish zero revisions; duplicate promotion is idempotent and keeps revision zero in the new runtime. |
| `SB15_INV_CURRENT_REOPEN` | Reopen parses strict stable config, resolves the current source, creates a new authorized occurrence session, and releases it independently. | Unit and PostgreSQL integration tests read current real bytes; browser duplicate/reopen shows actual content. | A missing current source fails before activation; no persisted browser workspace or old handle is accepted. |
| `SB15_INV_LIFECYCLE` | Temporary promotion and interaction authority is explicitly released on success, failure, cancellation, and disposal. | Ordered service tests and interaction disposal assert exact revoke/release behavior. | Cleanup failure cannot convert a failed persistence into success or mask a completed durable save; only failure type is logged. |
| `SB15_INV_BOUNDED_WORK` | Catalog, roots, browser search, content, and retained state have explicit bounds. | Projects cap at 512; one root; search 32/2,000/five seconds/concurrency one/200 matches/2 MiB; interaction 16 MiB; retention Disabled. | Over-count and stale binding fail explicitly; no unbounded browser/session retention or provider enumeration loop was introduced. |
| `SB15_INV_REDACTION` | Public errors and logs exclude raw locator/path, handle, token, actor, credentials, content, and provider exception details. | Typed UI errors, hashed stable display identity, and managed logs contain IDs/provider/revision plus hashed handle/actor only. | Unknown exceptions map to generic UI text; raw exception messages are not surfaced by the new pane/dialog. |
| `SB15_INV_UI_GOVERNANCE` | Registry editing cannot mutate governed storage identity; Browse is the sole promotion boundary and shared components own layout/overlays. | Real Registry proof shows read-only governed state and Browse Sources; dialog and two desktop layouts pass. | Editable connector list excludes storage-object; unsupported component parameters were caught in browser proof and removed before closure. |

These invariants apply to the final Resources catalog, binding, coordinator, connector, promotion writer/service, reopen service, Registry/Browse components, and their direct tests. Display names, browser keys, client capability flags, and old opaque handles are explicitly non-authoritative.
