## 2. Navigation and scope

Both surfaces host the same `ProviderRequestHistoryPanel`, in the existing AgentFramework module UI. A separate history UI package is unnecessary for these two consumers.

| Surface | Placement | Scope contract | Initial behavior |
| --- | --- | --- | --- |
| Provider detail | History immediately after Sharing in the current provider tab strip. | A typed single-provider scope containing the saved local provider ID. Show the provider identity as fixed context; do not expose an editable provider dropdown. | No history query, count, preview, payload, source-history lookup, or automatic search. A new unsaved provider shows “Save the provider before searching its history.” |
| Agents | Request history adjacent to Providers in the existing secondary tab list. Proposed route key: `AgentWorkspaceTabs.RequestHistory = "request-history"`, registered in `All` and parsed by the existing route-state code. | All authorized local and imported provider profiles in the current instance/database profile/security partition; optional provider filter narrows that scope. It never fetches another server's logs. | Same zero-history-load state. The page may load bounded non-history catalog/permission metadata needed to render controls, but not hidden historical counts or overview usage. |

The display scope is not an authorization grant. The service obtains the caller and active database/workspace context from trusted host state, intersects it with permitted provider scope, and applies that scope in the query. In a provider endpoint, a conflicting provider field in the body must be rejected; it must never widen the route provider ID. The same rule applies to detail and canonical-content retrieval.

For imported/shared profiles, the provider-specific tab searches the selected local profile ID and displays source identity separately. Renames, deleted catalog labels, aliases, matching model names, or a remote publication ID are not substitutes for local provider identity. Source-side invocation records and consumer-side requests must retain their distinct roles/cost semantics; the UI must not silently collapse rows because their labels match.

The all-provider tab does not reuse `ProviderUsageWorkloadSelection.Both`: that enum currently means Agents plus Simple Chats. History must represent the workloads supported by the history contracts, including workflows and externally relayed/untracked requests, without dropping them behind an unrelated selector.

## 3. Explicit search interaction

Use separate draft and applied query values. The draft initially shows the last 24 hours in the user's chosen display time zone; it is not executed. Central defaults are 50 rows, maximum page size 200, and maximum selected interval 31 days. Reject an out-of-bounds request server-side; do not silently clamp it. Any older retained 31-day interval can be searched: the interval limit is not a history-age cutoff. Read these values from central history options, not duplicated UI literals. No automatic summary-count request is part of rendering or Search.

| Input | Behavior and type |
| --- | --- |
| From / Until | Required finite range. Convert once to a half-open UTC interval at Search. Label the display time zone. Reject inverted ranges, invalid or ambiguous local times, and ranges exceeding the server limit with adjacent validation. Do not silently reinterpret dates. |
| Provider | Fixed for provider detail; optional typed ID for all-provider search. Use authorized catalog data already available to the shell, not `DISTINCT` scans over history before Search. |
| Model | Exact external model identifier, with requested/executed model semantics taken from the central query contract. Use ID-backed options where known; a bounded exact text field supports historical models no longer in the catalog. |
| Workload / outcome / pricing | Typed enums or typed option records. Include unknown/unpriced states explicitly. Never use UI labels as command values. |
| Client credential / subject | Managed API-token record ID and authenticated subject are separate filters. Two keys can have the same subject. Allow an exact ID without loading the entire token registry or exposing token administration to history readers. |
| Correlation | Bounded exact request/trace/correlation identifiers from the request contract. No wildcard payload search, raw SQL, or arbitrary expression strings. |

Only Search/Retry and deliberate paging may execute metadata queries. Filter changes, provider selection, tab activation, route hydration, row hover, dropdown opening, and component rendering do not query request history. Dynamic filter suggestions must use catalog metadata; if a later history-derived facet is desired, it is an explicit separately budgeted query after Search.

The controller owns these states: not requested, validating, loading, loaded, canceled, failed, and access denied. Do not represent all of them as an empty result list.

1. Search validates the draft, captures an immutable applied query and a new request generation, cancels the previous request, and starts one bounded query.
2. Only the current generation may commit rows, diagnostics, cursor, applied filters, or loading state. Compare request generation and scope identity as well as the cancellation token: a service that finishes after cancellation must not replace the current result.
3. Draft changes mark “Filters changed; Search to apply.” Existing results remain visibly associated with their applied range and timestamp. Paging always uses the applied query, never the partially edited draft.
4. Next/Previous use server-issued cursors with the original applied filters and stable descending `SortAtUtc, EntryId` sort order. Keep only a bounded cursor stack/current page; do not accumulate every row. Changing Search resets the cursor. An optional provider draft-filter edit does not fetch data or reinterpret the previous cursor: any deliberate paging still applies to the visibly labeled applied query. The result walk is live, not an immutable database snapshot; late backfill can change membership, and new matching rows before the current cursor require explicit Search/Refresh. Do not invent an insertion-fence guarantee or simulate unsupported sorting against the current page.
5. Cancel does not become an error. A failed query reports a safe actionable error and leaves the last successful metadata page visibly marked as previous results, if its authorization/scope is still current. It must not claim an empty successful search.
6. Host-provided single-provider identity, active database profile, workspace/security principal, or permission-version changes cancel in-flight queries, clear metadata/cursors, dispose detail state, and require a new explicit Search. This is distinct from editing an optional provider draft filter. The service must recheck trusted profile/security epoch and authorization revision before publishing metadata or content after an await; UI notification alone is insufficient. Unauthorized/stale data must not remain visible.
7. Component disposal cancels work and prevents late publication. Returning to the tab may preserve non-sensitive draft filters; the default design does not retain payloads or an unbounded cross-provider page cache.

Show explicit index coverage and retention diagnostics returned by the service: for example “History available since …”, “Content not captured”, or “Source unavailable”. An index gap is not “no requests”, and content retention is not a reason to remove still-retained metadata silently. The default 30-day metadata policy applies to standalone/direct and relay history. Canonical agent/chat/workflow projections follow their source owner's lifetime, including retained records older than 30 days; this feature does not change source transcript retention.

## 4. Result and detail contracts

The primary surface is a comparable request table, not another dashboard. Table rows contain only bounded summaries: indexed time (`SortAtUtc`) with `TimeBasis`, provider/model, workload/source, safe client attribution, outcome, duration, token usage, cost with pricing status, and a concise details action. Range filters use `SortAtUtc`; actual `StartedAtUtc` is nullable for legacy evidence and must not be fabricated. Stable `EntryId` identifies the row even when richer canonical evidence arrives. Show source/inbound/outbound context where necessary to prevent a relay and its canonical owner being mistaken for two billable requests. Do not expose request bodies, attachments, transcript JSON, exception dumps, or secret values in hidden DOM attributes or row tooltips.

Use the central request contract's typed pricing provenance. Preserve authoritative `ProviderReported` amounts/currency and distinguish them from configured-rate `Calculated` cost, `ExplicitFree`, `PartialEstimate`, missing tariff/usage, unsupported units, and `LegacyUnavailable`. A known zero cost, estimated cost, unknown pricing, and missing usage are different states. Do not render null as `$0.00`; do not recompute historical cost in Razor from today's price editor. The detail view can show the effective model, price snapshot/source, and reason the request was unpriced, when that evidence exists. Existing source-code display behavior is not proof of the deployed symptom's root cause.

Clicking Details performs a separate authorized metadata/detail request. Opening the dialog does not automatically fetch the conversation or every previous prompt. Its metadata section identifies the canonical owner, available content mode, provenance, usage, and sanitized failure information. “Open source” is available only when the owner is authorized and still exists; its typed owner reference is resolved to an allowlisted internal route, never treated as an arbitrary stored URL.

Detailed prompt/response content is a second explicit action after content authorization. The resolver retrieves canonical content when available and permitted; it does not copy it into another history record or make the UI join multiple repositories. For long canonical conversations, request one bounded message/segment page through the authorized owner reader and show its reference state. Do not assemble the complete conversation or repeat prior messages in every row. History-owned detail is different: a `PendingCanonical` owner never qualifies for fallback capture. Only reliably typed current-turn input and response are eligible, with defaults of 32 KiB UTF-8 each and 7-day retention, plus explicit omissions/redaction/truncation. It excludes prior conversation, system/tool/RAG expansions and binary media. Never select the last user message from an arbitrary relay transcript as a current-turn heuristic; an unsupported shape is metadata plus `UnsupportedDetailShape`. Light mode includes no private text excerpt. Distinguish not captured, retained only as metadata, expired/deleted, source inaccessible, and temporarily unavailable without leaking the existence of unauthorized owners.

Use encoded text for prompts, responses, subjects, model names, and failure summaries. No raw `MarkupString`, executable HTML, or automatic external-resource loading. User/LLM content must not become navigation or tool instructions. Raw bearer tokens, secret-vault values, authorization headers, cookies, and connection strings never enter a history DTO, tooltip, browser log, screenshot, or copy action. Copy/export of sensitive content is not implied by opening the metadata search and is outside this UI scope unless separately specified.

The metadata query service authorizes before reading and before returning results. UI hiding alone is not a control: Blazor Server callers can invoke application services without hitting the REST route. Every HTTP adapter, component facade, and canonical-content resolver must converge on the same service authorization rules.

Content authorization is conjunctive: history-content privilege, requested provider/workspace scope, and canonical owner access must all pass. A metadata reader may see permitted token counts and caller attribution without gaining access to the prompt, response, project files, or a private chat. Unknown owner permission cannot mean allowed. An owner resolver must return typed denied/unavailable/expired states and must not fall back to copied transcripts when access was denied.

Global capture/retention settings require a separate management privilege; a per-provider History tab does not become a configuration bypass. Revoked/deleted token records may leave a safe stable credential ID in retained metadata; label lookup failure must not erase the distinction between keys or require permission to manage tokens. Future EGCP may implement a richer identity/authorization adapter, but this bundle must work with present trusted subject/credential/context facts and must not add an IDM dependency to history storage.
