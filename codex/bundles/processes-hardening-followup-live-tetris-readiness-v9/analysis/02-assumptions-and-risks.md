# Assumptions And Risks

## Working Assumptions

- The repository already contains the Blazor app delivery process template and typed operation-contract infrastructure.
- The live demonstration topic is an input to a future run, not a reusable template requirement.
- A prepared-stage repair may update bundle files before production implementation begins.

## Critical Path Risks

- Topic-specific seed data can leak into reusable process instructions and narrow future delivery runs.
- A profile with pre-completed transitions or artifacts can create false confidence that agent execution works.
- A validation step with product mutation rights can accidentally repair code while pretending to validate.

## Validation Risks

- Source assertions that search only one folder can miss topic-specific guidance in `codex/skills` or generated process documentation.
- Passing tests can still be shallow if they only count scenarios instead of checking that live profiles have no seeded completion state.
- Browser readiness can be claimed without a real route, console, screenshot, and cleanup proof.

## Reopen Triggers

- Reopen SB02 if any reusable process template, reusable skill, or API example contains a topic-specific app name or acceptance criterion.
- Reopen SB03 if any Blazor template step gives mutation rights to validation, revalidation, writeback, or escalation.
- Reopen SB08 if agent assignment can proceed without required Blazor, browser, process, or project-structure tool readiness.
- Reopen SB14 if the runbook starts from seeded completed data instead of a fresh live profile.
