# Central relay and capability mapping

## Why this is a relay, not another agent runtime

The local CanDoItAll instance still owns:

- agent/system prompts;
- local conversation state;
- local tools and approvals;
- tool execution;
- project/session context;
- workflow orchestration.

The central instance owns:

- upstream credentials and endpoint;
- publication policy;
- protocol validation;
- route-to-provider resolution;
- upstream dispatch;
- usage/audit metadata;
- authorization and rate/size limits.

Therefore the central surface must relay function-tool definitions and return tool calls. It
must not instantiate local tools or run the client's workflow centrally.

## Central application flow

```text
HTTP endpoint
 -> auth policy
 -> access-context middleware
 -> bounded compatibility parser
 -> routing model resolver
 -> publication/eligibility/availability gate
 -> effective upstream target factory
 -> connector/operation relay adapter registry
 -> upstream HTTP or existing image capability
 -> safe response/error mapper
 -> metadata-only invocation record
```

## Adapter registry

Each adapter descriptor declares:

- supported connector plugin keys;
- supported operations;
- supported OpenAI surface(s);
- streaming mode;
- function tools;
- structured output;
- vision;
- image response modes;
- maximum request/output constraints;
- whether usage can be extracted;
- health/eligibility predicate.

Expected v1 adapters:

### OpenAI-compatible upstream adapter

For `provider.openai` and any current explicitly compatible profile:

- normalizes configured root;
- applies bearer secret centrally;
- maps public model to upstream model;
- sends `ResponseHeadersRead`;
- validates and forwards only supported fields;
- streams safe headers/body;
- extracts terminal usage when present.

### Ollama OpenAI adapter

For local/remote Ollama connector keys:

- uses Ollama's tested OpenAI-compatible Chat Completions and/or Responses endpoints;
- advertises only the operations confirmed by contract tests against the deterministic fixture
  and, optionally, a separate environment test;
- does not assume every OpenAI field is honored;
- preserves function-tool and structured-output behavior only when proven.

### ComfyUI image adapter

For `provider.comfyui`:

- accepts the bounded OpenAI image request subset;
- invokes the existing ComfyUI image capability through a narrow adapter, not a duplicate
  workflow implementation;
- maps generated bytes to `b64_json` or an authorized artifact URL;
- preserves revised prompt only when the public response contract supports it;
- enforces image count, size, format, and byte limits.

### Test adapters

Scenario/process/deterministic adapters may exist in test composition but are excluded from
production publication eligibility and catalogs.

## Capability intersection

Advertised capability is the intersection of:

1. profile purpose and configured model;
2. connector manifest and current provider capability;
3. relay adapter descriptor;
4. compatibility policy;
5. source network/security policy;
6. successfully proven contract tests.

User-editable support flags alone are not authoritative.

## Request field policy

Use a surface-specific policy object/validator, not endpoint inline conditionals. It must
produce a normalized request plus typed validation errors.

Unknown JSON members should be rejected or deliberately captured and validated. Do not add
`JsonExtensionData` that is then forwarded without inspection.

Function tools must be restricted to client-executed function definitions. Hosted/built-in
tool discriminator values fail.

## Streaming

Requirements:

- `HttpCompletionOption.ResponseHeadersRead`;
- no full-response buffering;
- bounded incremental event parser only where usage/error extraction is needed;
- exact `text/event-stream` semantics;
- downstream flush;
- cancellation from `HttpContext.RequestAborted`;
- upstream response disposed on disconnect;
- streaming idle timeout;
- safe header allowlist;
- terminal usage is recorded when available;
- missing usage records `UsageUnavailable`, not zero.

## Header policy

Inbound caller headers are not copied wholesale. Explicitly handle:

- Authorization: consumed by central only;
- `CanDoItAll-Access-Context-Ref`: audit/correlation only, never upstream;
- trace context: normal diagnostics propagation;
- content type/accept;
- idempotency header only if explicitly supported;
- no cookie, forwarded auth, arbitrary organization/project header, or caller host.

Outbound upstream headers are adapter-owned. Upstream response headers are allowlisted
(content type, safe request ID, retry-after, selected rate metadata if approved). Strip
set-cookie, location, auth challenges containing details, server internals, and private URLs.

## Usage and audit

At dispatch create one invocation record with metadata only. On completion/cancel/failure,
finalize it atomically/idempotently.

Extract provider usage from:

- normal Chat/Responses JSON;
- terminal streaming usage/event where available;
- image pricing metadata if current provider pricing supports it.

Use existing pricing normalization and usage completeness concepts. If existing usage
contracts cannot truthfully classify relay traffic, add a dedicated `SharedProviderRelay`
workload/consumer through the existing usage project and update its selection/UI semantics.
Do not label it Agent or SimpleChat without evidence.

## Caching

Cache public route resolution by catalog/publication revision. Invalidate on provider profile
commit, publication change, or source identity change. Cache entries contain no secret value.
Secret resolution occurs through the existing runtime resolver with its current lifecycle.
