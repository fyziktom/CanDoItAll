# Bounded recovery decisions

Registry/UI/API mutation receipts identify operation, candidate/target ID, immutable request fingerprint, expected revision and intended persisted revision where EF makes it available. Known-commit outcome remains distinct. Canonical verification uses AppDbContext directly, never runtime/catalog cache and never Save/Delete. Exact attempted revision proves update; unchanged expected revision proves no update; intervening revisions remain unknown. Deletion absence proves desired authoritative outcome, unchanged pre-revision proves no deletion; absent update cannot be classified as successful. Reads failing or returning unrelated identity remain unknown.

New provider submissions allocate a candidate before awaiting. The draft ID stays null until known commit. Create-only expected-absence protection prevents late/retried creates overwriting an already existing candidate. Controlled retry retains the original candidate and submission. Scoped unresolved state survives target/component recreation; incomplete New attempts remain discoverable and block another blind New write. No global service bag or outbox.

Shared target recovery holds an operation descriptor and rereads GetProfileSharingAsync with identity/token/generation checks. A successful authoritative snapshot permits safe continuation with current concurrency tokens, without asserting unprovable historical causation. Source recovery compares exact stable ID, prior revision and intended postcondition. A first source request has its ID before persistence; create under that ID is serialized and rejects a conflicting request. Name/list position are never identity. Unknown or superseded evidence remains blocked with explicit verification path. Typed callbacks for discovered commits are consumed once per attempt.

Product limits: scoped receipts survive navigation/overlay recreation in the owning circuit, not server restart. API returns a sanitized receipt so callers can retain it independently. No durable operation journal is introduced. Historical update causation cannot be reconstructed after another revision supersedes it; remain explicit unknown. Canonical absence allows only identity-preserving controlled retry, protecting against delayed first commits.

UI reuses current large-desktop editor and dialog composition, Alert/Button feedback and existing scroll owners. No extra page, modal stack, visual redesign or secret value storage. Ownership enforcement, source materialization, lazy runtime revision verification and catalog invalidation remain intact. No new project reference or partial-class expansion is permitted in 02D.

Architecture alternatives rejected: clearing Boolean after arbitrary list reload (unsafe); always replaying write (duplicates/effects); persistent general mutation/outbox framework (unnecessary for bounded identity-preserving recovery); read through runtime cache (not authoritative). One canonical read boundary and narrowly scoped recovery state have direct test seams.
