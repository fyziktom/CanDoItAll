### Preserve first; prefer a logical dump and restore

Prefer a one-off logical database dump and restore into a **separate PostgreSQL 18 cluster**. Missing local client executables can often be solved with the verified PostgreSQL 18 distribution or an appropriately connected disposable client container; do not immediately fall back to reconstructing data entity by entity. Use an explicit target-version toolchain, not whichever `pg_dump` is first on PATH.

Quiesce the application's writers and background work before the final database dump and corresponding filesystem backup. Stop only verified owned processes; keep the source database available for the dump. Disable automatic relaunch by the identified development supervisor during the cutover. Capture matching workspace, control-plane, local state, vault, Data Protection material, credentials/configuration, and recovery metadata using access-controlled local storage outside tracked repository content. Preserve the user/host/key context needed to decrypt the existing state. Do not replace vault keys or host-binding identities during the engine upgrade.

Write custom-format backups to files and check each native exit status. On Windows avoid routing the binary dump through PowerShell text pipelines/redirection; use `pg_dump -f` or an in-container file followed by `docker cp`. Compute integrity hashes. `pg_restore --list` is useful inspection, **not** proof of restorability: perform a real restore. A stopped copy of database files may be extra recovery material, but an arbitrary copy of a running data directory is not the logical backup.

Provision the target under an unambiguous separate data directory/volume and temporary database endpoint as needed. Prove separation using effective server/cluster/database identity and actual backing resources; different profile GUIDs or different aliases for the same server/database are not sufficient. Keep the old cluster unchanged and recoverable. Create only required roles and permissions deliberately; account for ownership, grants, extensions, database settings, and collation. A single-database dump does not replace the cluster role inventory. Do not blindly restore all global superuser definitions over unrelated databases, and do not use `Ensure-DevelopmentPostgres.ps1` to rotate existing source credentials.

Restore the complete dump into an empty, isolated target with errors treated as failures. Preserve source identifiers, relationships, historical rows, schema history, and sequence state. Do not bootstrap or seed an application into that target before a full schema/data restore. Resolve missing roles/extensions rather than ignoring restore errors. Validate restored data against the baseline **before** application startup, seeders, scheduled work, or intentional new EF migrations change it. Document and verify any legitimate schema transformations separately. Use suitable post-restore statistics maintenance and representative query checks.

The preferred logical route does not need a checksum-mode matching workflow. Do not introduce `pg_upgrade` complexity just because the target enables checksums by default. If facts on the workstation make `pg_upgrade` clearly preferable, use its official compatibility check, matching prerequisites and separate recovery copy; do not use an unprotected in-place or hard-link shortcut that destroys the fallback.
