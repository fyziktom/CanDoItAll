## Mandatory workstation preservation proof

The real 5032 migration is not interchangeable with the disposable tests above. Its evidence must connect the source app to the actual source database, prove a coherent restorable database/files/keys backup, prove the separate target, reconcile retained data before seed/schema changes, activate the effective target and repeat known-record/file checks after restarting the app.

Compare all populated source tables, identifiers/relationships, schema history, sequences, grants/extensions and representative full records. Include provider configuration/sharing/historical prices, long journals/opaque envelopes, conversations/operation state, API access data and external files when present. Unsupported legacy categories cannot silently disappear. Counts alone are insufficient; document deterministic values and expected operational changes without exposing payloads/secrets. Do not require bit-for-bit equality of PostgreSQL storage pages or different logical-archive encodings.

If API fallback is necessary, establish route/auth/TLS behavior and a complete preservation-coverage matrix first. Verify the source and target are physically distinct even if profile GUIDs differ. Check every handler result and authoritative target read-back; record partial completion/retry behavior and retain unsupported sharing guards. Keep an incomplete target unselected. Read-only projection endpoints, public catalog fields and HTTP 200 alone cannot prove completeness.
