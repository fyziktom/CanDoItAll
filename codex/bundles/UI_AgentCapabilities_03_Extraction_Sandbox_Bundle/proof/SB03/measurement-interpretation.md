# Accepted measurement interpretation

The complete repeat passes: 216 accepted warm observations across four configurations (27 forward and 27 reverse each), plus three process-cold starts per host. Three distinct edits each for Razor, C# and CSS were frozen before movement. Every source target is restored. The generated Fast theme needed one normal regeneration after watcher shutdown; it then matched the exact frozen hash. No application/test build competed with timing.

The strongest observed development-loop benefit is the sandbox: cold medians are 15.287 s Parity and 14.952 s Fast versus 57.959 s pre-move and 58.628 s post-move full app. Forward CSS medians are 402.7 ms / 409.0 ms in the sandbox versus 3780.2 ms pre and 3622.1 ms post full app. The fixture and real rendering assets are matched; database/bootstrap/runtime work is deliberately absent from the sandbox.

Do not infer a universal improvement from extraction. Post-full-app forward Razor median is 926.8 ms versus 592.4 ms before; Parity 454.4 ms and Fast 498.7 ms. C# medians are 139.7 ms pre, 103.0 ms post, 87.1 ms Parity and 148.5 ms Fast. Fast does not consistently beat Parity. The warmed C# path was already quick. The pre Razor 9.483 s and post reverse CSS 11.085 s outliers remain in the ranges; they are not deleted.

For every host, all 36 Razor/C# forward/reverse observations advance the managed hot-reload generation and receive SDK RefreshBrowser/enhanced-navigation events. Document identity/time origin and runtime process remain unchanged. The coarse `browser-reload` label therefore means managed update plus enhanced browser navigation here, not full-document replacement. All 18 CSS observations per host use UpdateStaticFile with unchanged managed generation, document and runtime. Fast has one additional duplicate static-file message in its forward series, without an extra semantic observation. No process restart, rude edit, unsupported edit or failed observation occurs in the accepted sample set. This does not prove arbitrary edits are supported.

First-visible time is measured from flushed source bytes to the actual DOM/computed-style predicate. Settled time includes the fixed 1.5-second minimum and quiet window. Both distributions, including per-edit results and all reverse rows, are retained in measurement-comparison.json and measurement-samples.csv. Calibration, initial asset generation and fixture seeding are outside the warm samples; process-cold means a new process with populated restore/filesystem caches, not clean-install startup.

Limitations: one machine/SDK/browser/power configuration, sequential non-randomized runs several hours apart, small supported edit set, real live sibling revisions and their precompiled asset pipeline. Absolute times and spreads are evidence for this environment, not a promised percentage for every developer machine. Parity and Fast pipelines are explicit factors. No managed watch service or manual browser refresh substitutes for direct SDK watch.

Negative evidence remains: invalid early cold readiness protocol attempts; the interrupted pre-move warm run with 43 completed observations; all setup/selector/fixture errors; the first complete post-extraction series (162 warm observations) excluded because sandbox responsive assets were incomplete; both direct responsive browser failures before the unlayered compatibility fix. The repeat reuses unchanged timing code and probe definitions. The valid pre-extraction baseline was captured before any physical source movement.
