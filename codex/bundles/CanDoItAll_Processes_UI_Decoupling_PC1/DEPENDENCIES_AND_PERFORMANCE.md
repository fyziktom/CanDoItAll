# Dependency, asset and performance closure

Evaluate the actual app/sibling configuration at entry. No old Components/FileTools SHA, branch match or package version in a historical bundle is an execution pin. The new project graph should remove the native Process module/application/runtime/persistence/agent-host graph from **independent UI development**, while the production host keeps the native integration it needs.

## Allow the right light graph

P11/P19–P21 show a potentially reusable neutral graph: Projections → Contracts/Abstractions/Core; Core → Contracts/Abstractions; Abstractions → Contracts; Contracts → SharedKernel. Read public types/effects and evaluated targets before deciding it is suitable. Do not ban pure Core merely by name, and do not assume “Projections” guarantees neutrality. A narrow extraction is warranted only when a specific unsuitable public/evaluated edge exists.

Inspect the actual shared conversation/AppComponents/FileTools/Charts/Canvas/overlay closure, including dynamic children. New UI must not reference the old Process module, Application, Runtime, Persistence, Web/composition or a service bag. Relevant unresolved references invalidate closure proof. Negative guard tests intentionally introduce a forbidden transitive edge and a missing relevant assembly. Check actual resolved assets, not just a text grep or an `[Inject]` count.

## Performance hazards to avoid

Do not clone the full ProcessWorkspaceShellProjection on every render, requery history from each mounted tab, evaluate authorization repeatedly inside row rendering, restart polling per child or hold unlimited retired drafts/sessions. Build bounded view data once per accepted relevant revision and reuse stable immutable data where appropriate. Keep raw draft state separate from accepted projections. No additional network hop or forced serialization through HTTP is necessary for the existing in-process UI client.

Preserve current lazy read options, event paging and history windows. Measure query/dispatch counts in semantic controls and watch for allocation/retention regressions under large bounded data and repeated open/close. A test should prove behavior/lifecycle first; do not invent machine-independent tiny timing ceilings or weaken native query limits to make the UI faster.

## Assets and delivered candidate

Update scoped CSS, JS imports, Tailwind source patterns, namespaces, `_content` URLs and route/render registration. Reuse current asset-generation scripts and modes after inspecting them; do not invent an MSBuild property from an old module. New sandbox-only projects should not acquire irrelevant template copying or production startup merely to obtain theme assets. A content-only production CSS link can be legitimate; a Web project reference for styling is not.

Record app and consumed sibling commits, relevant dirty deltas, source/package mode, asset mode, SDK, configuration and published output provenance. Verify source and clean published startup/real content. A later asset or source change invalidates dependent browser/measurement evidence until rerun.

## Measurement record

Compare a representative native Processes Web state before/after and the equivalent full sandbox. Record evaluated recursive references, resolved runtime/native assets, watch list and actual rebuilt projects. Measure cold startup plus repeated warm save-to-visible samples for Razor, C# presentation, scoped CSS and relevant JS. Distinguish hot reload, browser refresh, restart and missed update; record actual sample counts and ranges.

Report measured benefit, no benefit, regression or not measured. Do not claim that extracting an RCL alone accelerates full Web watch or choose a target percentage before observing the graph. Keep builds/processes/output paths task-owned and restore only temporary edits you own. Use the shared development-loop guidance for Fast/Parity and source/package distinctions.
