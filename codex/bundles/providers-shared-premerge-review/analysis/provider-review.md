## Findings

### SP-01 — P1 — Successful buffered Responses envelopes are rejected

- Location: `src/Integration/CanDoItAll.SharedProviders.Http/SharedProviderHttpRelayClient.cs:313-316`, `SharedProviderRelayResponsePolicy.RewriteBuffered`.
- Scenario: upstream `/responses` returns HTTP 200 with an ordinary completed response containing `"error": null`. The unconditional `TryGetProperty("error", out _)` rejects it, `DispatchAsync` catches the resulting `InvalidDataException`, and the public endpoint returns 502 `shared_provider_upstream_response_invalid`. Every successful envelope with the nullable error member takes this path.
- Evidence: official [Responses retrieve contract](https://developers.openai.com/api/reference/cli/resources/responses/methods/retrieve) includes the nullable error member; the production relay driver forwards the original HTTP response. Existing fake response at `tests/Integration/CanDoItAll.Tests.Integration/SharedProviderOpenAiCompatibilityIntegrationTests.cs:1909` omits the error member and therefore misses this.
- Minimal repair: reject a non-null error value, then validate operation-specific completion/error state explicitly; accept a completed Responses envelope with `error:null`. Do not loosen error-envelope rejection generally.
- Regression: extend `SharedProviderOpenAiCompatibilityIntegrationTests` with a realistic full successful Responses envelope containing `error:null`, plus non-null error/failed status cases; assert the public endpoint returns the correctly rewritten model, successful audit, and usage. Filter: `FullyQualifiedName~SharedProviderOpenAiCompatibilityIntegrationTests`.

### SP-02 — P2 — Loopback sources accepted by discovery cannot execute with the default network policy

- Location: `src/App/CanDoItAll.Composition/SharedProviderRuntimeHttpClientSelector.cs:57-61`.
- Scenario: create and synchronize `http://localhost:5100/` or `http://127.0.0.1:5100/` with `AllowInsecurePrivateNetwork=false`. `SharedProviderSourceUriPolicy.Normalize` intentionally accepts HTTP loopback under `PublicOnly` (`:66-76`; existing unit coverage `SharedProviderSourceUriPolicyTests.cs:81-93`). Catalog fetching selects the bounded private HTTP handler by scheme. Materialization and `SharedProviderProfileMapper` preserve `PublicOnly`. The runtime selector then throws because all HTTP requires `AllowPrivateNetwork`, so a source that tests and imports successfully cannot run.
- Minimal repair: align runtime destination classification with the canonical source policy, permitting only its explicit loopback exception under `PublicOnly` while retaining DNS/address restrictions and rejecting non-loopback private/public HTTP without approval. Avoid globally granting private-network access.
- Regression: carry a real imported graph through materializer, mapper, HTTP selector, and fake transport using localhost, IPv4 loopback and IPv6 loopback without the private-network checkbox; non-loopback HTTP must stay rejected. Filters: `FullyQualifiedName~SharedProviderRuntimeProjectionIntegrationTests|FullyQualifiedName~SharedProviderSourceUriPolicyTests`.

### SP-03 — P2 — Large upstream errors lose rate-limit/timeout classification

- Location: `src/Integration/CanDoItAll.SharedProviders.Http/SharedProviderHttpRelayClient.cs:50-61` and `:133-140`.
- Scenario: upstream returns HTTP 429 with `Retry-After: 30` and a 513-byte or larger error body (512 is `SharedProviderFailure.MaximumMessageLength`). `ReadBoundedAsync` throws instead of taking a bounded diagnostic prefix; the generic invalid-response catch converts this into 502 and discards Retry-After. The same issue converts upstream 408/504 into 502. Status-only mapping never executes, even though the mapper explicitly does not use the raw error body for public disclosure.
- Minimal repair: determine failure category and Retry-After from status/headers independently of optional body diagnostics; read only a bounded diagnostic prefix or discard diagnostics after the limit. Preserve caller cancellation. Never log/disclose raw provider error bodies.
- Regression: fake upstream 429/504 with oversized Content-Length and chunked oversized content; assert bounded reading and preservation of category, status, Retry-After, and sanitized message. Filter: `FullyQualifiedName~SharedProviderOpenAiCompatibilityIntegrationTests`.

### SP-04 — P1 — Streaming failures become a clean HTTP 200 end-of-stream

- Location: `src/Integration/CanDoItAll.SharedProviders.Http/SharedProviderSseRelayStream.cs:174-181`; `src/App/CanDoItAll.Web/Api/SharedProviderInferenceApi.cs:277-285` and `:290-297`.
- Scenario: upstream emits text deltas and then `response.failed`/`response.incomplete`, times out, produces malformed SSE, or drops its connection. The SSE reader records failure privately and suppresses the failed terminal frame; the HTTP endpoint only logs the completion failure (and catches enumeration failures) before returning normally. The downstream sees HTTP 200 and an orderly EOF with partial text and no failure event. The server-side `Completion` task is inaccessible to an external client, so it is not an error contract.
- Evidence: `SharedProviderStreamingIntegrationTests.Responses_terminal_event_completes_without_chat_done_marker` explicitly expects zero forwarded frames for failed/incomplete events (`:38`); `PostHeaderIdleTimeout_KeepsSseStatusAndFailsCompletion` asserts HTTP 200 and no error body while consulting the private relay completion (`:253-259`). Those tests verify internal accounting but do not establish a client-visible failure.
- Minimal repair: after headers, send a sanitized operation-appropriate protocol failure event or abort the downstream HTTP response when a failure cannot be represented safely. Do not forward raw provider errors, fabricate success, or emit a success terminal marker. Ensure the actual OpenAI client observes failure and the invocation history retains the same outcome.
- Regression: use actual .NET OpenAI Chat/Responses streaming clients against the public endpoint with partial text followed by failed/incomplete event, idle timeout, invalid frame, and upstream disconnect; clients must not finish successfully. Keep disposal/cancellation and audit assertions. Filter: `FullyQualifiedName~SharedProviderStreamingIntegrationTests`.

## Additional risks requiring focused proof

- Responses stateless replay accepts assistant message fields only `role/content/type` at `SharedProviderRelayRequestPolicy.cs:656`. A caller replaying native `response.output` message objects (including their `id`/`status`, and potentially `logprobs`) is rejected even though those objects were just returned through this relay. The existing real-client wire test constructs a fresh `ChatMessage` instead of round-tripping returned output. Confirm the supported external contract before widening its allowlist; add a real native Responses output replay test.
- Catalog route resolution loads and evaluates every published profile before checking the cache (`SharedProviderCatalogQueryService.cs:53-85`), so cache hits still perform database materialization, model parsing, and eligibility work for the entire catalog on each inference request. Quantify with allocation/query baselines; preserve current persisted target revalidation when improving the lookup.
- Extension ownership still needs consolidation: `SharedProviderHttpRelayClient.CreateRuntimeRequest` and `SharedProviderRelayUriPolicy` contain connector-name switches despite the relay adapter registry. Adding connectors can require coordinated edits in registry, transport mapper and URI policy. This is an architecture risk rather than a demonstrated runtime bug; do not extract extra projects without evidence of a useful owner boundary.

### H02 - P2 - Known provider timeouts are recorded as cancellation or generic failure

- Location: `src/MAF/Common/CanDoItAll.AgentFramework.Maf/Runtime/History/ProviderHistoryObservation.cs:30-32`; related `HistoryStreamingChatDriver.cs:31-33` and `ProviderHistoryChatClient.cs:33-37`.
- Scenario with an explicit timeout source: typed `OpenAiProviderDriver.CompleteChatAsync` performs `HttpClient.PostAsJsonAsync` (`OpenAiProviderDriver.cs:150-155`). Production `MafProviderDriverHttpClientPool` configures a ten-minute `HttpClient.Timeout` (`MafProviderRuntimeGateway.cs:333-338`). If that timeout elapses while the caller's token remains active, modern .NET emits an `OperationCanceledException`/`TaskCanceledException` with an inner `TimeoutException`. `ProviderHistoryObservation` unconditionally persists `Cancelled`. The actual operation outcome cannot be distinguished from a user cancellation in history, although `HistoryOutcome.TimedOut` exists. The streaming typed driver has the same unconditional cancellation branch. On SDK paths, `MafProviderTransportBoundaryChatClient` wraps non-caller timeout exceptions, which the history decorator instead records as generic `Failed`.
- Minimal repair: define one small typed outcome classifier that recognizes explicit timeout causes/deadlines (including the documented HttpClient timeout exception shape and known runtime timeout wrappers), separately recognizes actual caller cancellation, and preserves already-observed terminal evidence. Do not classify every OCE with an uncancelled token as a timeout; unknown cancellation sources remain explicit/unknown or failed according to the chosen contract.
- Regression: driver/SDK wrapper fakes produce (a) the explicit HttpClient timeout exception shape with an active caller token, (b) an actually cancelled caller token, (c) unrelated OCE without timeout evidence, and (d) a timeout after terminal evidence. Assert `TimedOut` only in (a), caller `Cancelled` in (b), and no evidence downgrade in (d). Add a fast HttpClient fake-handler deadline integration test to prove the actual .NET exception shape. Filters: `FullyQualifiedName~ProviderHistoryCaptureTests|FullyQualifiedName~ProviderHistoryLifecycleTests`.

The quoted JSON key redaction miss is within the declared credential-pattern allowlist (`provider-request-history/architecture/09-search-security-contract.md:127`), not a demand for universal DLP. Extracting the production regex and applying it to synthetic `api_key=fixture-secret` redacts it; the same named key quoted as JSON does not redact.

A claimed stale-recovery overwrite should be omitted: `HistoryEntryRow` is an EF concurrency-token entity, and `AppDbContext` stamps modified rows, so a stale recovery update conflicts rather than silently overwriting a committed completion. SDK-internal physical retries are explicitly outside the amended capture contract (`architecture/11-capture-implementation-decisions.md:16-18`); keep the application-visible-attempt limitation clear in user-facing documentation rather than treating those retries alone as unfinished implementation.

Primary-source checks: [HttpClient.SendAsync documentation](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclient.sendasync?view=net-10.0) documents timeout as OperationCanceledException with inner TimeoutException on .NET 5+. The [official OpenAI SDK AsyncSseUpdateCollection](https://github.com/openai/openai-dotnet/blob/main/OpenAI/src/Utility/AsyncSseUpdateCollection.cs) returns false when its SSE enumerator ends as well as on a DONE marker, without requiring a terminal event. This supports SP-04's external SDK failure mode; the regression should pin the repository's package version rather than rely on main remaining unchanged.
