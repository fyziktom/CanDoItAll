# Current State

## Canonical Data And Existing Projections

- Runtime state, steps, claims, receipts, plans, and assignments are canonical in Processes Runtime/Persistence.
- Agent Framework execution and usage evidence is retained in the sandbox workspace store.
- `IProcessProjectionStore` stores generic JSON payloads. `ProcessRunDetailProjection` is thin and lacks durable usage/attempt/actor aggregates.
- Runtime events retain envelope metadata and payload hashes, not enough payload to reconstruct every historic fact.
- The existing project-structure contributor rebuilds terminal summaries from runtime state, plans, assignments, and grouped step statistics on each projection.

## Pass 1: Initial Performance Review

1. `ProcessesApi` synchronously calls projection catch-up on live/detail/history GETs. Catch-up is globally serialized and replays at most 500 events before serving a read.
2. Projection replay performs approximately five snapshot/history saves plus an offset save per event.
3. Live history loads up to 500 generic JSON snapshots, hydrates metadata/state/actions/child waits/diagnostics sequentially, and applies the requested limit last.
4. One state hydrate is an EF split query over five collections, so per-run enrichment is several SQL commands plus JSON materialization.
5. Workspace loading serially requests live, selected detail, paged history, up to 10,000 metric events, and active agents. The same state/assignment can be loaded through separate caches.
6. Graphs and Analytics derive aggregates from raw history and Agent Framework usage every load.
7. The execution-observation reader can list all execution summaries once per run and per step, then load full details sequentially.
8. The usage reader lists broad history and then hydrates every execution detail sequentially.
9. Direct `Task.WhenAll` is unsafe on the shared scoped EF context; projection-shaped batch queries or independent contexts are the correct concurrency boundary.

## Post-Change Performance Review

### Pass 1: Changed Hot Paths

1. Ordinary Processes GET routes no longer invoke globally serialized projection catch-up. `ProcessRuntimeProjectionReplayBackgroundWorker` advances the projection outside request latency.
2. Terminal events seed a dedicated `process_run_records` row. Facts and narrative are completed independently by a leased background batch processor, so runtime completion and historical reads never wait for an LLM.
3. Compact list queries select indexed scalar summary columns only. Full summary payloads hydrate participant IDs and narrative only after bounded keyset selection; hard-fact JSON is loaded only for one selected record.
4. Assembly batches runtime state, plan, assignment, hierarchy, execution-observation, usage, and event evidence. Runtime events are scanned once per bounded subtree instead of once per step.
5. Execution-observation headers are filtered by typed run/step ID sets. Summary reads issue zero execution-detail calls; explicit full reads remain sequential and bounded because the workspace store has no batch-detail contract.
6. Usage reads filter execution headers by typed run IDs, over-read by one to detect truncation, and use workflow-store exact totals. A capped source marks evidence incomplete instead of silently publishing an exact-looking total.
7. Dashboard enrichment loads exact projection keys in one batch and uses compact records as the terminal fallback. Terminal workspace, project-structure, and historical-cost consumers use durable records; active/deep operational views retain canonical reads.
8. Shared scoped EF operations remain sequential. Independent project, record, and factory-created contexts may overlap; no `Task.WhenAll` was added over one scoped `DbContext`.
9. Backfill seeds are revalidated against the current runtime status and latest terminal/reactivation sequence inside the guarded persistence mutation. A stale seed captured before reactivation is rejected even when no prior run-record row existed.
10. Same-source manager-narrative lookup and reservation are atomic under the file workspace's cross-process lock. Two workers with the same stale preflight view create one execution; the other observes active work and defers without consuming another record-stage attempt.
11. Analytics reports source-derived `DataThroughUtc` and `SourceGlobalSequenceWatermark`. Worker claims and narrative maintenance may advance `RecordUpdatedAtUtc`, but they do not masquerade as newer source evidence.
12. Durable project-node paging, adaptation, and rendering were extracted behind `IProcessRunRecordReader`; Workbench no longer depends on the broad mutable run-record store.

### Baseline Versus Final Deterministic I/O Budgets

| Surface | Baseline | Final deterministic budget/proof |
| --- | --- | --- |
| Durable history list/API | Foreground replay plus broad generic snapshot reads and possible per-run enrichment | One bounded keyset record query; zero runtime-state, assignment, event-detail, or Agent Framework detail reads per row. |
| Selected summary/graph/analytics | Rebuilt from canonical history and usage on demand | One selected record for summary/graph; one DB aggregate query for analytics; facts and minute buckets are independently paged in the response. |
| Dashboard recent activity | Prefix scan of up to 500 projections and repeated enrichment | One canonical activity query, one exact-key projection batch, and at most one compact record batch; no per-row record GET. |
| Terminal workspace | State/assignment/history/usage reconstruction even when a terminal record existed | Durable summary and stored event aggregates; tests prove an incomplete terminal record is not rebuilt through usage/deep history. |
| Project-structure terminal nodes | Runtime state, plan, step, and assignment reconstruction | Full summaries page by indexed project/root query with a hard cap of 1,000; record-covered runs bypass canonical detail and remain visible after runtime rows are purged. |
| Execution evidence | Broad header scan followed by sequential detail hydration | One typed batched header query; summary mode has zero detail calls; explicit full mode is bounded and reports incomplete evidence when capped or missing. |
| Usage evidence | Broad execution history and detail hydration | Typed run-ID header filter, bounded `take + 1` detection, workflow exact-total page, and explicit incomplete status at every cap boundary. |

These are logical-I/O and call-count claims, not percentage speedup claims. Production latency and query plans still require measurement against representative PostgreSQL and workspace data.
