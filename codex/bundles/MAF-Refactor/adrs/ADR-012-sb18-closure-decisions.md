# ADR-012: SB18 closure decisions (deferred CP4 reviews + retained legacy reader)

## Status

Accepted for this bundle. Closes the "metadata-split owner" / "reviewed at CP4" markers left open by SB13, SB14, and SB15.

## Decision

Four items deferred to the release gate are decided as follows; none require a code change.

1. **Governed-intent grant location stays in generic Core.** `CreateRuntimeContextIntent` and the `ExecutionInvocationMetadata.IsTrustedGovernedProcessRun` AND-logic remain in `CanDoItAll.AgentFramework.Core` (`Execution/AgentFrameworkWorkspaceExecutionService.ExecutionRuns.cs`, `Execution/ExecutionInvocationMetadata.cs`). Capability grants that widen tool/mutation authority must be centrally auditable in one place that every module composes through; a module-supplied policy is allowed to *narrow* what Core already permits (see `IAgentExecutionProviderSelectionPolicy` / `IAgentExecutionRunCriticalityPolicy`, SB13) but must never itself be the sole authority that *elevates* trust. Moving the AND-logic into a module would let that module become a second, independently-auditable grant authority, which reopens the "duplicate execution authority" defect ADR-001 exists to prevent.
2. **`ProcessStepOutcomeValidator` and execution-summary rendering stay in Core.** The validator lives in `Core/OutputContracts/AgentOutputValidatorRegistry.cs`; it validates against the `ProcessStepOutcomeResult` Models contract (a Core-owned contract type), which is the same pattern every other structured-output validator in the registry follows. There is no process-specific business logic in the validator itself — it is schema/shape validation, not process semantics — so it does not violate the "process semantics owned by Modules.Processes" boundary (ADR-007). Moving it to Modules.Processes would special-case one contract's validation registration away from the uniform registry pattern for no boundary benefit.
3. **`ExecutionInvocationMetadata` process keys stay as the compatibility storage format.** The metadata JSON blob's process-scoped keys (`ProcessRunId`, `ProcessStepId`, governed-run markers, etc.) continue to live beside the general execution metadata keys in one `ExecutionInvocationMetadata` helper rather than being split into a process-owned metadata namespace/type. This is persisted data (every `ExecutionRunRecord.MetadataJson` row already written), and splitting the metadata namespace now is out of this release gate's risk budget. Follow-up criteria (owned by a future subbundle, not SB18): only revisit the split if (a) a second module besides Modules.Processes needs to add its own metadata keys to the same JSON blob (proving the shared helper is becoming a dumping ground), or (b) a schema-versioned metadata envelope is introduced for another reason and process keys can move for free as part of that migration.
4. **The legacy unversioned session-state reader stays, with explicit removal criteria.** `MafRuntimeStateCompatibilityPolicy.Evaluate` (`RuntimeStateCompatibilityOutcome.RegisteredMigration`, `LegacyWrapMigrationId = "legacy-v0-wrap-v1"`) and its consumption in `MafRuntimeSessionBuilder.RestoreOrCreateSessionAsync` are the only path that still reads a chat session's `SerializedSessionStateJson` when it is **not** a versioned `RuntimeStateEnvelope` (pre-SB15 persisted format). The write path is single and already versioned-only: every `MafStreamingTurnExecutor` call site (5/5, verified) writes exclusively through `MafRuntimeSessionPersistenceDriver.TrySerializePersistableRuntimeSessionAsync`, which always produces an envelope. The legacy reader exists solely to keep *already-persisted* production chat sessions (written before this bundle's cutover) restorable instead of silently failing closed. Removal criteria (either satisfied, not both required): (a) an operator-confirmed data-retention/migration pass has run against production chat-session storage such that no row's `SerializedSessionStateJson` predates the envelope cutover, or (b) an explicit operator decision to accept that any surviving legacy-format session fails closed (matching the existing `Incompatible`/`HasUnparseableStoredState` behavior) rather than restoring. Until one of these is satisfied, deleting the reader would silently break restoring/approval-continuation for real historical conversations — a data-loss-shaped regression this bundle's safety rules forbid introducing without an explicit decision.

## Consequences

- No source change accompanies this ADR; it is a closure record for reviews already decided in-flight (CP4) plus the one legacy reader SB15/SB17 explicitly deferred to SB18.
- Any future subbundle proposing to touch `ExecutionInvocationMetadata` process keys or the `RegisteredMigration` reader must cite the criteria above rather than re-litigating the review.
- `RuntimeStateCompatibilityOutcome.RegisteredMigration` and `MafRuntimeStateCompatibilityPolicy.LegacyWrapMigrationId` are the two symbols that mark the retained reader; a repository-wide search for either name locates 100% of the remaining legacy-format compatibility surface.
