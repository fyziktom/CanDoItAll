## SB13 design decisions (locked)

MAF calls a NEW Core abstraction `IAgentExecutionOutcomeRecoveryPolicy` (list, DI-supplied through MafRuntimeCapabilityDependencies) with typed generic evidence (context intent, cause enum StreamingTimeout|MissingRequiredFinalizer, tool traces, per-run bundle IWorkspaceFileService for artifact reads). The Processes-owned `ProcessAgentExecutionOutcomeRecoveryPolicy` moves the ENTIRE ProcessArtifactRecoveryService logic (path building, current-execution overwrite verification, artifact parse, Blocked heuristics, outcome synthesis) into Modules.Processes; MAF loses every process token.
- Core ExecutionRuns process branches (ShouldOverrideProviderForGovernedProcessStep, IsGovernedMachineCriticalRun, process log helpers) move behind Core abstractions IAgentExecutionProviderSelectionPolicy / IAgentExecutionRunCriticalityPolicy (typed request records; defaults = no-op) implemented in Modules.Processes (string logic verbatim), wired via module DI into the execution service ctor.
- ExecutionInvocationMetadata process keys stay as compatibility storage format (SB18 metadata-split owner); ProcessStepOutcomeValidator usage reviewed at CP4.
- MAF may branch on typed `ContextIntent.IsGovernedProcessStep` bool (application-supplied), but not on source-kind strings/paths/outcome types (guard tokens).

## SB15 design decisions (locked)

- Runtime-state envelope write seam is the single `MafRuntimeSessionPersistenceDriver.TrySerializePersistableRuntimeSessionAsync` method (all 5 `MafStreamingTurnExecutor` call sites route through it); read seam is `MafRuntimeSessionBuilder.RestoreOrCreateSessionAsync`/`EvaluateStoredRuntimeState` — both MAF-internal, both behind the new SDK-free `IAgentRuntimeStateAdapter`/`IRuntimeStateCompatibilityPolicy` (Runtime.Abstractions). Core's pre-existing `ShouldRestoreSerializedSession` heuristic and approval-continuation fail-closed exception surface are unchanged; the policy only judges envelopes that heuristic already decided to attempt restoring.
- The authoritative `policy.Evaluate` call for provider/model/toolset/context-policy compatibility lives in MAF's read path (not literally inside Core's `ContinuationGuards.cs`), because the toolset fingerprint is only known post-capability-composition (MAF-SDK-internal); Core must never import MAF SDK types to duplicate that. This still runs strictly before any old session/approval state is read or replayed. Do not split this into a partial Core-side check — see SB15 proof `knownGaps` for the full reasoning before revisiting.
- Toolset fingerprint = SHA-256 over the ordered composed tool name set (`MafToolsetFingerprint`), computed in both native MAF adapters immediately after `runtimeBuild.CapabilityState` is available, threaded via `AgentRuntimeExecutionOptions.ToolsetFingerprint`. Context-policy fingerprint reuses SB02's `AgentTurnContextReference.ModelContextDigest` (read from `run.MetadataJson`), threaded via `AgentRuntimeExecutionOptions.ContextPolicyFingerprint`, set once in Core's `BuildRuntimeExecutionOptions`. Neither is a knownGap — both are fully wired, not faked.
- Per-proposal decisions: `AgentApprovalDecisionMismatchException.ValidateExactCoverage` is the single strict validation point (every pending approval must receive exactly one decision; no unknowns/duplicates), called in `ContinueExecutionRunEntryAsync` immediately after loading the run and before any state transition. The bool `ContinueExecutionRunAsync`/`RespondToPendingApprovalsAsync`/`StartApprovalContinuation` overloads (Core contract, `IAgentChatExecutionOrchestrator`, module pass-throughs) are now bounded compatibility facades only — they read the pending set fresh and re-enter the same strict core; no new production caller uses them (grep-proven). Do not add a new bool-shaped caller anywhere in this chain; SB18 is the deletion owner once SB17 stabilizes.
- `AgentRunTransientContextRegistry` renamed to `AgentTurnContextLeaseRegistry`; TTL eviction (24h default) never evicts a lease whose last-observed state is `WaitingOnTool`, sweeps lazily on `Register`/`Resolve`, and is a backstop only — terminal cleanup via explicit `Remove()` calls remains the primary path (2 previously-missing defensive `Remove()` calls added to duplicate-continuation-call branches).
