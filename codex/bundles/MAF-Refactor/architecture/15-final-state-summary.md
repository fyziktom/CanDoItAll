# Final-state architecture summary (SB18)

A map, not a book — each section is the current production shape after the bundle closes. See the numbered docs 00–14 for the design history and per-subbundle detail; this page is the destination, not the journey.

## Floating context, epoch, and turn semantics

A floating agent chat follows the user's current workspace surface by default. `AgentChatContextRegistry` (Core) holds exactly one live, atomically-published observation snapshot per scope with a monotonic revision; UI components (`AgentChatContextSurfaceProvider.razor` and module providers) publish to it and never read execution state back out of it. `AgentConversationContextService` tracks conversation *affinity* — whether a bound chat is "following" the current surface or has been explicitly detached — independent of the observation registry. Each send captures a fresh `AgentTurnContextCaptureService` turn: observation snapshot → transition classification (same scope/epoch vs a new one) → authority resolution → admission → a durable `AgentTurnContextMetadata` (V2) turn reference. `AgentChatContextInvocationFactory` (V1) still performs the first compositional step — scope/permission/digest capture and trusted-alias resolution into `AgentChatContextInvocation` — and the turn-capture service (V2) builds authority/transition/epoch handling on top of it; both stages are live and required, not a legacy/current pair.

## Observation versus authority

UI state is always observation, never authority. `IAgentExecutionAuthorityResolver` (canonical implementation `CanonicalAgentExecutionAuthorityResolver` in Modules.AgentFramework) is the only place a turn's execution authority (which scope, which permissions) is decided; it never reads current navigation or raw payload text to grant capability. Approval continuation never recaptures current UI context — it resumes strictly from the original run's persisted authority and pending-approval set (source-asserted by `FloatingAgentContextBaselineCharacterizationTests`/`AgentConversationContextServiceTests`).

## Workspace scope bundle

`WorkspaceScopeDescriptor` plus `WorkspaceExecutionScope`/`IWorkspaceRuntimeServicesFactory` compose one per-scope bundle of file/command/image services; every execution and every MAF adapter call receives the same bundle for the duration of one run so tool access, artifact roots, and audit context stay scope-consistent end to end.

## Runtime ports and the MAF adapter

Production execution flows through exactly four narrow ports declared in `CanDoItAll.AgentFramework.Runtime.Abstractions`: `IAgentExecutionRuntime`, `IAgentContinuationRuntime`, `IProviderDiagnosticsRuntime`, `IProviderModelAdministrationRuntime`. The broad legacy `IAgentRuntime` interface and its `LegacyAgentRuntimeCompatibilityFacade` bridge are deleted (SB18); nothing constructs or references them anywhere in `src/`. `MafAgentRuntime` is a thin composition root that builds one native adapter set (`MafAgentExecutionAdapter`, `MafAgentContinuationAdapter`, `MafProviderDiagnosticsAdapter`, `MafProviderModelAdministrationAdapter`) per runtime scope from `MafAgentRuntimeDependencies` and exposes the four ports as properties; it owns no streaming/session/finalizer logic. Process-mock and scenario-harness proof providers are port-level decorators that own their own provider-matching branch and deterministic interception bodies directly — no shared broad-interface shim remains.

## Process policy ownership

Process semantics (governed-run provider overrides, run-criticality classification, artifact-based execution recovery) are owned by `Modules.Processes` and injected into Core through typed policy abstractions (`IAgentExecutionProviderSelectionPolicy`, `IAgentExecutionRunCriticalityPolicy`, `IAgentExecutionOutcomeRecoveryPolicy`) with fail-open no-op defaults for hosts without the Processes module. MAF contains zero process tokens (`ProcessStepOutcomeResult`, `ProcessStepOutcomeStatus`, `"process-step"`, `ProcessArtifactRecovery`, `artifacts/process-runs`) — guard-enforced by `check_architecture_guards.py`. Core may branch only on the typed `ContextIntent.IsGovernedProcessStep` bool, never on source-kind strings or paths. The governed-intent AND-grant (`CreateRuntimeContextIntent` + `IsTrustedGovernedProcessRun`) and `ProcessStepOutcomeValidator` intentionally stay in Core (ADR-012 §1–2): capability grants must be centrally auditable, and the validator is ordinary Models-contract validation, not process business logic.

## Runtime-state envelope and continuation

Session state is written exactly once, through `MafRuntimeSessionPersistenceDriver.TrySerializePersistableRuntimeSessionAsync` (all `MafStreamingTurnExecutor` call sites route through it), always as a versioned `RuntimeStateEnvelope` carrying adapter id, schema version, provider/model identity, and toolset/context-policy fingerprints. `MafRuntimeStateCompatibilityPolicy.Evaluate` is the single strict compatibility judge on read; `MafRuntimeSessionBuilder` retains one legacy reader (`RuntimeStateCompatibilityOutcome.RegisteredMigration`) for chat sessions persisted before the envelope cutover — kept per ADR-012 §4 until an operator-confirmed data-retention criterion is met, never as a second write path. Continuation is strictly per-proposal: `AgentApprovalDecisionMismatchException.ValidateExactCoverage` requires every pending approval to receive exactly one decision. The bool `approved`-shaped overloads (`ContinueExecutionRunAsync`/`RespondToPendingApprovalsAsync`/`StartApprovalContinuation`) are deleted from every production contract (SB18); the public HTTP API keeps accepting a bool `Approved` field for backward compatibility, but `AgentApprovalDecisionRequestMapper` expands it to per-proposal decisions before the service call — no handler or module calls a bool-shaped service method.

## Deleted full-agent workflow LLM path

Workflow LLM component nodes never construct a full agent (`AgentDefinition`/`ChatSessionRecord`), never infer workspace scope from payload JSON, and never transit the broad runtime. `MafWorkflowLlmComponentInvoker` calls `ILlmInvocationPort` directly; zero `CapturingAgentRuntime`-style shims remain in production (confirmed by repository scan). Source guards (`WorkflowLlmLightweightPathTests`, both bundle guard scripts) enforce this permanently.

## Provider-backed lightweight LLM boundary and future ordinary chat

`CanDoItAll.AgentFramework.Llm.Abstractions` (`ILlmInvocationPort` + request/result records) is SDK-free, agent-free, workspace/authority-free, process-free, and UI-free — enforced by both guard scripts' forbidden-token scans. `CanDoItAll.AgentFramework.Llm.ProviderRuntime`'s `ProviderBackedLlmInvocationAdapter` reaches the existing provider runtime pool exactly once per invocation (descriptor upsert → pool handle → dispatch), never duplicating provider credential/HTTP/retry/usage infrastructure. A future `ILlmConversationService` (ordinary multi-turn chat, transcript/summarization ownership above the stateless port) is documented only as an XML remarks note on `ILlmInvocationPort` — ownership of that abstraction, if built, belongs to a future subbundle and must not make ordinary chat transit the full agent runtime either.
