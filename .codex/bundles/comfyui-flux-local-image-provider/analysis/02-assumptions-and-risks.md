# Assumptions And Risks

## Assumptions

- ComfyUI is expected to expose its HTTP API on `http://127.0.0.1:8188` or a reachable LAN URL on the same port.
- The Flux model files referenced by `ImageGenerationFlux.json` are installed in the updated ComfyUI instance.
- The ZyphoNote sample project can be modified as a disposable testbed because the user has a backup.
- CanDoItAll should keep the existing provider-runtime architecture and not introduce a second ComfyUI-specific service outside the provider driver boundary.

## Critical Path Risks

- SB01 is a hard critical foundation: if ComfyUI cannot enqueue and complete the Flux workflow, SB02 and SB03 must not start.
- SB02 is a critical foundation for SB03: if provider configuration or driver mutation is shallow, project-structure proof can pass only by bypassing the real provider path.
- SB03 is critical closure proof because the user asked for image generation through project structure, not just direct driver tests.

## Validation Risks

- Flux image generation can take several minutes, so tests must use focused live proof rather than broad repeated generation.
- ComfyUI failures may come from network binding, missing models, disabled API, or workflow node mismatch; the failure transcript must preserve the actual HTTP or protocol error.
- Existing broad test suites may have unrelated failures. Closure should use focused tests plus any required build, while clearly separating unrelated failures if a broad run is attempted.
- Project-structure UI/browser proof may require the web host to be running with a workspace profile that includes the new ComfyUI provider.

## Reopen Triggers

- Reopen SB01 if any later proof uses a different workflow, different model family, or non-ComfyUI provider.
- Reopen SB02 if project-structure proof requires manual provider construction that bypasses the seeded/provider registry path.
- Reopen SB02 if tests show a negative prompt node is required for Flux, because that contradicts the sampled workflow.
- Reopen SB03 if the generated bytes are not stored as a project-structure asset or cannot be read back from project structure.
