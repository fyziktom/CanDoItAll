SB04 explicit process-to-workflow execution proof
Date: 2026-07-12

Production behavior proved:
- Process roles and launch overrides carry a typed workflow id, optional exact version id, and typed output mapping; no composite executor id or arbitrary-active selection is used.
- The resolver validates exact active/runnable versions or the latest active version within the explicitly selected workflow.
- The dedicated workflow driver launches through IWorkflowLaunchService with Production, WaitForStopped, a typed ProcessAssignment origin/input envelope, and a stable assignment idempotency key.
- Retry recovery accepts only persisted child runs whose workflow/version and typed process run/assignment origin match. Active children defer, terminal states map explicitly, and duplicate or spoofed children are rejected.
- A launcher-returned run is revalidated before use. Missing/mismatched workflow, version, or origin fails explicitly.
- Process artifact/tool-receipt contracts and externalized/truncated workflow output fail explicitly; no result or resume is fabricated.
- Runtime assignment persistence stores workflow id, version id, and typed output mapping. Migration 20260712210953_AddProcessWorkflowExecutorBinding is model-converged.
- The large-screen process role editor preserves workflow bindings across later edits, supports latest-active or exact-version selection, and blocks invalid GUID input using BaseLib form wrappers.
