# Resolve UI screenshot applicability

Read the architecture handoff, implementation and acceptance-plan context, optional runtime command nodes, and project structure to decide whether the .NET target has a visible UI. This child can run before QA validation, so do not require QA evidence to resolve applicability. Blazor Server/SSR, Blazor WebAssembly, Blazor WASM PWA, MVC/Razor Pages, SPA-hosted .NET, and other browser surfaces require screenshot capture. Backend-only API/service, worker, console, and class library targets require explicit no-UI evidence. Identify the process run node and the Screenshots parent node target under it.

Prefer durable Run app and Run tests project-structure node references when they exist. If those command nodes are absent but verified upstream runtime/browser evidence contains a concrete base URL, browser artifact paths, and UI state proving the app is running, continue with a degraded manifest instead of blocking. Record the missing command-node references as warnings, cite the exact evidence paths, and require the capture step to create fresh current-run screenshot artifacts from the verified URL. If no Run app node and no concrete base URL exist but `ProductRoot`, `ProductRootAlias`, or `DotNetAppProjectDirectory` is present, record a launch-required manifest for the capture step so it directly launches the grounded app project instead of claiming degraded runtime evidence is available.

`DotNet*` aliases are optional in this child. When they are absent, read the runtime-forwarded `solution-context` embedded in the inherited implementation handoff and use its explicit `dotnet.solution-context/v1` `requiredProjectFiles` only as candidate targets for grounded runnable-project inspection. Its child artifact ref is trace-only; do not attempt a cross-run read. If neither aliases nor forwarded context are available, inspect the grounded product root and record the discovered runnable project. Never compose `src/`, `tests/`, a solution name, a project name, or a UI framework into a guessed project path.

Resolve the deterministic writeback process-run target from launch context in this order: `TargetProcessRunNodeId`, `ParentProcessRunNodeId`, `ProcessRunNodeId`, then `CurrentProcessRunNodeId`. Use a focused `project_structure_read` with that node id or subtree root when possible. A fresh run is not expected to have a `Screenshots` child yet; record the process-run node as the create-or-reuse target for `store-ui-screenshots`. Do not describe an absent `Screenshots` child as unavailable writeback, a managed fallback, a limitation, a warning, or capture work. If no process-run target identity can be derived from launch context, runtime identity, or project structure, return `Blocked` with that exact contract failure. Otherwise block only when UI applicability is contradictory, route targets are empty for a UI app, no concrete launch/browser evidence exists for a UI app, or no-UI evidence is missing for a non-UI target.

## Contract
- Inputs: Architecture handoff, implementation and acceptance-plan context, optional runtime command nodes, route nodes, process run node context, and optional verified upstream browser evidence when available.
- Outputs: Screenshot applicability manifest with UI routes or explicit no-UI evidence.
- Evidence: App type, UI/no-UI decision, route list, viewport set, runtime command references or degraded runtime evidence, missing-reference warnings, and the deterministic process-run writeback target with the `Screenshots` child marked as existing or create-required storage work.
- Operation target scope: `ExternalProductTargetReadOnly`
