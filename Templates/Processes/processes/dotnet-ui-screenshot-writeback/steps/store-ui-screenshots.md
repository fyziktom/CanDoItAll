# Store screenshots under process run node

Create or reuse a Screenshots parent node under the current process run node. Resolve the writeback parent in this order: `TargetProcessRunNodeId`, `ParentProcessRunNodeId`, `ProcessRunNodeId`, then `CurrentProcessRunNodeId`. Use a focused `project_structure_read` with the selected node id or subtree root before creation. Do not fall back to `ProjectNodeId` or project root when a process-run target is present. For UI targets, inspect each screenshot, distinguish accepted proof from a grounded visual discrepancy, and create image asset nodes under Screenshots for both accepted and diagnostic rejected screenshots. Label diagnostic assets as rejected visual evidence; never present them as accepted proof. For a target explicitly classified as having no browser-visible UI, carry forward its evidence-backed no-UI receipt under Screenshots or as managed evidence and select `no-ui-evidence-recorded`; do not manufacture screenshots, image assets, or browser receipts. Do not mutate product files.

For UI targets, `workspace_inspect_image` and `workspace_analyze_image` are required receipts only for `ui-evidence-stored`. Call `workspace_inspect_image` and `workspace_analyze_image` for every accepted or rejected screenshot before storage, and ground the visual reason in the provider-backed result rather than dimensions, filenames, or chat-only description. If the assigned provider/model is not vision-capable, return `Blocked` with that exact capability gap. Those image requirements do not apply to `no-ui-evidence-recorded`.

When project structure, launch variables, the screenshot manifest, or upstream QA evidence list source visual target ImageAsset nodes such as proposals, mockups, reference screenshots, layout targets, or wireframes, compare the delivered screenshot against the relevant source target before accepting visual alignment. Resolve the target by node id and media path with `project_structure_read`, `project_structure_asset_get`, or `project_structure_asset_content_get` as needed, then call `workspace_analyze_images` with the ordered source-target image and delivered screenshot paths when the image files are accessible in the workspace. If the target asset content is not accessible to image-analysis tools, return `Blocked` with the missing node id, media path, and failed tool receipt instead of accepting screenshots in isolation. The storage review must include a `Visual target comparison` section naming the source ImageAsset node id, media path or file name, delivered screenshot ref, comparison method, and accepted or blocked disposition.

When UI screenshots exist, project-structure writeback is a required action. `project_structure_node_create` and `project_structure_asset_create` are declared required runtime tool receipts for this step. If the Screenshots parent is missing, call `project_structure_node_create` with objectType `ProjectBlock`, objectSubtype `delivery`, and `parentNodeKey` set to the process-run node. Then call `project_structure_asset_create` once per screenshot with objectType `ImageAsset`, objectSubtype `screenshot`, `parentNodeKey` set to the Screenshots node, and `sourceWorkspacePath` set to the current-run PNG path such as `artifacts/process-runs/{runId}/browser-route-home-desktop.png`; also set `sourceFileName` and `sourceContentType` explicitly. Mark an asset that shows a grounded visual discrepancy as diagnostic rejected evidence, not accepted proof. If `project_structure_read` works, do not infer the writeback tools are unavailable from memory or prompt text; attempt the required writeback tools before reporting a boundary. Do not read binary screenshots as text or base64 when `sourceWorkspacePath` can be used. If an upload attempt fails because an inline media payload is invalid base64, retry once with the screenshot using `sourceWorkspacePath` instead of the inline media payload. Record the Screenshots node id and every returned image asset node id.

Do not write `Status: Completed`, do not say storage completed, and do not hand off until `project_structure_node_create` has created or reused the `Screenshots` child and `project_structure_asset_create` has succeeded for every UI screenshot. There is no successful managed-only storage outcome for a UI target. If either write tool is unavailable, denied, or fails, retain a diagnostic receipt naming the failed tool, process-run parent target, screenshot path, route, viewport, inspection result, and failure receipt, then return `Blocked` instead of completing silently. Also block when UI screenshots are missing or unreadable or when writeback is unexplained or partial. Do not block merely because an otherwise readable screenshot is blank, error, wrong-route, scaffold, unstyled, or non-interactive: preserve its diagnostic asset and evidence so the assessment step can emit `visual-defect-observed` for parent QA. A missing browser, image tool, or storage tool does not justify `no-ui-evidence-recorded`; that outcome is valid only when the applicability manifest already declares no browser-visible UI.

## Contract
- Inputs: Screenshot files, browser evidence, and screenshot target manifest.
- Outputs: `ui-evidence-stored` with a Screenshots parent node and image asset storage receipts, or `no-ui-evidence-recorded` with durable no-UI evidence.
- Evidence: Screenshots parent node id and one image asset id per UI screenshot, plus `workspace_inspect_image`, `workspace_analyze_image`, and when source visual targets exist `workspace_analyze_images` receipt refs, `Visual target comparison` details, rejected images, or explicit no-UI classification evidence. A blocked writeback carries its diagnostic failure receipt but is not a completed storage alternative.
- Operation target scope: `ExternalActionControlled`
