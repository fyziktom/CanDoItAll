# Run QA validation

Execute targeted regression validation and defect triage against the reviewed implementation package. This step has `RunValidation`; missing restore/build/test receipts are not a reason to route repair until you have attempted the commands yourself. For .NET targets, record a current-run validation chain from the launch-variable product root: `dotnet restore`, `dotnet build --no-restore`, and `dotnet test --no-restore` when a test project exists or tests are expected. When `DotNetSolutionFile` or `DotNetSolutionFileAlias` is present, target that solution file for restore/build/test. Do not infer `<SolutionName>.sln` from `DotNetSolutionName`, and do not report a missing `.sln` as a defect when the canonical `.slnx` target exists or already has successful current-run restore/build/test receipts. If the canonical target is absent, inspect `DotNetSolutionFileCandidates` and the product-root file listing, then use the existing candidate, preferring `.slnx` when both exist. Use `ProductRoot`, `ProductRootFileSystemPath`, or the equivalent grounded `external-target/...` alias from the step brief. Do not use `.` or the process artifact workspace as the product root. Do not accept upstream build or test claims alone as QA proof. If the validation tools, product-root alias, or permissions are unavailable, return `Blocked` with the concrete missing tool or capability; do not select `repair-required` for missing validation access. If `--no-restore` fails because restore assets are stale or missing, run restore and then rerun build/test; select `repair-required` only when the restored validation chain still fails or product evidence does not satisfy the accepted scope.

External generated product roots may not be Git repositories. Do not call `workspace_git_status` as a validation precondition for a grounded product root, and do not treat a `not a git repository` result as a product-root, validation-tool, or repair blocker. If you already attempted Git status and it failed only because the product root is not a Git repository, record Git status as not applicable and continue immediately with product-root file listing plus the restore/build/test validation chain.

Write or update `artifacts/process-runs/<current-process-run-id>/steps/qa-validation.md` before returning. In that managed artifact, use grounded workspace refs such as `external-target/...`, managed process refs, project-structure node ids, and tool receipt refs; do not write native absolute product paths such as `C:\...` or `/home/...` in the artifact body, reason, summary, next actions, or final evidence refs. If a native absolute path appears in launch variables, translate it to the equivalent grounded alias before recording it. When restore, build, or test tools run, the final `submit_process_step_outcome.evidenceRefs` must include the qa-validation artifact ref and the exact current-run receipt refs for each successful validation command, not only the artifact that mentions those receipts. Do not return `quality-accepted` until the structured final evidence refs include those receipt refs.

Inspect the shipped entrypoint, referenced runtime commands, project files, and stale or unreferenced artifacts. When a visible UI workflow or source ImageAsset target exists and the step has `LaunchRuntime` plus `CaptureRuntimeProof`, run the app and validate the visible route before selecting `quality-accepted`. Start the app with `workspace_dotnet_run` against `DotNetAppProjectFileAlias` when present, otherwise `DotNetAppProjectFile`; never pass a solution file, product root, app project directory, or other directory as the run target. Use browser tools against the real route, interact with the primary workflow so at least one screenshot or state artifact shows a meaningful changed state, capture screenshot `.png`, browser state `.yml` or `.json`, and console `.log` evidence, and stop the app with `workspace_dotnet_stop` before finalizing. When source ImageAsset targets such as proposals, mockups, reference screenshots, layout targets, or wireframes are present, inspect or resolve the source media path and compare it to the delivered screenshot with `workspace_inspect_image`, `workspace_analyze_image`, and `workspace_analyze_images` when available. Record the ImageAsset node ids, media paths, comparison method, screenshot refs, runtime command hints, and screenshot/browser proof requirements for the downstream runtime-command and screenshot writeback subprocesses.

Select `repair-required` when the UI proof shows a concrete product defect that implementation can repair, including an untouched framework scaffold, stock navigation or starter routes that are still visible on the primary product route, placeholder styling, no meaningful workflow state, missing expected interaction behavior, an unstyled custom surface, or a delivered screenshot that materially misses the source visual target. Do not defer those findings only to screenshot writeback when this step has the browser and image-analysis tools to prove them. If the step lacks a required launch, browser, or image-analysis tool because of policy or provider capability, return `Blocked` with the exact missing tool or model instead of accepting the UI on file inspection alone.

Select `quality-accepted` only when the current-run validation chain, test execution, entrypoint/runtime inspection, and required UI/browser/image proof are sufficient for later gates. Select `repair-required` for failing restored validation, missing expected tests, stale shipped entrypoint, unreferenced output, unresolved visual-target mismatch, stock scaffold UI on a product route, missing interaction proof, or another concrete product defect that implementation can repair. Do not select `repair-required` merely because build/test receipts were absent before this step; run the validation chain first. Return `Blocked` only for a confirmed tool, policy, environment, access, product-root, provider-capability, or process-contract failure that prevents QA from executing validation or collecting enough evidence to choose `quality-accepted` or `repair-required`; cite the failed tool or missing capability.

## Contract
- Inputs: Peer-reviewed change set, changed-surface inventory, and release-scope assumptions.
- Outputs: Targeted QA result with restore/build/test evidence, regressions, warning and executed-test counts, shipped entrypoint/runtime consistency, current-run UI/browser/image proof when applicable, downstream runtime or screenshot proof requirements, residual quality risk, and an explicit accepted or repair-required branch.
- Evidence: Current-run restore logs, warning-free build output unless explicitly accepted, nonzero executed-test proof when tests are expected, exact restore/build/test receipt refs in final evidenceRefs when those commands run, shipped entrypoint plus referenced-runtime inspection, stale or unreferenced artifact assessment, source ImageAsset node id/media path evidence when visual targets exist, `workspace_dotnet_run` and cleanup receipts when UI proof runs, screenshot/browser state/console refs, `workspace_inspect_image`, `workspace_analyze_image`, and `workspace_analyze_images` receipt refs when visual comparison is required, runtime command hints, screenshot/browser proof handoff requirements, and defect notes. Managed QA evidence must use grounded aliases and managed refs instead of native absolute product paths.
- Operation target scope: `ExternalProductTargetReadOnly`
- Outcome rule: Return a completed process-step outcome with branchOutcomeKey `quality-accepted` or `repair-required` for evaluated QA dispositions. Do not combine status `Blocked` with branchOutcomeKey `repair-required`.
