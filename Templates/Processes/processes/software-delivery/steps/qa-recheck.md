# Re-run QA validation and runtime or browser proof after repair

Re-run targeted runtime/API/browser validation as applicable against the repaired package and select an explicit accepted or unresolved-repair branch. When project structure, original QA findings, or repair evidence identifies a visible browser workflow, recapture current-run process-visible browser artifacts under `artifacts/process-runs/<run-id>/browser/` before selecting quality-accepted.

When project structure lists visual target assets, QA recheck must use those ImageAsset node ids and media paths as source visual requirements. Fetch or analyze the relevant asset content again if the prior receipt is missing, then compare the repaired screenshot against the target image before accepting visual alignment. Do not accept visual quality from the repaired screenshot alone, and do not downgrade a listed target image to a vague style suggestion unless project governance explicitly says it is non-binding. The final recheck artifact must include a `Visual target comparison` section naming the source ImageAsset node id, media path or file name, source asset fetch or analysis receipt, repaired screenshot ref, comparison method, and acceptance or repair-escalation disposition.

For every screenshot used to accept or reject a repaired visual claim, call `workspace_analyze_image` and cite the current execution run, provider, model, token counts, and tool receipt path or id. For before/after comparisons, animated behavior, queued work, background loading, polling, timers, streaming, or any claim that visible state changes over time, capture ordered screenshots over elapsed time and call `workspace_analyze_images`. If image analysis is unavailable but current browser snapshot/evaluate output, console evidence, screenshot inspection, and validation receipts are enough to identify an unresolved repair defect or proof gap, return status `Completed` with branchOutcomeKey `repair-escalation`. Return `Blocked` only for a confirmed tool, policy, environment, access, or process-contract failure that prevents QA from collecting enough evidence to choose `quality-accepted` or `repair-escalation`; cite the failed tool, provider/model, and receipt or missing capability.

## Contract
- Inputs: Repair change set, original QA findings, and reviewed implementation package.
- Outputs: Recheck result with warning-free validation, nonzero executed-test proof when tests are expected, shipped entrypoint/runtime consistency, runtime/API/browser evidence as applicable, regression evidence, and explicit quality disposition. Browser-workflow repair acceptance requires fresh process-visible screenshot, current-run `workspace_analyze_image` or `workspace_analyze_images` receipt for visual claims, browser_snapshot or browser_evaluate state output, browser_console_messages output, actual URL or entrypoint, launch and cleanup receipts, acceptance-state assertion, and a `Visual target comparison` section when source ImageAsset targets exist.
- Evidence: Regression logs, warning-free validation output unless explicitly accepted, nonzero executed-test proof when tests are expected, shipped entrypoint plus referenced-runtime inspection, stale or unreferenced artifact assessment, runtime/API/browser proof as applicable, screenshots for UI surfaces, source ImageAsset node id/media path evidence when visual targets exist, provider-backed image-analysis receipts for repaired visual conclusions, repair verification, unresolved defects if any, and fresh current-run process-visible browser artifacts when a visible browser workflow is in scope.
- Operation target scope: `ExternalProductTargetReadOnly`
- Outcome rule: Return a completed process-step outcome with branchOutcomeKey `quality-accepted` or `repair-escalation` for evaluated repaired QA dispositions. Do not combine status `Blocked` with branchOutcomeKey `repair-escalation`.
