# Re-run QA validation after repair

Re-run targeted regression validation against the repaired package and select an explicit accepted or unresolved-repair branch. This step has `RunValidation`; missing restore/build/test receipts are not a reason to escalate until you have attempted the commands yourself. For .NET targets, record a current-run validation chain from the launch-variable product root: `dotnet restore`, `dotnet build --no-restore`, and `dotnet test --no-restore` when a test project exists or tests are expected. When `DotNetSolutionFile` or `DotNetSolutionFileAlias` is present, target that solution file for restore and build. When `DotNetTestProjectFileAlias` or `DotNetTestProjectFile` is present, target that test project for `workspace_dotnet_test`, preferably with `noBuild=true` after a successful solution build; use the solution target for tests only when no test project target exists. Do not infer `<SolutionName>.sln` from `DotNetSolutionName`, and do not report a missing `.sln` as a defect when the canonical `.slnx` target exists or already has successful current-run restore/build receipts. If the canonical target is absent, inspect `DotNetSolutionFileCandidates` and the product-root file listing, then use the existing candidate, preferring `.slnx` when both exist. Use `ProductRoot`, `ProductRootFileSystemPath`, or the equivalent grounded `external-target/...` alias from the step brief. Do not use `.` or the process artifact workspace as the product root. Do not accept repair notes or upstream build claims alone as recheck proof. If the validation tools, product-root alias, or permissions are unavailable, return `Blocked` with the concrete missing tool or capability; do not select `repair-escalation` for missing validation access. If `--no-restore` fails because restore assets are stale or missing, run restore and then rerun build/test; select `repair-escalation` only when the restored validation chain still fails or product evidence does not satisfy the repair target.

Re-read the required `scope-boundary-packet`, architecture decision record, and acceptance-driven validation plan, then verify the repaired product against every original required ProductAcceptance core behavior as well as the immediate repair target. When `ProductAcceptanceCriteriaContract` is present, preserve every criterion id in the artifact, but require Pass/Fail product proof only for criteria with `kind=ProductAcceptance` and `required=true`. Record `kind=DeliveryPlanning` items separately as nonblocking planning context; they cannot route `repair-escalation`, block `quality-accepted`, or require human confirmation unless a separate typed decision gate explicitly requests that decision. Do not accept because the latest defect disappeared while another required ProductAcceptance interaction, calculation, persistence, reload, recovery, or output criterion remains absent or unproved. A planned proof is not executed acceptance evidence. Record required product criterion coverage and route `repair-escalation` with exact evidence when the bounded repair did not restore the complete required core workflow.

Use `DotNetSolutionFileAlias`, `DotNetAppProjectFileAlias`, and `DotNetTestProjectFileAlias` exactly when they are present. Do not probe a guessed product-root `<App>.csproj` first and do not treat its absence as a blocker when the declared app project exists under `src/` or another grounded layout. Inspect the supplied alias and execute the required validation tools yourself. Never request that a manager assign another agent merely because this QA execution has not produced its own receipts yet; attached validation and runtime tools belong to this step.

Root delivery processes intentionally do not activate a .NET launch driver. When `DotNet*` variables are absent, use the runtime-forwarded `solution-context` embedded in the implementation handoff and use only its declared `dotnet.solution-context/v1` `solution.file`, `requiredProjectFiles`, and optional `testProjectFiles`. The child artifact ref is trace-only: do not attempt a cross-run read. If the runtime-forwarded context is absent, inspect the grounded product root with workspace listing and read tools, record the discovered target, and continue; never invent a conventional `src/`, `tests/`, `<App>.csproj`, `.sln`, or application-framework layout.

Read the post-repair screenshot handoff before revalidation. `visual-defect-observed` is concrete product evidence, not an infrastructure blocker: independently validate the route, preserve the child evidence, and select the existing `repair-escalation` branch when the defect remains. `no-ui-evidence-recorded` means browser validation is inapplicable for the declared target; preserve its explicit classification evidence, continue the required non-browser QA checks, and do not treat the missing browser proof as a blocker or as product acceptance. Return `Blocked` only when a concrete tool, access, policy, environment, or provider failure prevents QA from choosing `quality-accepted` or `repair-escalation`.

External generated product roots may not be Git repositories. Do not call `workspace_git_status` as a validation precondition for a grounded product root, and do not treat a `not a git repository` result as a product-root, validation-tool, or repair blocker. If you already attempted Git status and it failed only because the product root is not a Git repository, record Git status as not applicable and continue immediately with product-root file listing plus the restore/build/test validation chain.

Write or update `artifacts/process-runs/<current-process-run-id>/steps/qa-recheck.md` before returning. In that managed artifact, use grounded workspace refs such as `external-target/...`, managed process refs, project-structure node ids, and tool receipt refs; do not write native absolute product paths such as `C:\...` or `/home/...` in the artifact body, reason, summary, next actions, or final evidence refs. If a native absolute path appears in launch variables, translate it to the equivalent grounded alias before recording it. When restore, build, or test tools run, the final `submit_process_step_outcome.evidenceRefs` must include the qa-recheck artifact ref and the exact current-run receipt refs for each successful validation command, not only the artifact that mentions those receipts. Do not return `quality-accepted` until the structured final evidence refs include those receipt refs.

Inspect the repaired shipped entrypoint, referenced runtime commands, project files, and stale or unreferenced artifacts. When a visible UI workflow or source ImageAsset target exists and the step has `LaunchRuntime` plus `CaptureRuntimeProof`, run the app and validate the repaired visible route before selecting `quality-accepted`. Start the app with `workspace_dotnet_run` against `DotNetAppProjectFileAlias` when present, otherwise `DotNetAppProjectFile`; if neither is supplied, resolve the declared application file from the bootstrap decision or grounded product-root readback before running. Never pass a solution file, product root, app project directory, or other directory as the run target. Use browser tools against the real route, interact with the primary workflow so at least one screenshot or state artifact shows a meaningful changed state, capture screenshot `.png`, browser state `.yml` or `.json`, and console `.log` evidence, and stop the app with `workspace_dotnet_stop` before finalizing. Runtime start, browser proof, and stop cleanup must all be produced in the same retry from the same `workspace_dotnet_run` startup receipt; prior receipts, screenshots, browser state, or summaries do not satisfy the current-run lifecycle gate. When source ImageAsset targets such as proposals, mockups, reference screenshots, layout targets, or wireframes are present, inspect or resolve the source media path and compare it to the delivered screenshot with `workspace_inspect_image`, `workspace_analyze_image`, and `workspace_analyze_images` when available. Record the ImageAsset node ids, media paths, comparison method, screenshot refs, runtime command hints, and screenshot/browser proof requirements for downstream repaired runtime-command and screenshot writeback subprocesses.

Upstream repair and handoff artifacts are not product inspection. Before accepting repaired source-backed UI work, read the actual app project, at least one representative repaired source file for the primary workflow, and the relevant test source from the grounded product alias. Capture baseline state, perform the representative click, fill, selection, key, type, drag, or elapsed-time action, then use `browser_evaluate` plus snapshot or screenshot evidence to prove the expected post-action state. Navigation, responsive resizing, and unchanged screenshots do not satisfy repaired interaction proof. If the workflow still does not change as required, select `repair-escalation` with the source, action, and observed-state evidence.

Before writing the recheck artifact or finalizing, reconcile every required current-execution receipt. Product-source readback and post-interaction `browser_evaluate` must happen before runtime stop; an artifact that merely says they happened is not proof.

Select `repair-escalation` when repaired UI proof still shows a release-blocking product defect, including an untouched framework scaffold, stock navigation or starter routes that are still visible on the primary product route, placeholder styling, no meaningful workflow state, missing expected interaction behavior, an unstyled custom surface, or a delivered screenshot that materially misses the source visual target. Do not defer those findings only to screenshot writeback when this step has the browser and image-analysis tools to prove them. If the step lacks a required launch, browser, or image-analysis tool because of policy or provider capability, return `Blocked` with the exact missing tool or model instead of accepting the repaired UI on file inspection alone.

Select `quality-accepted` only when repaired validation evidence, test execution, entrypoint/runtime inspection, and required UI/browser/image proof satisfy the original repair target. Select `repair-escalation` only after current-run restored validation was attempted and still fails, expected tests are missing, the shipped entrypoint is stale, output is unreferenced, proof remains unmapped, unresolved visual-target mismatch remains, stock scaffold UI remains on a product route, interaction proof is still missing, or another release-blocking defect remains after repair. Do not select `repair-escalation` merely because build/test receipts were absent before this step; run the validation chain first. Return `Blocked` only for a confirmed tool, policy, environment, access, product-root, provider-capability, or process-contract failure that prevents QA from executing validation or collecting enough evidence to choose `quality-accepted` or `repair-escalation`; cite the failed tool or missing capability.

## Contract
- Inputs: Authoritative scope boundary packet, architecture decision record, acceptance-driven validation plan, repair change set, original QA findings, and reviewed implementation package.
- Outputs: Recheck result with restore/build/test evidence, warning-free validation, nonzero executed-test proof when tests are expected, shipped entrypoint/runtime consistency, current-run UI/browser/image proof when applicable, downstream runtime or screenshot proof requirements, regression evidence, and explicit quality disposition.
- Evidence: Acceptance-criteria coverage with current-run proof or failure for every required ProductAcceptance criterion and preserved nonblocking DeliveryPlanning items, current-run restore logs, warning-free build output unless explicitly accepted, nonzero executed-test proof when tests are expected, exact restore/build/test receipt refs in final evidenceRefs when those commands run, current-run repaired product source and test-source read receipts, shipped entrypoint plus referenced-runtime inspection, stale or unreferenced artifact assessment, source ImageAsset node id/media path evidence when visual targets exist, `workspace_dotnet_run` and cleanup receipts when UI proof runs, representative browser action plus post-action `browser_evaluate`/snapshot/screenshot state evidence, screenshot/browser state/console refs, `workspace_inspect_image`, `workspace_analyze_image`, and `workspace_analyze_images` receipt refs when visual comparison is required, runtime command hints, screenshot/browser proof handoff requirements, repair verification, and unresolved defects if any. Managed QA evidence must use grounded aliases and managed refs instead of native absolute product paths.
- Operation target scope: `ExternalProductTargetReadOnly`
- Outcome rule: Return a completed process-step outcome with branchOutcomeKey `quality-accepted` or `repair-escalation` for evaluated repaired QA dispositions. Do not combine status `Blocked` with branchOutcomeKey `repair-escalation`.
