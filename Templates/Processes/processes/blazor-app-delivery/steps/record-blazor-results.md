# Record Blazor results and evidence index

Write a compact run evidence index, agent self-review summary, output-root path, screenshot references, console status, build/test status, and final verdict back into project structure through APIs/tools. Resolve the exact launch-selected node from `ProjectNodeId` and current `project_structure_read`. When it is a WorkItem, use that WorkItem as the direct parent. When the launch selected a delivery ProjectBlock, use that exact delivery ProjectBlock as the direct parent; this is an explicit launch target, not a fallback or a reason to guess a WorkItem. For any other node kind or a missing selected node, return Blocked with the current read evidence. Never fall back to the project root or any other delivery/output block. Before creating a result node, call `project_structure_read` for the launch-selected parent and its children and look for a result Note for the current process run. On retry, reuse that current-run Note: call `project_structure_node_reparent` first if it is not a direct child of the launch-selected parent, then call `project_structure_node_update` to refresh its title, notes, and verdict. Do not create a duplicate. Only when no current-run result Note exists, call `project_structure_node_create` with objectType `Note`, no subtype, parentNodeKey set to the launch-selected parent id, and metadataJson `{}`; the result is a plain descriptive Note, not a WorkItem, ProjectBlock, asset, or runnable node. Use `project_structure_asset_create` separately for screenshot or evidence files that must become project assets. Read back the final Note, and record whether it was created, reused, updated, or reparented plus its node id, direct parent node id and kind, asset ids, and raw record pointers needed for selective follow-up. If a required read, create, update, reparent, asset, or readback call fails, return status Blocked with the exact failed tool and receipt; do not select the Error branch as a completed outcome.

## Evidence

Record commands, files, URLs, screenshots, console messages, errors, assumptions, and project-structure writeback references as applicable.

## Application runtime node

Delivery includes a persistent launch control, separate from the plain result Note and temporary QA hosts. Under the same launch-selected parent, create or reuse one application runtime node with objectType `Environment`, objectSubtype `dotnet-runtime`, and metadataJson containing `environment.environmentKind` = `dotNetRuntime`, `environment.projectPath` = the exact existing runnable app `.csproj`, and `environment.workingDirectory` = that project file's directory. Use the actual app entry project from the implementation and QA handoffs; never target a solution, test project, guessed folder, published DLL, or disposable evidence server. For hosted Blazor, choose the runnable server project; for standalone WASM/PWA, choose the client project with its development server. This local launch control does not replace the published-output/offline proof or claim production deployment.

Read the project file and its `Properties/launchSettings.json` when present using the admitted workspace tools. Copy an existing Project launch profile and its matching loopback URL into `environment.launchProfileName` and `environment.localhostUrl`; use the corresponding `environment.runtimeProtocol` (`http` or `https`). Prefer the existing HTTP profile for local startup when the contract does not require HTTPS. If no profile exists, omit profile and URL rather than inventing a QA port; record how startup resolves the endpoint. Do not store tokens, shell commands, process ids, session ids, or extra authority in metadata. Use the existing typed Environment contract, not a Script wrapper around dotnet.

Before any runtime-node write, use a current `project_structure_read` including metadata and notes to inspect the selected parent's children. Reuse a matching Environment node for the same exact app project; do not duplicate it on retry. Preserve user-edited launch settings and unrelated nodes. A conflicting runtime target or concurrent mutation requires a fresh read and explicit reconciliation, never an overwrite with stale metadata. Pass the original current-read mutation expectations to the existing create/update tools. Do not automatically repoint an older run's runtime node to a different app path. Create with parentNodeKey set to the launch-selected parent only when no matching runtime node exists. Record the current run id and local-launch purpose in the node's notes.

Read back both the final Note and runtime node. Require the runtime node's exact project path, matching subtype/kind, direct parent and direct-launch capability; include its id, create-or-reuse disposition, launch profile/URL and tool receipts in the evidence index and writeback summary. A missing, rejected or non-launchable runtime node makes writeback Blocked. This step registers the launch control; it does not start or leave an application process running. The user's Start/Stop actions continue through the Workbench runtime owner.
