# Revalidate Blazor repair

Resolve the product root, runnable host, test targets, acceptance surfaces, and required capabilities from the current delivery contract and grounded project-structure aliases. Revalidate those declared targets only. Honor the declared topology: sibling or nested app and test projects are valid when the contract declares them; they remain defects only when an undeclared target substitutes for a declared product or test target, or when proof comes from the wrong root. Copy every authoritative project-structure node id, external-target alias, and tool identifier verbatim from current grounded input; never retype, shorten, or infer it. If a lookup returns `NodeNotFound`, re-read the current grounded source, correct any identifier mismatch, and retry the exact identifier. If the exact authoritative target remains unavailable after that current failed receipt, treat it as a revalidation-input blocker, not a repaired-product defect.

Before restore or build, stop any prior `workspace_dotnet_run` process for the same host with its recorded startup receipt when available. Restore and build the declared product targets, test the targets present in the resolved test topology, then start the repaired runnable host and record its current startup receipt. Treat that startup receipt as the temporal boundary for revalidation proof. Only after the receipt exists, create a fresh isolated browser context or page and perform a new navigation to the current startup URL. Evidence produced before the current startup receipt, inherited from an existing page, or captured from the pre-repair execution is invalid for the repaired-build decision.

For WebAssembly and PWA hosts, keep repaired-build proof isolated from earlier browser cache and service-worker state by using the fresh context and navigation. Revalidate service-worker registration, cache/update behavior, offline behavior, installation, or other PWA capabilities only when the resolved delivery contract requires them. Likewise, require API/backend and persistence proof only when those surfaces are part of the resolved contract.

Use Playwright browser tools for each visible UI surface required by the contract. Capture screenshot paths, snapshot or evaluate state, console and page errors, the actual URL or entrypoint, visible behavior assertions, and the cleanup receipt. Missing, blank, detached, pre-start, stale, or chat-only evidence is not acceptable. Treat current post-start console errors, failed required local assets, loading placeholders, blank bodies, or unavailable required interactions as unresolved defects. For visual or time-dependent claims, inspect the screenshots and capture enough ordered state to prove the assertion.

Before finalizing, resolve every required criterion. When a required criterion would be `NotVerified` only because authorized proof has not yet been executed, execute that proof now. `NotVerified` or missing proof is not repaired-product defect evidence and must not select an escalation branch. Select `quality-accepted` only when the declared acceptance criteria and required proof are satisfied after repair. Select the declared `repair-escalation` branch only for a typed `Failed` required criterion or equivalent deterministic current repaired-build product defect, and identify its current receipt, console/page error, assertion, path, or other deterministic evidence. Do not route from stale browser state, undeclared topology, or an undeclared optional capability. If a confirmed tool, policy, infrastructure, input, access, or contract failure prevents required proof, return `Blocked` without a branch and cite the failed receipt.

After browser proof, call `workspace_dotnet_stop` with the current startup receipt and record cleanup evidence before returning any branch outcome. Project-structure writeback belongs to the result-recording steps; do not call project-structure mutation tools from this revalidation step.

## Evidence

Record declared targets and capabilities, commands, files, current startup and cleanup receipts, URLs, screenshots, browser state, console/page errors, failed criteria, and assumptions.
