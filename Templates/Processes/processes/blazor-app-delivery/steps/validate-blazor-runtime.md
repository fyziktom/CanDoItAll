# Validate Blazor runtime and browser evidence

Run validation against the delivered Blazor SSR, WASM, or WASM PWA app. Use the authoritative product root from the delivery contract and implementation change set. Before reporting an external-target access failure, call `workspace_stat_path` or `workspace_read_file` against the exact path and cite the failed receipt; absence of a failed receipt is not proof of access failure.

If the contract names an exact product root, validate that root only. A sibling app project, sibling `*.Tests` project, nested copied scaffold, nested probe project, or custom host output path property inside the product root is a validation finding; choose `repair-required` instead of validating a different project. Tests must be under the approved root's `tests` child, and the runnable host build/run proof must target the approved root.

Before running restore/build, stop any prior `workspace_dotnet_run` process for the same product root by calling `workspace_dotnet_stop` with the recorded startup.json receipt when available; do not run build while the product executable is still locked by a previous validation runtime. Run dotnet restore, dotnet build, and dotnet test when a test project exists or was created. Start the app once from the approved product root and record the startup receipt. Build, test, and analyzer warnings are validation defects for generated apps, not ignorable risks; if a warning cites an editable product or test file, choose repair-required with the exact warning and line instead of quality-accepted. Use Playwright browser tools for every visible UI surface named by project structure or implementation evidence. Capture screenshot image paths, browser_snapshot or browser_evaluate state output, browser_console_messages output, actual URL or entrypoint, visible behavior assertions, and cleanup receipt. After browser proof, call workspace_dotnet_stop with the startup receipt path and record cleanup.json evidence before returning any branch outcome, including repair-required or Blocked. For new app delivery, include the matching API/backend proof as well. Missing, blank, detached, stale, or chat-only screenshots are not acceptable.

Treat every browser console error and every failed local static asset response as a validation finding unless the implementation explains a concrete external-service dependency that is outside the app. Missing local CSS, Bootstrap files, icons, manifests, service workers, framework scripts, generated styles, or other product-root assets must choose `repair-required`; do not accept the app only because the main route rendered.

For screenshots used in visual claims, call `workspace_inspect_image` and, when available, `workspace_analyze_image`, then cite the provider/model/token result. For before/after screenshot comparisons or any claim that visual state changed over time, prefer `workspace_analyze_images` with the ordered screenshot paths when available. If the assigned provider/model is not vision-capable, choose `repair-required` or `Blocked` for that visual-analysis gap instead of accepting screenshot metadata alone.

For Blazor WebAssembly or PWA apps, a route that remains on the loading placeholder, renders a blank body, or has no visible enabled controls is a validation finding. Inspect browser console/page errors and local script load order for missing DI registrations, unregistered interface-backed services, missing JavaScript interop globals, or local bridge scripts loaded after `_framework/blazor.webassembly.js`; choose `repair-required` with those concrete findings instead of accepting startup smoke alone.

If implementation evidence or runtime inspection shows a scaffold-only app, deferred acceptance criteria, missing routes, missing product behavior, no-op handlers for named interactions, missing persistence, missing PWA/static-hosting proof, failed browser assertions, or incomplete screenshots/console proof, choose the `repair-required` branch and write both required validation artifacts with concrete findings. For time-dependent, animated, queued, asynchronous, or continuously progressing UI behavior, capture before/after state over elapsed time and prove the observable state changed as expected; if the product wording or acceptance criteria imply automatic progression, manual input proof is not a substitute. A single static screenshot is insufficient. Use `Blocked` only for a confirmed tool, policy, or infrastructure failure that prevents validation and has a matching failed receipt. Project-structure evidence-node attachment is not part of this validation decision: after the managed validation artifacts are written, do not fail this step solely because `project_structure_node_create` or project-structure writeback cannot attach the evidence node, and do not call `project_structure_node_create` or `project_structure_asset_create` from this validation step. Do not use `workspace_pwsh_run_script` for cleanup or diagnostic helper scripts; record startup receipts from `workspace_dotnet_run` and cleanup receipts from `workspace_dotnet_stop`, with browser evidence and managed artifacts. Do not return any branch outcome until the validation runtime is stopped or an explicit failed cleanup receipt is cited as the blocker. This review step must select exactly one governed branch: `quality-accepted` only when all criteria and proof are satisfied, otherwise `repair-required`; do not complete with the Default branch.

## Evidence

Record commands, files, URLs, screenshots, console messages, errors, and assumptions. Project-structure writeback belongs to the result-recording steps, not this validation step.
