# Build Blazor application

Create or update the requested Blazor solution and app using the project-structure declared mode, package choices, routes, features, and output folder. Use workspace file and command tools only inside the approved product root; if that product root is absent, create it there. Never scaffold, restore, build, or write product files under backup, agent-evidence, observation, process-definition, launch-plan, or other evidence-only folders.

If the contract names an exact generated app output root, that root is authoritative. Resolve the runnable host and test projects from the contract-declared topology and grounded project aliases. A root-level host, `src/` host, nested test project, or explicitly grounded sibling project can be valid. Do not scaffold or validate an undeclared sibling, probe, scratch project, or copied scaffold as a substitute for the declared product. Change output-path properties only when the contract or a concrete build diagnostic requires it, and keep final build/run/test commands targeted at the declared projects.

For greenfield delivery, scaffolding is only the first action, not a deliverable. Implement every explicit project-structure acceptance criterion in this step, including the named UI behavior, routes, input handling, and validation proof required by the delivery contract. Implement persistence, API/backend, publishing/static output, service-worker, offline, installation, or other PWA capabilities only when the resolved contract includes them. Do not defer a declared capability to "next actions". If a requested criterion cannot be implemented with the available tools, block with the exact failed tool receipt and affected criterion.

Do not ship placeholder behavior for named interactions. If the contract names keyboard controls, route behavior, persistence behavior, or domain-specific interaction rules, the implementation must make those controls change observable application state and must exercise them in self-review. A scaffold, no-op handlers, random demo loop, or document that lists missing work is not a completed implementation.

For Blazor WebAssembly or PWA work, prefer `workspace_dotnet_new` with the matching Blazor template under the approved product root, then modify the generated project in place. If the contract says WASM PWA, Progressive Web App, installable, offline, manifest, service worker, or static-hosting PWA, scaffold with the Blazor WebAssembly PWA option (`blazorwasm` with the PWA switch supported by the tool/template) and verify `wwwroot/manifest.webmanifest` or `wwwroot/manifest.json`, service worker files, and index.html registration exist before implementation is considered complete. A plain Blazor WASM scaffold without PWA assets is the wrong scaffold for WASM PWA work and must be repaired in the same step.

Before the final build/run handoff, inspect the delivered app entry document (`wwwroot/index.html` for WASM/PWA or the equivalent layout/root document for SSR) and make every local `href`/`src` reference resolve to a real file under the product root or build output. Do not reference Bootstrap, scaffold CSS, icons, manifests, service-worker scripts, or generated CSS paths unless those files exist at the exact referenced route. If the scaffold wrote `wwwroot/app.css`, reference `app.css` or move it under `wwwroot/css/app.css`; do not leave a stale `css/app.css` link. Browser console 404s for local static assets are implementation defects, not acceptable warnings.

For Blazor WebAssembly apps, inspect the complete runtime dependency graph from actual component and service injection sites through transitive dependencies. Register the intended abstractions, implementations, and lifetimes with the host, and make repairs from current compiler, host, or browser evidence rather than a remembered registration recipe. If current evidence identifies a JavaScript bootstrap or interop failure, inspect the entry document and loading model and repair that concrete cause. Do not mark complete while current startup proof remains on a loading placeholder or fails because the declared runtime graph is incomplete.

Replace starter content and routes with the contract routes. If the contract names `/`, a primary workspace route, secondary views, or equivalent product routes, implement those routes and make the primary route render the actual app surface, not a link list to a secondary scaffold page. Use `workspace_dotnet_run` as HTTP startup proof for web apps; do not request a foreground web run that is expected to keep running until timeout. Run dotnet restore before build-sensitive changes when dependencies changed. Run dotnet build after implementation and run dotnet test for targets in the resolved test topology. For generated tests, keep execution deterministic and bounded: do not write `while` loops that depend only on mutable app/UI state without a maximum iteration guard and an assertion that each state transition succeeded. Treat compiler, build, test, and analyzer warnings as validation defects in generated apps; read the exact diagnostic and apply the supported repair for the actual framework and package version instead of a remembered assertion or analyzer recipe. Use a `workspace_dotnet_test` timeout of 300 seconds or less unless a real diagnostic proves the generated app tests need more time. When the current-run tool requirements include runtime startup proof, start the app once with `workspace_dotnet_run` and record the startup receipt; leave browser screenshots and console proof to the validation step. Do not mark complete if explicit acceptance criteria are omitted, if output is written outside the approved product root, or if project-structure constraints are narrowed without a decision record.
