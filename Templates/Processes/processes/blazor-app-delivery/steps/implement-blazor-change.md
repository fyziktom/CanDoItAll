# Build Blazor application

Create or update the requested Blazor solution and app using the project-structure declared mode, package choices, routes, features, and output folder. Use workspace file and command tools only inside the approved product root; if that product root is absent, create it there. Never scaffold, restore, build, or write product files under backup, agent-evidence, observation, process-definition, launch-plan, or other evidence-only folders.

For greenfield delivery, scaffolding is only the first action, not a deliverable. Implement every explicit project-structure acceptance criterion in this step, including the named UI behavior, routes, input handling, local persistence, PWA/static-hosting assets, and validation proof required by the delivery contract. Do not mark complete while game/business/UI behavior, tests, publishing/static output, or PWA requirements are deferred to "next actions". If a requested criterion cannot be implemented with the available tools, block with the exact failed tool receipt and affected criterion.

Do not ship placeholder behavior for named interactions. If the contract names keyboard controls, route behavior, persistence behavior, or domain/game mechanics, the implementation must make those controls change observable application state and must exercise them in self-review. A scaffold, no-op handlers, random demo loop, or document that lists missing work is not a completed implementation.

For Blazor WebAssembly or PWA work, prefer `workspace_dotnet_new` with the matching Blazor template under the approved product root, then modify the generated project in place. If the contract says WASM PWA, Progressive Web App, installable, offline, manifest, service worker, or static-hosting PWA, scaffold with the Blazor WebAssembly PWA option (`blazorwasm` with the PWA switch supported by the tool/template) and verify `wwwroot/manifest.webmanifest` or `wwwroot/manifest.json`, service worker files, and index.html registration exist before implementation is considered complete. A plain Blazor WASM scaffold without PWA assets is the wrong scaffold for WASM PWA work and must be repaired in the same step.

Replace starter content and routes with the contract routes. If the contract names `/`, `/game`, `/scores`, or equivalent primary/scores routes, implement those routes and make the primary route render the actual app surface, not a link list to a secondary scaffold page. Use `workspace_dotnet_run` as HTTP startup proof for web apps; do not request a foreground web run that is expected to keep running until timeout. Run dotnet restore before build-sensitive changes when dependencies changed. Run dotnet build after implementation and run dotnet test when tests exist or are created. When the current-run tool requirements include runtime startup proof, start the app once with `workspace_dotnet_run` and record the startup receipt; leave browser screenshots and console proof to the validation step. Do not mark complete if explicit acceptance criteria are omitted, if output is written outside the approved product root, or if project-structure constraints are narrowed without a decision record.

## Evidence

Record commands, files, URLs, screenshots, console messages, errors, assumptions, and project-structure writeback references as applicable.
