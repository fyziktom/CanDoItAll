# Repair Blazor validation findings

Repair only findings produced by the validation step. Do not expand scope beyond project-structure acceptance criteria. If validation found scaffold-only delivery or deferred acceptance criteria, implement the missing requested product behavior in the approved product root instead of adding more evidence around the incomplete scaffold. Rerun the smallest relevant build and test checks for the declared targets before handoff. If validation found missing dependency injection, inspect the actual component and constructor injection sites plus transitive dependencies, then repair the intended abstraction, implementation, and lifetime registrations before rerunning runtime proof. If a compiler, build, test, or analyzer diagnostic identified the defect, read its exact stdout/stderr artifact, edit the cited product or test file, and use the supported repair for the actual framework and package version; do not apply a remembered analyzer or assertion recipe. When runtime startup proof is invalidated by the repair, start the declared host once with `workspace_dotnet_run` and record the startup receipt; leave fresh browser proof to the revalidation step. Do not mark complete while a behavior, route, persistence capability, API/backend surface, PWA/static-hosting capability, test target, or command diagnostic required by the resolved contract remains unresolved. Do not require or repair optional capabilities that the contract does not declare.

Validation evidence owned by the revalidation step, such as fresh browser proof and published-output or static-host proof, is not a repair deliverable: when the contract declares static delivery, confirm that the repaired target still publishes, and leave serving and verifying that output to revalidation instead of blocking on it.

If validation found source or proof under the wrong root, repair the contract-declared project itself. A sibling or nested project is a defect only when it is an undeclared substitute for a declared host or test target. Preserve declared project relationships and output topology unless the contract or a concrete diagnostic requires a change, and rerun proof against the declared targets rather than a probe or copied scaffold.

## Evidence

Record commands, files, URLs, screenshots, console messages, errors, assumptions, and project-structure writeback references as applicable.

Include the exact runnable app `.csproj`, its directory, and the current `Properties/launchSettings.json` Project profile and loopback URL (when present) in the implementation handoff. The result-writing step will register a persistent typed Environment runtime node for this app under the launch-selected parent. Keep this launch target distinct from test projects, solution files and disposable published-output QA hosts; do not create the runtime node in implementation.

Keep validation-host cache policy separate from production deployment policy. The managed workspace_static_serve host deliberately returns no-cache, max-age=0, must-revalidate for fresh-build proof; this is compatible with service-worker offline caching and is not by itself a product defect. Require a particular cache lifetime or immutable fingerprinted-asset response only when explicitly required by the project source or a named deployment target. Do not promote a recommended production caching optimization into a new mandatory acceptance criterion, or replace the managed proof host with a custom script solely to obtain that optimization. Still verify current published assets, entry/worker revalidation, required offline/update behavior and cleanup. An explicitly required deployment cache policy remains a separate required check; if the available host cannot prove it, report the concrete capability gap as Blocked without claiming that deployment requirement passed.
