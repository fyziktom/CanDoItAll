# Implement the feature or function

Make the minimal code and test changes that satisfy the validation contract. Follow local project patterns, keep state explicit, and block instead of guessing when dependencies or architecture constraints are missing.

If the grounded product root is empty, incomplete, or missing the expected app/test scaffold, create or repair the scaffold inside that product root with the available product-mutation tools before implementing the behavior. Do not report that there are "no files to mutate" when this step has `MutateProductTarget`; that is scaffold repair work owned by this step unless the tool boundary denies product mutation.

Use the grounded external-target alias for structured workspace path arguments when mutating product files. Product files changed by this step must be written under that product target with a product-mutation tool such as `workspace_write_file`, `workspace_append_file`, `workspace_copy_path`, `workspace_move_path`, `workspace_delete_path`, `workspace_dotnet_new`, or `workspace_pwsh_run_script`. Writing only the managed step artifact under `artifacts/process-runs/...` is not a product change and cannot satisfy this step.

When you create or repair tests, keep them deterministic and bounded. Do not write loops that depend only on mutable product state without a maximum iteration guard and an assertion that each state transition succeeded. Use a `workspace_dotnet_test` timeout of 300 seconds or less for focused generated-app tests unless a current diagnostic proves the test suite needs more time.

When implementing or repairing deterministic tests, verify that the expected assertions are internally consistent with the test's own action sequence and the accepted behavior. For calculator behavior, every expected display value and history row must follow from the exact digits and operators invoked in that test. If a generated test contradicts arithmetic or another explicit acceptance rule, repair the test rather than changing product code to satisfy the invalid expectation.

For Blazor WebAssembly targets, preserve and verify template-critical namespace wiring before completing the change set. If `Program.cs` registers `RootComponents.Add<App>`, `Program.cs` must either import the app root namespace or fully qualify the `App` component. If `App.razor`, `Routes.razor`, `Pages/NotFound.razor`, or layout files reference `MainLayout`, `_Imports.razor` must import the layout namespace or the reference must be fully qualified. Before finalizing Blazor app changes, read `_Imports.razor` and restore scaffold-critical shared imports when the template files still need them: `@using System.Net.Http.Json`, `@using <app-root-namespace>`, and `@using <app-root-namespace>.Layout` where `<app-root-namespace>` is the actual root namespace from the project. Prefer shared `_Imports.razor` imports over page-specific layout guesses when existing scaffold pages depend on shared namespace wiring. A `CS0246` for `App`, `MainLayout`, `Routes`, `Router`, or `HeadOutlet`, or a `GetFromJsonAsync` extension-method error, is an in-scope scaffold wiring defect for a Blazor feature implementation; repair the product file before writing the final change-set artifact when this step has product mutation tools.

When a Razor component markup file references members such as `State`, event handlers, injected services, or helper methods from a companion class, bind that class explicitly before completing the change set. Either keep the members in the same `.razor` file inside `@code`, use a same-name partial class generated by the Razor compiler, or add an explicit `@inherits <BaseClass>` directive to the `.razor` file. Do not create a separate `ComponentBase` class and then only state in the artifact that the page derives from it; the product file readback must show the directive or partial-class binding that makes the markup compile.

This step does not own final acceptance and does not own runtime launch, browser navigation, screenshots, viewport proof, or downstream acceptance validation. It owns the implementation attempt and change-set evidence. Complete this step after current-run product source/test files were mutated under the grounded product root, the changed product files were read back or stat-checked, and the changed-file inventory plus current implementation evidence were written to the managed step artifact. Focused build/test commands may be run here when they help catch immediate wiring mistakes, but missing restore/build/test receipts are not a manager escalation reason because `targeted-validation` owns the required validation proof. Do not claim changed files in the managed artifact until those exact files exist in the product target.

Changed-file and evidence refs in the managed artifact must be copied exactly from current-run tool receipts, product file readbacks, launch variables, or required upstream refs. Do not hand-compose or shorten external-target paths in artifact evidence lists; a typo or missing path segment is a grounding failure.

Do not cite stale source document paths, managed-files paths, project-media paths, email summaries, or unrelated domain notes unless those exact refs appear in the current launch variables, selected project structure node, or required upstream artifact for this feature. Keep source context scoped to the selected project node and current process evidence.

If product files were changed and the focused build/test proof fails because of compile errors, test failures, missing imports, or incomplete implementation, do not return `Failed` or `Blocked`. Write `Status: Completed` for the change-set artifact, include the failing command receipt/output refs, and state that targeted validation must choose `feature-repair-required`. The validation branch owns repair routing. Do not claim the defect was corrected unless the corrected product file was read back from the grounded product target and a later command receipt proves the corrected build or test path. Current file readback and current command receipts are authoritative over upstream summaries and over your own intended change list.

Return `Succeeded` / `Completed` once product mutation and the grounded change-set artifact are complete, even when restore/build/test, runtime launch, browser proof, screenshot comparison, or final acceptance remain for downstream steps. Do not return `NeedsManager`, `WaitingApproval`, `Failed`, or `Blocked` only because downstream proof is pending, command receipts are missing from this implementation step, or validation still needs to choose `feature-accepted` versus `feature-repair-required`.

Return `Blocked` only when an environment, permission, unavailable product-mutation tool, missing grounded product root, unsafe architecture conflict, or process-contract issue prevents producing a change-set artifact. Do not block only because current-run browser proof is still pending.
