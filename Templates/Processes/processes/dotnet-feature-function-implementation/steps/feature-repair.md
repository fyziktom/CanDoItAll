# Repair focused validation findings

Repair the concrete validation failure described by the `feature-repair-required` evidence, plus any sequential same-validation-target build or test blockers revealed while proving that repair.

- Read the original feature scope, validation contract, code-change summary, and targeted validation evidence.
- Mutate only the product files needed to address the failing proof.
- Treat current product file readback and current command receipts as authoritative. If a summary says a repair is already present but the product file readback or command output disproves it, repair the product file; do not repeat the summary as fact.
- If the failing proof shows the grounded product root lacks the expected app/test scaffold, create or repair that scaffold inside the product root with the available product-mutation tools before returning.
- Do not widen the accepted feature behavior or add deferred backlog work.
- Rerun the smallest useful build or test check that proves the repair direction before writing the repair change-set artifact when the validation tool is available. If a `--no-restore` build fails in `ResolvePackageAssets`, run restore and then rerun build before classifying source defects. If the rerun still fails, inspect the failing output, mutate the product file again when the defect is inside the same product target and validation boundary, and rerun validation.
- A compile error, scoped CSS error, missing component, missing handler, missing state field, missing namespace import, failing unit test, or similar defect in the same validation boundary is still repair work for this step when product mutation and validation tools are available. Do not treat a later compiler or test failure as outside scope merely because it appeared after fixing the first failure. Continue through sequential build/test failures until the focused proof passes, an explicit product requirement conflict is proven, or a required tool/root/permission is unavailable.
- When a failing generated test has expected values or recorded history that contradict its own action sequence or an explicit deterministic rule, repair the test expectation instead of changing product code to satisfy an invalid test. Record the test repair and rerun restore/build/test before completing.
- Do not write `Status: Completed` for a repair artifact that says validation still fails for any corrected validation-target product defect, even if one earlier mutation was made.
- For Blazor WebAssembly targets, `CS0246` errors for `App`, `MainLayout`, `Routes`, `Router`, or `HeadOutlet` are scaffold namespace wiring defects owned by this repair step when product mutation tools are available. Repair `Program.cs`, shared `_Imports.razor`, `App.razor`, `Routes.razor`, `Pages/NotFound.razor`, or layout files as needed so the root component and default layout resolve. If `Program.cs` registers `RootComponents.Add<App>`, add the app root namespace import or fully qualify the component. If layout is referenced by short name, add the layout namespace import or fully qualify the layout reference. If `HttpClient.GetFromJsonAsync` is unresolved, restore `@using System.Net.Http.Json` in shared `_Imports.razor` or add the equivalent source import. Prefer repairing shared `_Imports.razor` with the actual app root namespace and layout namespace over adding one-off page imports when several scaffold files depend on the same namespace. Continue through sequential build errors until the smallest build check passes or an explicit unavailable tool/scope blocker is proven.
- For Razor component symbol errors where markup references members such as `State`, event handlers, injected services, or helper methods, verify the actual component binding in the product file. If a companion `ComponentBase` class provides those members, the `.razor` file must contain an explicit `@inherits <BaseClass>` directive, or the companion class must be the same-name partial class generated for that Razor component. A repair artifact that says the page derives from a base class is not evidence unless current product file readback shows `@inherits`, a matching partial class, or same-file `@code` members.
- When the inherited validation failure contains compile or test failures, a repair completion requires current-run proof that the same validation target no longer reproduces the defect. After each product mutation, rerun the smallest restore/build/test chain needed to prove the fix. Use `DotNetSolutionFileAlias` or `DotNetSolutionFile` for restore/build and use `DotNetTestProjectFileAlias` or `DotNetTestProjectFile` for `workspace_dotnet_test` when present; fall back to solution-level test only when no test project target exists. If `workspace_dotnet_build` or `workspace_dotnet_test` returns a non-zero exit code for the corrected validation target and the defect is inside the product target, keep repairing; do not write `Status: Completed` by relying on inspection, intended changes, or stale successful test output. If no product mutation was needed because the file was already correct, the artifact must quote the exact readback evidence and still include a successful current-run build receipt.
- Select `feature-repair-applied` only after a product mutation receipt, owning-source readback, and current-run restore/build/test proof show that the targeted defect no longer reproduces.
- Select `repair-attempt-incomplete` when the bounded repair attempt cannot produce that accepted mutation-and-proof state. This completed branch routes directly to a parent no-go packet; do not rely on an unchanged green build or test run to describe it as repaired. Do not select `feature-repair-required` from this step.
- If the validation tool or product root is unavailable, record that as a blocker with the exact missing capability/root; do not silently skip validation and mark the repair complete as fully proved.
- Do not launch runtime or capture browser proof here unless the inherited validation failure explicitly came from runtime proof owned by this subprocess.
- Record changed files, failing proof addressed, commands rerun, exit codes, remaining risks, and evidence refs. Evidence refs must be copied exactly from current-run tool receipts, current product file readbacks, launch variables, or required upstream refs. Do not hand-compose or shorten product paths in evidence refs; a path typo is a grounding failure. If a command was not run, include the explicit unavailable tool/root/contract reason so `targeted-recheck` can treat it as a blocker instead of a normal no-go.
- Do not cite stale source document paths, managed-files paths, project-media paths, email summaries, or unrelated domain notes unless those exact refs appear in the current launch variables, selected project structure node, or required upstream artifact for this repair. Keep repair evidence scoped to the selected project node and current process evidence.

Return `Completed` with exactly one branch outcome: `feature-repair-applied` for an accepted mutation and proof, or `repair-attempt-incomplete` for a bounded failed repair attempt. Return `Blocked` only for missing access, unavailable tools, contradictory requirements, unavailable product root, or a repair that would require behavior outside the accepted feature/product scope.
