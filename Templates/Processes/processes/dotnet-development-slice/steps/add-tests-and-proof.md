# Validate tests and targeted proof

Review current-run coordinator evidence and run targeted build and test validation without mutating product files. This step has validation-command ownership: do not defer restore, build, or test execution to a later root proof step. Use the governed validation tools `workspace_dotnet_restore`, `workspace_dotnet_build`, and `workspace_dotnet_test` for the current run. If current-run restore/build/test receipts are missing and those validation tools plus the grounded product root are available, run the validation chain now; missing receipts are not a repair finding by themselves.

Read the required `slice-scope-packet` directly and treat it as the authoritative acceptance contract. Build a compact criterion-to-production-source/test/proof map for every explicitly named core behavior. A green build, a nonzero passing test count, or a child handoff cannot close a criterion that is absent, unwired, tested only through fabricated test state, or deferred without an explicit remaining-slice schedule. Route those concrete gaps to `slice-repair-required` even when existing tests pass.

Use the current-run `implement-code-change` artifact as the subprocess coordinator packet. Child-run refs cited inside that artifact are trace links, not direct read requirements for this QA validation step. Do not read `artifacts/process-runs/<child-run-id>/...` files directly unless the step brief explicitly lists that exact child artifact as a required upstream ref. If the coordinator packet says the child completed and lists accepted handoff evidence, independently validate from the product root with build/test/readback proof instead of returning `Blocked` for the child artifact boundary.

Managed artifact evidence rule: cite this step's managed artifact and current-run validation tool receipts as proof. Do not put product source/test file aliases, native product paths, `external-target/...` file paths, `managed-files/...` paths, or project-media storage paths in `evidenceRefs`. In the artifact body, prefer product-root-relative file names. If a retry diagnostic names an ungrounded product path but the grounded product root and validation tools are available, rerun the restore/build/test chain or read/list the file with a current-run workspace tool, then overwrite the artifact with grounded receipt-based proof instead of selecting `slice-repair-required` or returning `Blocked`.

For .NET product roots, run and record a current-run validation chain: `dotnet restore`, `dotnet build --no-restore`, and `dotnet test --no-restore` when a test project exists or tests are expected. Target restore/build at the discovered solution when present; target `workspace_dotnet_test` at `DotNetTestProjectFileAlias` or `DotNetTestProjectFile` when present, preferably with `noBuild=true` after a successful solution build, and use the solution target for tests only when no test project target exists. Do not mark the slice accepted from implementation handoff evidence alone, and do not select `slice-repair-required` only because the receipts were absent before this step ran. If `--no-restore` fails because restore assets are stale or missing, run restore and then rerun build/test; select `slice-repair-required` only when the restored validation chain still fails or product proof does not satisfy the chosen slice behavior.

External generated product roots may not be Git repositories. Do not call `workspace_git_status` as a validation precondition for a grounded product root, and do not treat a `not a git repository` result as a product-root, validation-tool, or repair blocker. If you already attempted Git status and it failed only because the product root is not a Git repository, record Git status as not applicable and continue immediately with product-root file listing plus the restore/build/test validation chain.

Before running validation commands, resolve the actual solution target from the setup handoff, product readback, or product-root file listing. Inspect `<ProductRoot>/<SolutionName>.slnx` and `<ProductRoot>/<SolutionName>.sln`; use the existing file, preferring `.slnx` when both exist. Never synthesize or require `<SolutionName>.sln` when only `<SolutionName>.slnx` exists. If a validation attempt fails only because a guessed solution path is missing, immediately rerun the current-run validation chain against the discovered `.slnx` or `.sln` target and do not route repair for the missing guessed path.

This step owns the slice validation branch decision:

- Select `slice-accepted` only when child implementation evidence, current-run build proof, current-run executed-test proof when tests exist or are expected, and focused proof satisfy the chosen slice behavior.
- Select `slice-repair-required` when tests are missing or inadequate, build or focused validation fails, the current-run coordinator packet lacks accepted child handoff evidence, or proof does not map to the chosen slice behavior.
- When selecting `slice-repair-required`, write a repair target packet in this step artifact. It must include the exact failed acceptance criteria, failing command or evidence metric, child run id when present, child step artifact refs as trace links when present, and the smallest proof that would close the defect. If the current-run coordinator packet cites a child `feature-repair-escalation` or `targeted-recheck` artifact but direct child reads are not allowed, restate the missing or failing evidence from the coordinator packet and product proof instead of returning `Blocked`.
- Return a completed process-step outcome with the selected branch outcome. Do not return `Blocked` only because product proof failed and can be repaired by a bounded implementation subprocess.
- Return `Blocked` only when an environment, permission, unavailable validation tool, or process-contract issue prevents validation or repair routing.

QA does not add or edit product tests in this step.

When visual target ImageAsset ids or media paths are part of the slice scope, verify that child-run evidence preserves those acceptance inputs and require root runtime-command and screenshot writeback follow-up for live screenshot comparison before release. Do not launch the app, open a browser, or capture screenshots in this slice proof step.
