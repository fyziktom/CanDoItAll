# Validate tests and targeted proof

Review current-run coordinator evidence and run targeted build and test validation without mutating product files. This step has validation-command ownership: do not defer restore, build, or test execution to a later root proof step. Use the governed validation tools `workspace_dotnet_restore`, `workspace_dotnet_build`, and `workspace_dotnet_test` for the current run. If current-run restore/build/test receipts are missing and those validation tools plus the grounded product root are available, run the validation chain now; missing receipts are not a repair finding by themselves. `slice-accepted` means ready for parent QA and runtime proof, not released end-to-end.

Read the required `slice-scope-packet` directly and treat it as the authoritative acceptance contract. Build a compact criterion-to-production-source/test/proof map for every explicitly named core behavior. A green build, a nonzero passing test count, or a child handoff cannot close a criterion that is absent, unwired, tested only through fabricated test state, or deferred without an explicit remaining-slice schedule. Route those concrete gaps to `slice-repair-required` even when existing tests pass.

Use the current-run `implement-code-change` artifact as the subprocess coordinator packet. Its runtime-synthesized `implementation-ready` branch, `accepted` child disposition, exact typed child evidence ref, hash-verified selected child payload, and runtime accepted-completion section are the canonical accepted-child provenance. The runtime-authenticated child-output payload is available as implementation context; its child-run refs are trace links, not direct read requirements for this QA validation step. Do not read `artifacts/process-runs/<child-run-id>/...` files directly unless the step brief explicitly lists that exact child artifact as a required upstream ref. Do not re-decide the typed bridge from payload prose, require a separate agent-authored restatement, or route product repair because that restatement is absent. Independently validate the product from the grounded root with build/test/readback proof.

Managed artifact evidence rule: cite this step's managed artifact and current-run validation tool receipts as proof. Do not put product source/test file aliases, native product paths, `external-target/...` file paths, `managed-files/...` paths, or project-media storage paths in `evidenceRefs`. In the artifact body, prefer product-root-relative file names. If a retry diagnostic names an ungrounded product path but the grounded product root and validation tools are available, rerun the restore/build/test chain or read/list the file with a current-run workspace tool, then overwrite the artifact with grounded receipt-based proof instead of selecting `slice-repair-required` or returning `Blocked`.

For .NET product roots, first read the required `dotnet-solution-context` artifact. Use its explicit `dotnet.solution-context/v1` `solution.file` for restore/build, its `requiredProjectFiles` as the authoritative implementation targets, and its optional `testProjectFiles` for `workspace_dotnet_test`; use `DotNet*` aliases only when they agree with that typed context. Run and record a current-run restore/build chain and run `dotnet test --no-restore` for every declared test target. When no test target is declared, record that explicit non-applicability and validate the acceptance-driven proof at the declared production boundary; do not invent a test project or turn a missing guessed test path into a repair. Do not mark the slice accepted from implementation handoff evidence alone, and do not select `slice-repair-required` only because the receipts were absent before this step ran. If `--no-restore` fails because restore assets are stale or missing, run restore and then rerun the applicable validation chain; select `slice-repair-required` only when the restored validation chain still fails or product proof does not satisfy the chosen slice behavior.

External generated product roots may not be Git repositories. Do not call `workspace_git_status` as a validation precondition for a grounded product root, and do not treat a `not a git repository` result as a product-root, validation-tool, or repair blocker. If you already attempted Git status and it failed only because the product root is not a Git repository, record Git status as not applicable and continue immediately with product-root file listing plus the restore/build/test validation chain.

Before running validation commands, resolve the exact solution and test targets from the required typed bootstrap decision. If a declared target is unavailable, inspect the grounded product-root file listing and record the discovered replacement before validation; do not form a path from `SolutionName`, assume `.sln` versus `.slnx`, or invent `src/` or `tests/` layout. If a validation attempt fails only because a previously guessed path was missing, immediately rerun the current-run validation chain against the typed or grounded-discovered target and do not route repair for the missing guessed path.

This step owns the slice validation branch decision:

- Select `slice-accepted` only when child implementation evidence, current-run build proof, current-run executed-test proof when tests exist or are expected, and focused proof satisfy the chosen slice behavior. Record browser-only, visual, or other parent-owned runtime criteria as parent QA follow-up instead of selecting repair solely because this read-only slice step cannot execute that proof.
- Select `slice-repair-required` when tests are missing or inadequate, build or focused validation fails, or product proof does not map to the chosen slice behavior. An absent separate agent-authored restatement of the runtime-authenticated child payload is not a product defect.
- When selecting `slice-repair-required`, write a repair target packet in this step artifact. It must include the exact failed product acceptance criteria, failing command or evidence metric, child run id when present, child step artifact refs as trace links when present, and the smallest product/test/proof change that would close the defect. If the current-run coordinator packet cites a child `feature-repair-escalation` or `targeted-recheck` artifact but direct child reads are not allowed, restate the concrete product or proof failure from the coordinator packet and product proof instead of returning `Blocked`.
- Return a completed process-step outcome with the selected branch outcome. Do not return `Blocked` only because product proof failed and can be repaired by a bounded implementation subprocess.
- Return `Blocked` only when an environment, permission, unavailable validation tool, or process-contract issue prevents validation or repair routing.

QA does not add or edit product tests in this step.

When visual target ImageAsset ids or media paths are part of the slice scope, verify that child-run evidence preserves those acceptance inputs and require root runtime-command and screenshot writeback follow-up for live screenshot comparison before release. Do not launch the app, open a browser, or capture screenshots in this slice proof step.
