# Independently validate the repair action

Reproduce the original proof from the manager diagnosis and run current-execution restore, build, and tests. Read the actual repaired app project, representative workflow source, and relevant test source; upstream repair notes are not product inspection. For a UI-visible failure or UI product contract, launch the product, capture baseline state, perform the representative click/fill/select/key/type/drag or elapsed-time action, then capture post-action `browser_evaluate`, changed-state snapshot, screenshot, and console evidence before stopping the same runtime. Apply the corrected route or proof recipe when the prior action selected `proof-only-revalidation-prepared`.

Use the inherited authoritative scope packet to verify the complete core workflow, not merely application reachability or a single repaired control. When `ProductAcceptanceCriteriaContract` is present, product proof gates only criteria with `kind=ProductAcceptance` and `required=true`. Preserve `kind=DeliveryPlanning` items as nonblocking context; they cannot select `bughunt-required`, block `quality-repair-accepted`, or require human confirmation unless a separate typed decision gate explicitly requests that decision. Before writing the artifact or finalizing, audit every required current-execution receipt and every required ProductAcceptance core criterion. Run concrete product-source readback and post-interaction `browser_evaluate` before runtime stop.

For persistence proof, a deterministic test through the typed storage adapter or coordinator is sufficient to prove graceful unavailable behavior unless a required ProductAcceptance criterion explicitly demands a live browser storage outage. For normal IndexedDB reload proof, use `browser_evaluate` to seed and inspect the declared database and object-store schema, reload the app, and verify restored UI state; do not require playing or operating the workflow until it naturally creates a nonzero value.

Pass full managed filenames to every browser screenshot, snapshot, and console capture: `artifacts/process-runs/<current-process-run-id>/browser/<evidence-name>.<ext>`. If an inherited or newly captured bare provider-native screenshot cannot be opened by a workspace image tool, recapture it once with the full managed current-run filename and retry analysis before choosing `bughunt-required`, `Blocked`, or escalation. When a source visual target exists, call `workspace_analyze_images` with the ordered pair of source target first and delivered current-run screenshot second, and cite that receipt in final evidence.

If the prior action was routed as `repair-attempt-incomplete`, do not retry the same implementer. Reproduce the still-unfixed defect, select `bughunt-required`, and provide exact current-run evidence to the specialist.

Known failed proof is not residual risk. Select `quality-repair-accepted` only when current-execution proof is clean. If the original error persists, a new release-blocking error appears, or expected behavior is still broken, select `bughunt-required` and attach the exact failing evidence for the specialist.

Capture all command/runtime/browser evidence before writing the primary managed artifact. Write that artifact once with the final observed disposition; do not write a provisional or placeholder `Status: Blocked` artifact. A reproduced product defect, unchanged interaction, visible error, or failed expected behavior is a completed validation decision with branch `bughunt-required`, not a Blocked outcome. Return Blocked only when required product access or validation capability was unavailable and no proof decision could be executed.

Return `Blocked` only when a required tool, product root, permission, or process contract prevents validation.
