# Independently revalidate the bughunt action

Reproduce both the original and persistent failed proof, then run current-execution restore, build, tests, and conditional runtime/browser validation against the typed second action. Read the actual repaired app project, representative workflow source, and relevant test source. For UI work, capture baseline state, perform the representative click/fill/select/key/type/drag or elapsed-time action, and capture post-action `browser_evaluate`, snapshot, screenshot, and console proof. Apply the corrected proof target or recipe when the action selected `proof-only-revalidation-prepared`. Known failed proof is not residual risk.

Verify the inherited authoritative scope packet criterion by criterion, but gate the result only on criteria with `kind=ProductAcceptance` and `required=true`; do not accept an app shell or one changed control as the complete required workflow. Preserve `kind=DeliveryPlanning` items as nonblocking context. They cannot select `final-specialist-repair-required`, block `quality-repair-accepted`, or require human confirmation unless a separate typed decision gate explicitly requests that decision. Before writing the artifact or finalizing, reconcile every required current-execution tool receipt. Read concrete owning product source and run `browser_evaluate` after the representative interaction and before `workspace_dotnet_stop`.

Before selecting `quality-repair-accepted` or calling the finalizer, populate `acceptanceCriteriaEvidence` with one entry for every active required ProductAcceptance criterion. Every entry must use the exact structured properties `criterionId`, `status`, `summary`, and `evidenceRefs`; set `criterionId` to the exact criterion id, set `status` to `Passed`, and cite criterion-specific current-run proof in `evidenceRefs`. Do not use aliases such as `id`, `passed`, or `proofRefs`. If every required entry cannot be populated, select `final-specialist-repair-required` instead.

For persistence proof, a deterministic test through the typed storage adapter or coordinator is sufficient to prove graceful unavailable behavior unless a required ProductAcceptance criterion explicitly demands a live provider outage. For ordinary persistence reload proof, exercise the declared storage boundary with available validation or runtime tooling, restart or reload the applicable host, and verify restored application state without waiting for unrelated workflow-generated values.

Pass full managed filenames to every persisted browser screenshot, snapshot, evaluation, and console capture: `artifacts/process-runs/<current-process-run-id>/browser/<evidence-name>.<ext>`. If an inherited or newly captured bare provider-native screenshot cannot be opened by a workspace image tool, recapture it once with the full managed current-run filename and retry analysis before choosing `final-specialist-repair-required`, `Blocked`, or escalation. When a source visual target exists, call `workspace_analyze_images` with the ordered pair of source target first and delivered current-run screenshot second, and cite that receipt in final evidence.

If the second action was routed as `repair-attempt-incomplete`, do not retry that implementer. Reproduce the unresolved defect and select `final-specialist-repair-required` with exact current-run evidence.

Select `quality-repair-accepted` only when both defect sets are resolved and no new release blocker exists. Select `final-specialist-repair-required` with exact failing evidence when the defect persists or the second repair introduces another release blocker. This routes to a fresh read-only diagnosis before the third and final mutation opportunity; it is not permission for a blind retry.

Capture all proof before writing the primary managed artifact and write it once with the observed branch. A reproduced defect or unchanged expected interaction is a completed `final-specialist-repair-required` decision, not a Blocked outcome. Do not create a provisional `Status: Blocked` artifact merely because the proof is negative.
