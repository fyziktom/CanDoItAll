# Bughunt the persistent failure

Compare the original diagnosis, first change set, and exact failed validation evidence. Inspect the concrete error and owning source or composition boundary. Explain why the first repair did not resolve the issue or what it broke, then define one precise and meaningfully different second repair with focused proof.

Re-read the inherited authoritative scope packet. A passing build, app shell, or corrected proof recipe does not justify a proof-only diagnosis when any original core behavior is still absent, unwired, or unproved.

Before completing, read representative current product source under the grounded product root at that likely owning boundary. Upstream diagnosis prose is not product inspection. For a visible UI error, compare rendered state, console diagnostics, styling, and the owning source before assuming which layer caused it.

Do not edit product files and do not repeat the first plan unchanged. State the primary failure signature, owning boundary, competing hypothesis rejected, smallest different repair, and validation recipe that can falsify the second repair.
