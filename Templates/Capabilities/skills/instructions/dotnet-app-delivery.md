Deliver .NET applications with a real scaffold, explicit validation, and durable proof. Use this skill as a .NET specialization of the concrete deliverable delivery skill. It is generic across .NET app domains and project types: console apps, class libraries with tests, web APIs, worker services, ASP.NET Core apps, and Blazor apps.

Start from the project-structure node or step contract. If it names a concrete output directory, treat that directory as the product root even when it is outside the managed workspace. Use `external-target/<drive>/...` aliases for workspace file and dotnet tools when needed. Do not substitute `artifacts/...`, `output/...`, or execution-run evidence folders for the product working directory unless the project structure explicitly says those are the product files.

For greenfield work with an explicit output root and no more specific scaffold contract, split that root into a parent folder and project folder before scaffolding. Example: output root `C:\work\apps\<AppName>` maps to product root `external-target/C/work/apps/<AppName>`; call `workspace_dotnet_new` with `parentDirectory: external-target/C/work/apps` and `name: <AppName>`. When a process scaffold contract names a solution file at the product root, a `src/` app layout, or exact `parentDirectory`/`name` values, that contract overrides this generic shortcut; keep every `workspace_dotnet_new` target inside the grounded product root. Before any scaffold call, check the mapped product root with `workspace_stat_path` or `workspace_list_files` unless the current step already proved the path is absent. If the mapped product root already exists and contains a project or solution, inspect and repair it in place instead of calling `workspace_dotnet_new`, creating a sibling, or writing a managed artifact copy. Then build, test, run, inspect, and summarize files under the mapped product root.

When an exact generated product root is named, resolve the runnable host and test topology from the current delivery contract and grounded project-structure aliases. A root-level host, a `src/` host, a nested test project, or a contract-declared sibling project can all be valid. Treat a sibling, nested project, temporary probe, copied scaffold, or scratch project as a defect only when it is undeclared and substitutes for a declared product or test target. Do not set `BaseOutputPath`, `BaseIntermediateOutputPath`, or `MSBuildProjectExtensionsPath` as an ungrounded path workaround; change output topology only when the contract or a concrete build diagnostic requires it.

Keep generated app projects, support libraries, test projects, scripts, static assets, and evidence helpers inside the roots grounded by the current contract or project structure. For `workspace_dotnet_new`, choose `parentDirectory` and `name` pairs that resolve to the declared topology. Do not impose a universal sibling, `src/`, `tests/`, or `Tests/` layout: use the supplied solution/project aliases and declared project relationships. If no topology is declared for a new small app, choose a conventional contained layout under the product root and record that assumption. Do not create deliverable source, tests, helpers, or assets under managed evidence roots such as `artifacts/`, `output/`, `data/`, or `integration-map/` unless the project structure names one as a product root. If policy denies an ungrounded parent, treat the parent as wrong; do not retry the same parent.

SDK-style default items can include nested project files and outputs. Inspect the declared project graph and the concrete build diagnostic before changing item inclusion or output paths. If a host compiles test sources, copies nested outputs recursively, or reports static-web-asset collisions, repair the responsible project boundary with exclusions or topology changes that fit the existing contract; do not add unrelated packages, impose a different layout pre-emptively, or retry the same command without new evidence.

Keep the requested product domain authoritative. Do not reuse sample app names, old external target paths, remembered source files, or topic-specific acceptance criteria from prior runs unless the current project structure, work brief, or upstream artifact explicitly names them for this run. If policy denies an external-target path, treat the denied path as invalid context for this run; switch to the current grounded product root or current-run artifacts and do not retry that path. Never inspect, cite, copy, or infer implementation patterns from sibling external-target applications on the same host. The scaffold parent directory is only a `workspace_dotnet_new` argument; it is not a product root, source corpus, evidence source, or permission to read sibling folders. Framework patterns must come from loaded skills, official templates, tool descriptions, component-library resources, or current-run artifacts. Do not claim contextual examples, source files, templates, or implementation references were reviewed unless this execution actually inspected them through current-run tools or loaded them from attached skill/template resources.

For greenfield work, create real projects rather than loose source files. Use `workspace_dotnet_new` for approved current SDK templates that match the deliverable type only after confirming the intended root is missing or safe to scaffold. Keep runnable hosts and tests in a clear layout under the product root, and inspect the generated `.csproj`, entry point, and test project before replacing scaffold content. For existing work, repair in place and do not force re-scaffold over non-empty project directories. If a scaffold command returns an unsuccessful result, treat it as a failed attempt, inspect the result, and correct the template or path before retrying; do not assume a failed scaffold created a usable project.

For greenfield scaffold replacement, budget the tool loop around product mutation. Use one bounded file listing, inspect only the project/import/entry files and direct mutation targets, and do not read every stock template page before the first write. When several related product files must change, prefer a bounded current-run PowerShell helper executed through `workspace_pwsh_run_script` with the grounded product alias as `workingDirectory` and a `ProductMutation` side-effect manifest restricted to that alias. Inside the helper, `(Get-Location).Path` is the product root; join only product-root-relative child paths and never append the `external-target/...` alias to the current directory. If a helper invocation fails and you correct the helper, verify and invoke the corrected version again in the same execution; a helper rewrite is not a successful product mutation receipt. Then read back representative changed production and test files. Never write the final managed artifact while the product remains read-only.

Workspace command timeout arguments are seconds, not milliseconds. Prefer the tool defaults unless there is a concrete need for a longer run. For generated app tests, use `300` seconds or less unless a concrete diagnostic proves the tests need more time.

Keep domain and application logic strongly typed and testable. Put non-trivial behavior in public classes under a clear domain or application namespace, then reference the host or support library from a separate test project under the grounded product root with a `ProjectReference`. Avoid root namespace/type collisions, weakly typed state, hidden lifecycle side effects, and silent fallback paths that hide real failures.

When the requested deliverable is an app with a user-facing surface, implement a real surface for the requested topic. Do not stop with only a support library, tests, markdown notes, or an untouched template host. Replace placeholder routes, starter copy, and stock navigation with a topic-specific workflow, then prove the running app through the relevant runtime or browser tools. For greenfield user-facing apps, remove or replace stock visible scaffold chrome such as `Counter`, `Weather`, `About`, default sidebar links, starter home copy, and placeholder sample data unless the current request explicitly asks to keep them. Browser screenshots, snapshots, console logs, and state outputs must be current-run evidence, not chat-only claims or stale prior-run files, and at least one UI proof artifact must show a meaningful filled, selected, or changed state for the primary workflow. If browser tools return provider-native filenames before managed artifact import, cite those filenames; do not fail or escalate solely because workspace file tools cannot see the managed browser folder during the same attempt. For project-structure handoff, do not create a node per validation command or screenshot attempt; use the final accepted screenshot ImageAsset, one run-app proof node, one run-tests proof node, and one manager summary node, with detailed logs left under managed artifacts.

When the project structure includes a source visual target ImageAsset, treat it as implementation input. Inspect or resolve its media path when available, derive the visible composition and interaction state it implies, and make the primary route materially align with that target within the requested scope. If you cannot access or analyze the image with the assigned tools, record that blocker instead of building from memory.

For web, Blazor, or static-hosted app delivery, inspect the entry document after final source mutations and make every local `href` and `src` resolve to a real product-root asset or generated framework asset. Do not leave stale links to `css/app.css`, Bootstrap, icons, manifests, service workers, generated styles, or scripts when those files do not exist at the referenced path. If a scaffolded or generated app writes `wwwroot/app.css`, either reference `app.css` or move it to `wwwroot/css/app.css`. Browser console 404s for local product assets are validation failures, not harmless noise. For user-facing web surfaces, custom route/component class names must be backed by a loaded stylesheet or scoped component stylesheet; a page with domain-specific classes but only stock template CSS is a product defect.

For Blazor WebAssembly delivery, verify the complete runtime dependency graph from actual component and service injection sites through transitive dependencies. Register the intended abstractions, implementations, and lifetimes in the WebAssembly host, and base any repair on the current compiler, host, or post-start browser diagnostic rather than a remembered service recipe. Inspect the entry document and JavaScript loading model when current evidence points to an interop or bootstrap failure. A page that remains on the loading placeholder, renders blank, or has no enabled visible controls after current startup is a product defect even when build, test, and HTTP startup smoke pass. Validate service-worker registration, installation, update, cache, offline, or other PWA behavior only when the resolved delivery contract requires that capability.

Preserve the template-selected `TargetFramework` unless a concrete build or SDK error proves it cannot be used in the current environment. Do not downgrade or retarget projects to a remembered default framework. If a retarget is genuinely required, update every related project consistently, remove or replace APIs that are unavailable on the new framework, rerun restore/build/test, and run the host again when the deliverable is runnable.

Use the test framework selected by the resolved contract or existing test project. For greenfield work with no declared framework, choose one supported current SDK template once and keep it consistent. Do not combine runners, manually convert a scaffolded test project without diagnostic cause, invent package versions, or upgrade from memory. Preserve generated or centrally managed packages unless restore output proves a change is required. Diagnose compiler and analyzer messages against the actual framework and package version, then apply the supported framework-specific repair shown by that evidence. Prefer `ProjectReference` for declared project relationships, and do not use broad source globs as a substitute for a clean project boundary.

Do not add XML documentation comments unless the user explicitly asks for them or the existing project already uses that convention. Keep comments rare and focused on non-obvious behavior.

Validation is part of implementation. After source changes, run the narrowest relevant `workspace_dotnet_restore`, `workspace_dotnet_build`, and `workspace_dotnet_test` sequence. The .NET restore/build/test tools may target explicit `.csproj`, `.sln`, or `.slnx` files; they also accept an unambiguous project directory, but pass an explicit file when a directory contains multiple candidate projects. For generated or greenfield test projects, keep tests deterministic and bounded: do not write `while` loops that depend only on mutable app/UI state without a maximum iteration guard and an assertion that each state transition succeeded. Build, test, and analyzer warnings in generated deliverables are validation defects, not ignorable risks; if a warning cites an editable product or test file, edit that file and rerun the same command until the warning is gone before finalizing. Use a `workspace_dotnet_test` timeout of 300 seconds or less unless a real diagnostic proves the generated app tests need more time. For runnable console or worker-style projects, use `workspace_dotnet_run` with `waitForHttp: false` when a runtime smoke is required. For ASP.NET Core, web API, or Blazor apps, build first, then use `workspace_dotnet_run` with loopback HTTP startup proof. `workspace_dotnet_run` targetPath must be a runnable project file; prefer `DotNetAppProjectFileAlias` and then `DotNetAppProjectFile`, and never pass a `.sln`, `.slnx`, product root, app project directory, or other directory as the run target. Leave `keepAlive` false for startup proof that does not need same-step browser follow-up. If the same step must run Playwright/browser checks, set `keepAlive: true` with `lifetimeScope: ExecutionRun`, capture screenshot `.png`, browser_snapshot `.yml` or browser_evaluate `.json`/`.txt`/`.md` state output, and browser_console_messages `.log` as current-run evidence, then call `workspace_dotnet_stop` with the recorded `startup.json` receipt before finalizing and cite its `cleanup.json` proof. If `workspace_analyze_image` is available, use it on accepted or rejected screenshot files and cite the provider/model/token result for visual claims; if the assigned provider/model is not vision-capable, block that visual-analysis gap instead of accepting screenshot metadata alone. For time-dependent, animated, queued, asynchronous, or continuously progressing UI behavior, capture before/after state over elapsed time and prove the observable state changed as expected; if the product wording or acceptance criteria imply automatic progression, manual input proof is not a substitute. A single static screenshot is insufficient. Use `lifetimeScope: ProcessRun` only when the process graph has separate later capture and cleanup steps that consume the startup receipt.

When launch variables provide `DotNetSolutionFileAlias`, `DotNetAppProjectFileAlias`, or `DotNetTestProjectFileAlias`, use those exact grounded files before probing for alternatives. A missing guessed root-level `<App>.csproj` is not a blocker when the supplied app-project alias resolves under `src/` or another declared layout. Inspect that declared location and continue the validation yourself. Do not ask a manager to assign another agent merely because this step has not executed its required receipts yet; if the validation tools are attached, the current validation role owns calling them.

If `workspace_dotnet_restore`, `workspace_dotnet_build`, `workspace_dotnet_test`, or `workspace_dotnet_run` fails, read the returned stdout/stderr previews and any referenced `stdout.txt`, `stderr.txt`, request, or receipt artifacts before editing. Do not repeatedly rewrite `.csproj` files, retarget frameworks, add packages, change test runners, or rerun the same command from exit code alone. Diagnose the concrete compiler, restore, test, startup, or route error first, make the smallest targeted fix, then rerun the same failing command. If stdout/stderr are truncated, read the artifact paths supplied by the tool before repairing.

Final product-validation order: finish the last product source/content/configuration mutation first, then rerun every required validation that could be affected, then read at least one representative changed product file, then write durable evidence artifacts, then submit the governed step outcome. Do not mutate product files after that final read. Evidence artifacts under managed `artifacts/`, `output/`, `data/`, or `integration-map/` roots are proof records, not a reason to repeat product validation unless they are the requested product deliverable.

Before final evidence artifacts or a governed outcome, read at least one representative changed product file after the final product mutation. For app work, prefer the changed `.csproj`, entry point, routed page, domain/application class, or test source that best proves the delivered behavior. If you change another product file after that read, repeat the read and rerun the required build, test, run, browser, or deliverable validation before concluding.

If a command fails, inspect stdout, stderr, receipts, and the concrete project files before retrying. Do not repeat the same failed command until you change the cause or gather new diagnostics. Do not claim completion with only markdown evidence when source, build, test, run, browser, or artifact proof was required.

When writing xUnit tests, include a visible `using Xunit;` or project-level global using before using xUnit attributes or assertions.

Never make validation pass by writing fake package, framework, runtime, browser, or test-tool shims. Do not define local `Microsoft.VisualStudio.TestTools.UnitTesting`, `Xunit`, `NUnit.Framework`, browser API, or ASP.NET Core replacement namespaces/classes to satisfy compilation. Fix the real package restore, project references, test framework choice, target framework, or environment issue; if that is impossible with available tools, return a concrete blocker instead of hiding it.
