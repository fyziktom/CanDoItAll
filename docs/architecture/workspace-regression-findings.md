## Evidence and harness corrections

The Data Sources owner assertion originally ignored a seeded target preference;
its repair compares the exact target before and after refusal. The Workflow fixture
needed an explicit free tariff for its scripted provider. The Scheduler journey now
uses one actual seven-field, one-shot Quartz expression instead of a recurring minute
schedule. Each failed attempt remains separately retained.

Agent token text is not streamed into the current transcript. Its actual activity
stream shows progress and the completed turn supplies the persisted text. The test
therefore holds the external response while asserting the responding phase, then
requires the completed message, tool receipt and file hash. This is not a new product
capability and is not live-provider proof. Navigation checks wait for the existing
shell listener before operating controls, avoiding prerender/hydration overlap.

The first live file attempt encountered an approval acknowledgement while its old
button was still rendered. One case tried to reject the same proposal again; the other
required a pending proposal after it had already been approved. The harness now tracks
the typed business-intent identity and submits each decision once, then observes its
terminal owner result. It neither repeats a mutation nor accepts a new proposal silently.
The original two failed cases consumed four and six provider requests respectively.

The second positive attempt exposed a different observation interval: the owner had
a Pending proposal before its approval ID was registered, while the preceding control
was still visible. It consumed seven requests. The harness now requires a nonempty
approval ID and that exact enabled control before recording its one decision. The
negative-control retry passed with four requests and exact unchanged node/content checks.

The final positive attempt consumed nine requests, reaching the campaign's forty-request
limit. Its spend guard disposed the private database before the final evidence read,
which failed with PostgreSQL `3D000`. The raw TRX and nine durable proxy reservations
remain; complete owner proof from that attempt is unavailable. The exact guard trigger
(the existing ten-batch check or the proxy's next-request refusal) was not captured.
The harness now stops only the owned application process at the guard, retaining the
database until failure evidence is collected and normal disposal completes. Neither
guard nor budget was raised. A complete live repeat requires a separately authorised
campaign; no successful attachment, final read-back or rollback is inferred here.

`campaign-live-host-retirement` passes a deterministic production-browser regression:
it saves a unique Workspace value through the real UI, stops the owned Web process twice,
requires the HTTP endpoint to be unavailable, and reads that persisted value through a
fresh owner scope while the browser can still create an evidence page. The private
database and browser are disposed only afterward. It makes zero model requests and
does not turn the failed live file journey into a pass.

The first live Workflow fixture explicitly supplied temperature zero to a model that
rejects that parameter. The owner and provider journal correctly recorded failure after
one request. The retry uses the existing nullable temperature setting (provider decides),
keeps the 150-token setting, and uses the repaired token-limit handoff. No temperature
fallback, provider model substitution or budget increase is introduced.

The second Workflow request received HTTP 200, but its provider journal and persisted
Workflow run both failed. Its exact diagnostic was truncated in the runner output.
The response may have been incomplete under the 150-token cap, but the response body
was not retained, so that is a hypothesis, not a proven cause. Future attempts preserve
the sanitised terminal UI result and a failure screenshot. The campaign has no remaining
live requests; this is an open live-validation finding, not evidence that the deterministic
Workflow/asset path failed. See [the live follow-up map](workspace-live-follow-up.md).

The inert plugin test executor proves real registration and invocation, but does not
implement the shipped grant evaluator. A denied invocation is instead checked against
the actual Office365 executor before OAuth or network work. No permissive production
fallback or new plugin authority was introduced.

## WC-F6: initialization replaced a newly acquired Data Sources editor

Final source review found that the runtime read could finish while the initial profile
list was still pending. That enabled New PostgreSQL profile; when the list completed,
`InitializeAsync` unconditionally selected the runtime profile and replaced the user's
new draft, EditContext, raw invalid port and validation state.

`Initial_list_completion_preserves_a_newly_acquired_form_and_raw_input` holds the list
read, clicks the real New control, edits the real text/number components, then releases
the list. Its original attempt failed on draft identity, showing Workspace A in place
of the newly acquired draft. The repair captures the editor revision before initialization
reads and only performs the initial automatic selection if that revision is unchanged.
Explicit user selection still uses its existing read lane; no owner command, authority,
database-selection rule or mutation outcome changes.

The failing-first and repaired attempts are retained as
`data-sources-initial-acquisition-before` and `data-sources-initial-acquisition-after`.
The complete leaf now contains 21 passing cases. A mistyped initial leaf filter selected
zero cases and was rejected by the expected-count check. The first host rerun omitted
the isolated-database flag and safely refused 12 database cases; its two pure cases passed.
Those attempts remain separate from the correctly configured revalidation.

The correctly configured reruns pass all 14 host/MainLayout/lifetime cases and all seven
production/sandbox browser cases. Fresh owner reads confirm that profile A remains
canonical before restart, B becomes canonical afterward, the preference group committed,
the later Project group was refused, and the instance API accounts/tokens were preserved.
The source and published sandbox still retain raw invalid input and partial group receipts.

This is a defect introduced in the new W2 initialization path, with controlled causal
proof. Its fix is UI-only. The affected host, production two-database and source/published
sandbox proofs are explicitly repeated; it does not invalidate unchanged integration
owner implementations or justify rerunning external-model requests after the budget cap.
