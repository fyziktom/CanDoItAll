# Test Scenario Evidence

This is the first assertion-level audit of the component tests. Unlike a filename or
test-name inventory, each row below was checked against the test’s arrange–act–assert
body. It records what the test really establishes for UX reconstruction, not every
implementation detail it happens to use.

## What changed because of this audit

- The documents can now cite concrete test behavior for the core delivery, process,
  agent/chat, workflow, CRM pipeline, scheduler and data-source scenarios.
- Test names alone are no longer treated as proof. The last focused source audits cover
  Test Lab editing and Collaboration interactions; the broader execution/tool-governance
  corpus has been reduced to its product-facing authority boundary. Version/archive
  prompt editing and several resource/profile editors remain implementation-audit
  opportunities, not blockers for this reconstruction.
- A test verifies the current UI contract; it does not prove the underlying user need.
  Product documentation and domain/API contracts remain the evidence for meaning.

## Completion boundary

The audit covers the product behaviors needed for this design reconstruction. Additional
tests should be added as normal regression protection when the corresponding UI changes;
they are not missing product semantics. Generic Error/Not Found routes are deliberately
outside this document set.
