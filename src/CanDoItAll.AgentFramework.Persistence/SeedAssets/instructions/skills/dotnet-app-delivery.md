Deliver .NET applications with a real scaffold, explicit validation, and durable proof. Use this skill as a .NET specialization of the concrete deliverable delivery skill. It is generic across .NET app domains and project types: console apps, class libraries with tests, web APIs, worker services, ASP.NET Core apps, and Blazor apps.

Start from the project-structure node or step contract. If it names a concrete output directory, treat that directory as the product root even when it is outside the managed workspace. Use `external-target/<drive>/...` aliases for workspace file and dotnet tools when needed. Do not substitute `artifacts/...`, `output/...`, or execution-run evidence folders for the product working directory unless the project structure explicitly says those are the product files.

For greenfield work with an explicit output root, split that root into a parent folder and project folder before scaffolding. Example: output root `C:\work\apps\<AppName>` maps to product root `external-target/C/work/apps/<AppName>`; call `workspace_dotnet_new` with `parentDirectory: external-target/C/work/apps` and `name: <AppName>`. Before any scaffold call, check the mapped product root with `workspace_stat_path` or `workspace_list_files` unless the current step already proved the path is absent. If the mapped product root already exists and contains a project or solution, inspect and repair it in place instead of calling `workspace_dotnet_new`, creating a sibling, or writing a managed artifact copy. Then build, test, run, inspect, and summarize files under the mapped product root.

When a grounded product root exists, keep every generated app project, support library, test project, script, static asset, and evidence helper inside that product root unless the project structure explicitly grants another root. For `workspace_dotnet_new`, choose `parentDirectory` and `name` pairs that resolve inside the grounded product root. A test project can live under a child such as `external-target/C/work/apps/<AppName>/tests` or `external-target/C/work/apps/<AppName>/Tests`, but do not create a sibling such as `external-target/C/work/apps/<AppName>.Tests` unless that sibling path is explicitly grounded for this run. When scaffolding tests, use `parentDirectory: <product-root>/tests` and `name: <AppName>.Tests`; never reuse the app scaffold parent such as `external-target/C/work/apps` with `name: <AppName>.Tests`. For small apps, prefer source folders inside the host or main app project for testable domain/application code. If a separate support library is justified, put it under a child folder such as `<product-root>/src/<AppName>.Domain`, using `parentDirectory: <product-root>/src` and `name: <AppName>.Domain`; do not create `<product-parent>/<AppName>.Domain` as a sibling beside the product root. Do not create deliverable source, test projects, helper scripts, or generated assets under managed workspace roots such as `src/`, `tests/`, `tools/`, `output/`, or the bare workspace root when an external product root is grounded; those managed folders are only for current-run evidence unless the project structure explicitly names them as the product root. If policy denies an ungrounded parent, treat the parent as wrong; do not retry the same parent.

If a production SDK-style `.csproj` sits directly at the product root, remember that default items include child folders such as `tests/` and `Tests/`. Prefer a layout with production code under `<product-root>/src/<Host>` and tests under `<product-root>/tests`. If the host must stay at the product root and a child test folder exists, inspect the host `.csproj` before final validation and add a durable exclusion unless one already exists. The preferred host-project exclusion is a `PropertyGroup` entry such as `<DefaultItemExcludes>$(DefaultItemExcludes);tests/**;Tests/**</DefaultItemExcludes>` because it excludes compile, content, static web asset, and copied output items from the production project. Equivalent explicit `Compile`, `Content`, `None`, and `EmbeddedResource` `Remove` entries are acceptable when they match the project style. Use XML path separators in project files; do not write JSON/C#-escaped globs such as `Tests\\**\\*.cs`. If the production build reports missing `Xunit`, `Fact`, `MSTest`, or test attribute namespaces, inspect for test sources compiled by the production host and fix the layout or exclusions; do not add test framework packages to the production project as a shortcut. If build or test output shows repeated nested paths such as `tests/<TestProject>/bin/.../tests/<TestProject>/bin/...`, `MSB3030` copy failures, missing `.staticwebassets.runtime.json`, missing `.staticwebassets.endpoints.json`, missing test `runtimeconfig.json`, or missing `project.assets.json` from nested test output, treat it as host default-item/static-web-asset bleed from child test output. Repair the host layout or exclusions before rerunning; do not finalize, invent package versions, or keep retrying the same command.

Keep the requested product domain authoritative. Do not reuse sample app names, old external target paths, remembered source files, or topic-specific acceptance criteria from prior runs unless the current project structure, work brief, or upstream artifact explicitly names them for this run. If policy denies an external-target path, treat the denied path as invalid context for this run; switch to the current grounded product root or current-run artifacts and do not retry that path. Never inspect, cite, copy, or infer implementation patterns from sibling external-target applications on the same host. The scaffold parent directory is only a `workspace_dotnet_new` argument; it is not a product root, source corpus, evidence source, or permission to read sibling folders. Framework patterns must come from loaded skills, official templates, tool descriptions, component-library resources, or current-run artifacts. Do not claim contextual examples, source files, templates, or implementation references were reviewed unless this execution actually inspected them through current-run tools or loaded them from attached skill/template resources.

For greenfield work, create real projects rather than loose source files. Use `workspace_dotnet_new` for approved current SDK templates that match the deliverable type only after confirming the intended root is missing or safe to scaffold. Keep runnable hosts and tests in a clear layout under the product root, and inspect the generated `.csproj`, entry point, and test project before replacing scaffold content. For existing work, repair in place and do not force re-scaffold over non-empty project directories. If a scaffold command returns an unsuccessful result, treat it as a failed attempt, inspect the result, and correct the template or path before retrying; do not assume a failed scaffold created a usable project.

Workspace command timeout arguments are seconds, not milliseconds. Prefer the tool defaults unless there is a concrete need for a longer run; if you set a timeout, use normal second values such as `120`, `300`, `600`, or `1200`, not millisecond-style values such as `120000`.

Keep domain and application logic strongly typed and testable. Put non-trivial behavior in public classes under a clear domain or application namespace, then reference the host or support library from a separate test project under the grounded product root with a `ProjectReference`. Avoid root namespace/type collisions, weakly typed state, hidden lifecycle side effects, and silent fallback paths that hide real failures.

When the requested deliverable is an app with a user-facing surface, implement a real surface for the requested topic. Do not stop with only a support library, tests, markdown notes, or an untouched template host. Replace placeholder routes, starter copy, and stock navigation with a topic-specific workflow, then prove the running app through the relevant runtime or browser tools.

Preserve the template-selected `TargetFramework` unless a concrete build or SDK error proves it cannot be used in the current environment. Do not downgrade or retarget projects to a remembered default framework. If a retarget is genuinely required, update every related project consistently, remove or replace APIs that are unavailable on the new framework, rerun restore/build/test, and run the host again when the deliverable is runnable.

Use one test framework per test project. Choose it before the first test-project scaffold, do not scaffold the same test-project root with a different template, and do not manually convert a generated test `.csproj` from one runner to another in the same attempt. Do not layer MSTest and xUnit or other runners into the same project after scaffolding; replace placeholder tests in the chosen framework instead. Preserve the package family and versions produced by `workspace_dotnet_new` unless diagnostics prove they are unavailable. Do not invent package versions or "upgrade" to remembered latest versions. If restore reports `NU1102` or a nearest available package version, use that diagnostic, the generated template package set, existing central package management, or the current project's package pattern before editing references; otherwise return a blocker instead of guessing. Prefer `ProjectReference` to tested projects, or place reusable logic in a small library under the grounded product root. Do not rely on broad source-file globs into the app host as a substitute for a clean project boundary.

Do not add XML documentation comments unless the user explicitly asks for them or the existing project already uses that convention. Keep comments rare and focused on non-obvious behavior.

Validation is part of implementation. After source changes, run the narrowest relevant `workspace_dotnet_restore`, `workspace_dotnet_build`, and `workspace_dotnet_test` sequence. The .NET tools may target explicit `.csproj`, `.sln`, or `.slnx` files; they also accept an unambiguous project directory, but pass an explicit file when a directory contains multiple candidate projects. For runnable console or worker-style projects, use `workspace_dotnet_run` with `waitForHttp: false` when a runtime smoke is required. For ASP.NET Core, web API, or Blazor apps, build first, then use `workspace_dotnet_run` with loopback HTTP startup proof and follow with Playwright/browser checks when the user-facing surface matters.

If `workspace_dotnet_restore`, `workspace_dotnet_build`, `workspace_dotnet_test`, or `workspace_dotnet_run` fails, read the returned stdout/stderr previews and any referenced `stdout.txt`, `stderr.txt`, request, or receipt artifacts before editing. Do not repeatedly rewrite `.csproj` files, retarget frameworks, add packages, change test runners, or rerun the same command from exit code alone. Diagnose the concrete compiler, restore, test, startup, or route error first, make the smallest targeted fix, then rerun the same failing command. If stdout/stderr are truncated, read the artifact paths supplied by the tool before repairing.

Final product-validation order: finish the last product source/content/configuration mutation first, then rerun every required validation that could be affected, then read at least one representative changed product file, then write durable evidence artifacts, then submit the governed step outcome. Do not mutate product files after that final read. Evidence artifacts under managed `artifacts/`, `output/`, `data/`, or `integration-map/` roots are proof records, not a reason to repeat product validation unless they are the requested product deliverable.

Before final evidence artifacts or a governed outcome, read at least one representative changed product file after the final product mutation. For app work, prefer the changed `.csproj`, entry point, routed page, domain/application class, or test source that best proves the delivered behavior. If you change another product file after that read, repeat the read and rerun the required build, test, run, browser, or deliverable validation before concluding.

If a command fails, inspect stdout, stderr, receipts, and the concrete project files before retrying. Do not repeat the same failed command until you change the cause or gather new diagnostics. Do not claim completion with only markdown evidence when source, build, test, run, browser, or artifact proof was required.

Never make validation pass by writing fake package, framework, runtime, browser, or test-tool shims. Do not define local `Microsoft.VisualStudio.TestTools.UnitTesting`, `Xunit`, `NUnit.Framework`, browser API, or ASP.NET Core replacement namespaces/classes to satisfy compilation. Fix the real package restore, project references, test framework choice, target framework, or environment issue; if that is impossible with available tools, return a concrete blocker instead of hiding it.
